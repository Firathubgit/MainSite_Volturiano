██  MEGA-PROMPT 1 of 5: The "Iron-Clad" Database Security Foundation (SQL & RLS) ✅
================================================================================

CONTEXT:
You are the Lead Database Architect for Volturiano Builder. We are implementing a mission-critical
billing system that must be immune to frontend tampering, race conditions, and "double-spending."
The source of truth for all credits must live inside the PostgreSQL engine in Supabase.

LOCATION:
This prompt focuses on executing SQL in the Supabase Dashboard. No files are modified except 
recording the migration in your internal logs or project documentation.

DATABASE STATE:
- Existing table `profiles`: id (uuid), username, plan (text), created_at.
- Existing table `credit_transactions`: id, user_id, amount, type, description, created_at.

TASK:
Implement the secure foundation for the credit system by running the following SQL logic. This 
logic MUST ensure that users cannot manually update their own balances through the API.

1. SCHEMA ENHANCEMENT:
   - Add the following columns to the `profiles` table:
     • total_credits_purchased (INTEGER, default 0) - Persistent paid credits.
     • daily_credits_limit (INTEGER, default 15) - Free tier limit.
     • daily_credits_used (INTEGER, default 0) - Tracking daily free usage.
     • daily_credits_reset_at (TIMESTAMPTZ, default now()) - When to reset the daily counter.

2. ATOMIC DEDUCTION FUNCTION (`deduct_credits_safe`):
   - Create a PostgreSQL function that performs the check and subtraction in ONE atomic step.
   - Requirements:
     • Use a ROW LOCK (`FOR UPDATE`) on the profile row to prevent concurrent request hacking.
     • Reset the `daily_credits_used` if `daily_credits_reset_at` is in the past.
     • Deduction Priority: Use "Daily Free" credits first, then "Purchased" credits.
     • Handle 'admin' and 'enterprise' plans (unlimited usage, just log the transaction).
     • Insert a record into `credit_transactions` on every successful deduction.
     • Return a JSON object: `{ "success": boolean, "error": string | null }`.
   - Security: Set the function to `SECURITY DEFINER` so it can bypass RLS but is only callable via RPC or internal logic.

3. ROW LEVEL SECURITY (RLS) LOCKDOWN:
   - Enable RLS on the `profiles` table.
   - Create a policy that allows users to SELECT their own profile.
   - Create a policy for UPDATE that EXPLICITLY forbids touching the credit columns.
     The `WITH CHECK` clause must ensure `total_credits_purchased`, `daily_credits_limit`, 
     and `plan` remain identical to their previous state in any user-initiated update.

4. CREDIT ADDITION FUNCTION (`add_credits_safe`):
   - A secure function for the Stripe Webhook to call.
   - Adds the specified amount to `total_credits_purchased` and logs the transaction.

GOAL:
After this prompt, any attempt by a user to change their credit count using `supabase.from('profiles').update(...)`
will be REJECTED by the database, while the `deduct_credits_safe` function remains the only 
sanctioned way to use a service.

ESTIMATED LINES OF LOGIC: 80+ lines of SQL.

entire infrastructure.

   - Stripe Webhooks require the RAW request body for signature verification.
   - Update `web/server/index.js` to use `express.raw` for the `/api/webhooks/stripe` path 
     BEFORE the standard `express.json()` middleware.

   - Implement `POST /api/webhooks/stripe`.
   - SIGNATURE VERIFICATION: Use `stripe.webhooks.constructEvent` with your webhook secret.
   - Logic for `checkout.session.completed`:
     • Extract `user_id` and `credit_amount` from the `session.metadata`.
     • Sanity Check: Ensure the amount is a positive integer.
     • Call the Supabase RPC `add_credits_safe` (created in Prompt 1) using the `supabaseAdmin` 
       client (service role). This bypasses user RLS because it's a server-level action.
     • Log the success with the Stripe Session ID for auditing.

3. ERROR HANDLING:
   - If the signature is invalid, return a 400 immediately.
   - If the DB update fails, log the error but return a 200/500 depending on if we want Stripe 
     to retry (recommending 200 to acknowledge receipt, but logging for manual fix).

GOAL:

exactly the right number of credits added, with zero possibility of spoofed payments.
