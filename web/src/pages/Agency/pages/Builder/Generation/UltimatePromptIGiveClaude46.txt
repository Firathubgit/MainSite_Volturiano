“Pipelineanalys av Lovable, Google AI Studio, Base44, Replit och Emergent
Sammanfattning för beslutsfattare
De fem plattformarna implementerar i praktiken samma övergripande “agentisk webbbyggar‑pipeline”: (1) användarinput normaliseras och kompletteras med projekt‑/kodbas‑kontext, (2) en LLM drivs i en iterativ loop som både planerar och exekverar via verktyg (filändringar, testkörningar, integreringar), (3) resultat parsas till patchar/filträd/konfigurationsändringar, (4) förändringar verifieras i runtime (preview, loggar, browser‑tester), och (5) artefakter publiceras eller exporteras (t.ex. GitHub/deploy). Det som skiljer leverantörerna är främst: hur explicit planeringsfasen är, hur verktygsanrop och verifiering exponeras i UI, hur kontext och kostnad kontrolleras i långa trajectories, samt hur multi‑tenant‑isolering/säkerhet implementeras. 
Lovable, Base44 och Replit har tydliga “tänk‑först, bygg‑sen”‑mönster: Lovable har Plan‑läge och Agent‑läge med synliga tasks/verktyg och en prompt‑kö som möjliggör batchning och upprepning.  Base44 har ett separat Discuss‑läge där inga appändringar görs (lägre kreditkostnad), och Visual Edit‑läge som binder UI‑selektioner till kodändringar.  Replit har Plan vs Build och dessutom Fast vs Full build, med inbyggd autonom testning (”automated browser testing”) och checkpoints/rollback som spänner över kod, konfiguration och databaser. 
Google AI Studio (Build/vibe coding) är bäst förstått som ett “prompt‑till‑webbapp”‑arbetsflöde ovanpå Gemini‑ekosystemet: användare genererar och itererar på kod i AI Studio, sätter långlivade System Instructions (“persona”), sparar till GitHub och kan deploya till Cloud Run via UI; centrala underliggande byggblock är Gemini API:s verktygs-/function calling, strukturerade outputs (JSON Schema), säkerhetsfilter, kvoter/rate limits samt kontext‑caching för kostnad/latens. 
Emergent framstår – utifrån publika tutorials och app‑beskrivningar – som en multi‑agent‑orkestrering (planering, frontend, backend, test, deploy) med “Universal Key” som kan routa mellan flera LLM‑leverantörer och konsolidera billing. Emergent betonar en standardiserad fullstack‑runtime (FastAPI + React + MongoDB) med preview, “health check” inför deploy, och one‑click deployment med separata preview/production‑miljöer. 
Metod, källor och osäkerheter
Analysen bygger primärt på officiella produktdokument (Lovable Docs, Base44 Docs, Replit Docs), engineering‑bloggar (särskilt Replit), samt officiella Google‑resurser (Google AI Developers, Google Developers Blog, codelabs). Där Emergent‑hjälpcentret inte gick att läsa utan JavaScript användes istället Emergent‑tutorials och publika policysnuttar. 
Viktigt bevisläge: de interna systemprompterna, exakta verktygs‑schema (function signatures), modellroutinglogik, cache‑nycklar, samt interna säkerhetsklassificerare är normalt inte offentliga. För dessa delar anges därför (a) explicita antaganden och (b) alternativa plausibla designval baserade på vad plattformarna exponerar (t.ex. Plan/Agent‑lägen, testverktyg, GitHub‑koppling, “decision‑time guidance”, checkpoints). 
När “chain‑of‑thought” efterfrågas i en sådan jämförelse bör den tolkas som resoneringsstrategier på systemnivå (t.ex. plan→exekvera→verifiera, subagents, decision‑time prompt injection), inte som att leverantören publicerar privata mellanresonemang. Replit beskriver uttryckligen hur statiska prompts/few‑shot tappar styrka i långa trajectories och att de istället injicerar kort guidning vid beslutstillfällen. 
Referensarkitektur för agentiska webbbyggare
En “vibe coding”‑plattform som bygger och itererar på en riktig kodbas behöver fyra kärnprimitiver: (1) en kod-/projektrepresentation som kan läsas/patchas, (2) en isolerad runtime för preview/test (helst med browser‑automation), (3) en orkestrator som kör en agentloop och hanterar verktygsanrop, och (4) säkerhets- och kostnadskontroller (rate limits, krediter, secrets, policyfilter, rollback). Detta är direkt observerbart via Lovables Agent‑läge + testverktyg, Replits Agent + testning + checkpoints, och Base44:s chat‑lägen + Activity Monitor + secrets/integrations.

Nyckelsteg i praktiken
Input → kontext: Lovable har “Custom knowledge” som ska “kommas ihåg och tillämpas” över alla ändringar, och MCP‑anslutna verktyg (Notion/Linear/Jira m.fl.) kan ge strukturerat underlag som agenten läser och ibland skriver tillbaka till.  Base44 ger motsvarande via AI chat modes + AI Controls + möjlighet att koppla integrationer, samt en utvecklarstack där requests kan inspekteras (Activity Monitor).  Replit löser “working set”‑problemet genom att isolera testning i en subagent för att undvika kontextförorening. 
LLM‑anrop → parse: I Gemini‑världen är “structured outputs” (JSON Schema) ett centralt verktyg för stabil parsing, och function calling används för att låta modellen emitera parametriserade verktygsanrop.  Emergent‑tutorials beskriver explicit ett schema‑drivet “vision‑modell → JSON → text‑modell”‑flöde med Universal Key som routar. 
Iterativ loop: Lovable kör verktyg selektivt och kan använda browser testing när snabbare verifiering inte räcker; triggerfraser som “verify it works” nämns.  Replit driver loopar längre och lägger styrning “vid beslut” (decision-time guidance) för att hålla kostnad och kontext i schack. 
Publicering/rollback: Replit checkpoints tar snapshots av hela miljön inkl. databas (valbart vid rollback) och stödjer till och med “roll forward”.  Lovable har Test/Live‑miljöer där agenten alltid bygger i Test och Live endast uppdateras vid explicit publish. 
Leverantörspipelines och integrationer
Lovable
Lovable exponerar tre input‑vägar som är relevanta för pipelineanalys: vanlig chat‑prompt, Visual Edits (UI‑selektion), samt en “Build with URL”‑funktion där prompt och upp till 10 bild‑URL:er skickas via URL‑parametrar och kan autosubmittas; dokumentationen beskriver även inloggnings‑/workspace‑val‑flöde samt error handling som del av den publika API‑ytan. 
Efter input hamnar användaren i ett tvåläges‑system: Plan mode (beslutsfattande) och Agent mode (exekvering). Agent mode beskrivs som autonomt och “end‑to‑end”: agenten tolkar intent, utforskar kodbasen för kontext, gör multi‑fil‑ändringar och hanterar problem som uppstår. Under arbetet visas tasks med vilka filer och verktyg som används, och Lovable har en synlig prompt‑kö med pause/reorder/edit och möjlighet att repetera prompts upp till 50 gånger (en konkret UI‑mekanism för orkestrering). 
Verifikationsstegen är tydligt produktiserade: “Test and verify your app” beskriver browser testing, frontend tests och edge function verification; browser testing kör i en verklig browser i en virtuell miljö och kan ta screenshots, läsa console logs och nätverksrequests. Den körs selektivt och ofta först efter snabbare verifiering. 
Lovable Cloud definierar backend‑/deployment‑sidan av pipelinen: fullstack hosting, databas, auth, storage, edge functions, secrets och logs. Cloud‑verktyg kan styras av permissions (Always allow / Ask each time / Never allow), vilket är en explicit “tool gating”‑mekanism. Lovable Cloud sägs bygga på en öppen källkods‑grund från Supabase, och har dessutom Test/Live‑miljöer som separerar dev‑data från prod‑data, där Live endast uppdateras när du publicerar och där data/kontent inte kopieras efter initial setup. 
Integrationsytan är ovanligt bred för en “builder”: GitHub‑integration via OAuth + GitHub App, med tvåvägssync där repo blir “single source of truth” när kopplat; samt “personal connectors” via MCP (Model Context Protocol) som kan ansluta verktyg som Notion/Linear/Jira/Miro och även egna MCP‑servrar med OAuth/bearer/no‑auth. Detta är i praktiken RAG + tool‑use som kan mata agenten med icke‑kod‑kontext (PRDs, tickets, diagram). 
För AI‑funktioner i de appar du bygger har Lovable en separat “Lovable AI”‑connector: defaultmodell anges som “Gemini 3 Flash”, men användaren kan instruera agenten att använda andra modeller/combos. Prismässigt hävdas att kostnaden matchar underliggande LLM‑leverantör utan påslag, och att workspace har en “Cloud & AI balance”. 
Säkerhet och dataskydd är i Lovable en del av pipeline: “Security overview” beskriver fyra automatiserade scanners (RLS‑analys, DB security check, code security review, dependency audit) och en Security view där användaren kan lägga till säkerhetskontext för att minska false positives; samt en separat policy för träningsdata/PII (PII används inte “raw/identifiable” för träning; opt‑out på workspace‑nivå för Business/Enterprise). 
Base44
Base44 gör Plan/Execute‑separationen explicit i UI via tre chat‑lägen: Default (agerar direkt på prompts), Discuss (planera utan att ändra appen, “0.3 credits per message”), och Visual Edit där man antingen manuellt justerar design eller låter AI ändra det markerade elementet. Visual Edit skapar därmed en deterministisk “UI‑target selector” som kan minska prompt‑tvetydighet – ett praktiskt sätt att förbättra parsing av “vad menar du?”‑problemet. 
Base44 har dessutom tydligt exponerad modellrouting: användaren kan på högre plan välja “Automatic” eller “Manual” och explicit välja modeller (t.ex. Claude Sonnet/Opus, Gemini 3 Pro, GPT‑5) där kreditförbrukning varierar per modell. Det innebär att “Model Router” i referensarkitekturen antingen är ett internt beslutssteg eller ett användarstyrt valpunkt. 
På kod-/runtime‑sidan beskriver Base44 en klassisk webbstack: Base44‑appar är “standard React apps built with Vite” och har en Code Tab, en Activity Monitor som visar varje request under preview inklusive statuskoder och timing, och GitHub‑integration för tvåvägssync. Det ger tydliga observationskanaler (logs/requests) för agentloopens “observe”‑steg. 
Integrationsarkitekturen är relativt väl dokumenterad och har tre lager med olika säkerhetsprofil. Först “Connectors” (OAuth‑setup utan API‑nycklar) och inbyggda integrationer via chat. Sedan “Custom integrations” där en workspace‑admin importerar en OpenAPI‑spec och konfigurerar credentials; anrop proxas via Base44‑backend, så att secrets aldrig når webbläsaren, och integrationen delas av alla appar i workspacet. Slutligen “Backend functions” för app‑specifik logik där hemligheter hålls i servermiljön. 
Basen för dataflöden mellan frontend/backend är Base44 SDK: den är förinstallerad i genererade appar och kan även användas externt (npm‑paket @base44/sdk). Modulerna (“agents”, “app-logs”, “auth”, “connectors”, “entities”, “functions”, “integrations”) indikerar att Base44 har ett API‑lager där både agent‑samtal, loggfrågor, auth och integrationer är förstaklassobjekt. 
Base44:s publikdokumenterade prompt‑engineering är mer användarorienterad än systemintern: en “prompt formula” ges som mall, vilket i praktiken fungerar som en enkel prompt‑template med parametrar (funktion, layout, stil).
Replit
Replit Agent‑pipen är dokumenterad som ett flerläges‑system där Agent först klassificerar app‑typ utifrån prompt (t.ex. Web App) och användaren kan välja Fast build (~3–5 min) eller Full build (10+ min, mer autonomi och självtstning), samt Plan (plan innan bygget) eller Build (bygg direkt). Detta är en explicit “plan gate” plus en “autonomy budget”‑toggle som påverkar både latency och kostnad. 
Replit har en ovanligt utvecklad verifierings‑/observationsstack: “App Testing” beskrivs som automatiserad browser‑testning i “actual browser” som navigerar appen som en användare, identifierar problem och kan ge video‑replays; dessutom finns Workflows, Console/Logs, och Deployments som separerar dev och prod. 
Den tydligaste publika beskrivningen av hur Replit hanterar långa trajectories (där kontextfönster, kostnad och fel ackumuleras) är “Decision‑Time Guidance”: Replit argumenterar att omfattande statiska prompts/few‑shot kan bli dyra och opålitliga när sessioner blir långa, och beskriver i stället “decision‑time injection” där kort guidning läggs nära den punkt där agenten ska fatta nästa beslut. De kopplar detta till primacy/recency‑bias och visar att vissa instruktioner fungerar bättre när de injiceras sent i spåret. 
För testning i skala beskriver Replit en hybrid: de bryter ut testning i en separat subagent för att undvika “context pollution”, där huvudagenten ger en testplan, testsubagenten kör action/observe‑loop och sedan returnerar en sammanfattning och guidance. Man påstår att detta är en del av att nå “200 minutes of autonomous runtime” och anger en median‑kostnad per testsession på $0.20. 
Säkerhets- och rollback‑egenskaperna är centrala i Replits pipeline och är mycket mer än vanlig git. Replit checkpoints beskrivs som snapshots av hela app‑konteksten: workspace, AI‑kontext, miljökonfiguration och kopplade databaser; rollbacks kan (valbart) återställa utvecklingsdatabasen, och systemet stödjer även att rulla fram igen.  Replit beskriver även prompt‑scanning som avleder användaren till Secrets om de försöker klistra in API‑nycklar i chatten, samt “App History” med runnable snapshots (inkl. kod + DB snapshot) i upp till 7 dagar. 
Under huven beskriver Replit “Snapshot Engine” som en compute‑ och storage‑fabric där filsystem kan forkas snabbt och reversibelt. De nämner en blockdevice‑lösning via NBD mot Google Cloud Storage, chunking i 16 MiB immutabla chunks och manifest‑kopior för konstant‑tid‑kopiering. De beskriver guardrails såsom dev/prod‑split och att Agent begränsas till development database. 
Kostnadsmodellen är “effort‑based”: priset beror på tid och computation per request; små ändringar blir ofta billigare än tidigare $0.25/checkpoint, och stora builds bundlas i en checkpoint. Replit exponerar dessutom “High power model” och “Extended thinking” som per‑request kontroller.  Detta är i praktiken en prissatt “reasoning budget” i agentloopen.
Google AI Studio (Gemini‑driven webbbyggare)
Google beskriver AI Studio som en plats där man snabbt går från prompt till fungerande AI‑app genom “vibe coding”. Man betonar att AI Studio kan ta dig från idé till fungerande app utan att du själv behöver “wire up” API keys och koppla ihop modeller.  I en senare produktuppdatering lyfter Google “Starter Apps” och “native code editing” i AI Studio för att bygga direkt i verktyget. 
I praktisk pipelineform är den bäst dokumenterade representanten Google codelabben där man: genererar en webapp i AI Studios Build mode från en prompt, förbättrar med System Instructions (“Vibe Check” som långlivad persona), sparar till GitHub och deployar till Cloud Run via GUI. Det är en explicit “prompt → kod → repo → deploy”‑kedja. 
Underliggande LLM‑byggblock i Gemini‑stacken är väldokumenterade och direkt relevanta för hur en builder implementerar parsing och tool‑use:
Gemini API function calling låter modellen välja när den ska kalla funktioner och med vilka parametrar (dvs. tool calls som sedan exekveras av din app).  “Structured outputs” låter dig kräva JSON Schema‑kompatibla svar för mer robust parsing och agentiska workflows.  Kontext‑caching (explicit caching) gör det möjligt att cachea input tokens och referera dem i efterföljande anrop; detta är en viktig kostnads‑/latens‑optimering när buildern skickar samma kodbas/standardkontext om och om igen. 
Gemini‑plattformen har också publika kontroller för säkerhet och throttling: safety settings per kategori, samt “rate limits” som appliceras per projekt och varierar per modell (RPM/TPM/RPD‑liknande dimensioner).  För kontextfönster och tokenstyrning finns officiella token‑räknarresurser (cookbook/colab), vilket är centralt för context/window‑management i en builder. 
Emergent
Emergents publika tutorials ger relativt konkreta datapunkter om runtime, deployment och multi‑LLM‑routing. En deploy‑guide beskriver att Emergent deployar fullstack FastAPI + React + MongoDB “utan att konfigurera servrar” och listar funktioner som automatic scaling, managed MongoDB, secure environment variables, Preview & Production environments, custom domains och one‑click deployments; deployment sägs typiskt ta ~15 minuter och UI nämner en pre‑deployment “health check”. 
På LLM‑integrationssidan beskriver Emergent “Universal Key” som en förenkling: ett enda nyckel‑/billing‑lager som kan routa prompts till rätt LLM och konsolidera usage tracking. I tutorialn för multi‑LLM beskriver Emergent ett konkret bakom‑kulisserna‑flöde: bild laddas upp → skickas säkert till backend → routas till GPT‑visionmodell → modellen producerar strukturerad JSON → JSON skickas vidare till Claude för att generera recept‑JSON. Detta är ett uttalat “structured intermediate representation”‑mönster (IR) för robust pipeline‑parsing. 
För agentiska “chips” (MoltBot/OpenClaw) beskriver Emergent att en enda åtgärd provisionerar agent runtime på en cloud VM, dependencies/tools, default LLM‑konfiguration och en “secure, isolated execution environment”; de säger också att Emergent tillhandahåller rekommenderade LLM‑keys by default och att användaren kan lägga in egna senare. 
Ett intressant integrationsspår är MCP‑baserad koppling till ChatGPT: Emergent beskriver en “Bridge (MCP)” som översätter naturligt språk till funktionsanrop i användarens app (t.ex. create_note(...)). Det är i praktiken samma design som Gemini function calling – men där MCP är standardiseringslagret för verktyg. 
En kompletterande (men mer marknadsföringsnära) primärkälla är Android‑appens beskrivning, där Emergent explicit kallar plattformen “a coordinated system of AI agents” med separata roller (Planning, Frontend, Backend, Testing, Deployment). Denna uppdelning matchar många moderna agent‑arkitekturer och är en rimlig modell för hur Emergent segmenterar pipeline‑stegen, även om exakta implementeringsdetaljer inte är publicerade. 
På privacy/data retention‑sidan går det att hitta uppgifter om att “usage data” sparas upp till 24 månader i Emergent Labs privacy policy‑texten (åtminstone i det indexerade utdraget). Exakt policytext kunde inte analyseras fullt utan JS i detta körläge, varför detta bör behandlas som en “indikator” snarare än en fullständig juridisk tolkning.

## Architecture Overview


### Technology Stack


**Frontend:**
- React 18+ with Vite (JavaScript, no TypeScript initially)
- React Router v6 for navigation
- Zustand for state management
- Framer Motion for animations
- React Three Fiber + Drei for 3D visualization
- i18next for internationalization
- CSS Modules + PostCSS for styling


**Backend:**
- Supabase (PostgreSQL, Auth, Storage, Edge Functions)
- Stripe for payments (via Edge Functions only)
- Supabase Realtime for live updates


**Infrastructure:**
- Supabase Storage CDN for assets
- Vercel/Netlify for frontend hosting
- GitHub Actions for CI/CD
- Sentry for error monitoring


### Architecture Principles


1. **Feature-Sliced Design:** Each feature is self-contained with its own components, API, store, and styles
2. **Dual Visualization Engine:** 2D layered images (primary) + optional 3D (R3F) for immersion
3. **Data-Driven Configuration:** Manifests, SQL rules, i18n JSON - minimal hardcoded logic
4. **Performance First:** Code splitting, lazy loading, optimistic UI, prefetching
5. **Security by Default:** RLS on all tables, service keys never exposed, input validation
6. **Offline Support:** localStorage caching, service worker (future), graceful degradation


### Key Architectural Decisions


**Why Zustand over Redux?**
- Minimal boilerplate, fine-grained subscriptions
- Better TypeScript inference (when we add TS)
- Smaller bundle size
- Simpler mental model for team


**Why Supabase over custom backend?**
- Rapid development, built-in auth/RLS
- Real-time subscriptions out of the box
- Edge Functions for serverless logic
- PostgreSQL for complex queries
- Storage CDN included


**Why 2D + 3D dual engine?**
- 2D: Universal device support, photorealism, instant swaps
- 3D: Immersive experiences, AR/VR readiness, cinematic moments
- Users can choose based on device capability and preference


**Why CSS Modules over Tailwind?**
- Better component isolation
- No build-time class generation overhead
- Easier to maintain design tokens
- Better for theme switching (base/sport/luxury)

### 1.2 Row-Level Security (RLS) Policies
**Priority:** Critical  
**Estimated Time:** 3 days  
**Dependencies:** 1.1


**Detailed Steps:**


**Step 1.2.1: User-Owned Tables RLS**
- `user_configurations`: Users can only read/write their own configs
  ```sql
  CREATE POLICY "users_own_configurations" ON user_configurations
    USING (owner_id = auth.uid())
    WITH CHECK (owner_id = auth.uid());
  ```


- `orders`: Users can only read their own orders
  ```sql
  CREATE POLICY "users_own_orders" ON orders
    USING (user_id = auth.uid())
    WITH CHECK (user_id = auth.uid());
  ```


**Step 1.2.2: Public Read Tables**
- `vehicles`: Public read, admin write
- `options`, `option_values`: Public read, admin write
- `option_groups`: Public read, admin write
- `materials`: Public read, admin write
- `compatibility_rules`: Public read, admin write


**Step 1.2.3: Admin Bypass**
- Create service role policies for admin operations
- Use JWT claims: `request.jwt().claims.role = 'service_role'`
- Document admin API usage

- Security testing checklist
