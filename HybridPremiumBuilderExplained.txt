3. MODE MATRIX
================================================================================

  premiumMode (string; default often 'hybrid' from query/state/profile):
  • off     — V1 planning path only (see section 8). select-components returns
              empty selections. Fairness rule forbids premium in SYSTEM_PROMPT.
  • hybrid  — V2 pipeline: selectComponentsV2 + optional generated components for
              missing roles / customComponentsNeeded from V1 selection.
  • strict  — V2 pipeline + strict fairness: must use premium when catalog match
              exists; strictMode + manualSelectionIds can force manual-only list.

  strictMode (boolean; Generation.jsx / plan body):
  • When true AND manualSelectionIds.length > 0, V2 **mandatory** list is only
    manualSelectionIds (plan-website-components.js).

  isEdit (apply-ai-code-stream body):
  • false — initial generation apply.
  • true  — chat-driven apply after streamed edit.

  skipPolish (apply-ai-code-stream body):
  • When true, entire final polish block is skipped (e.g. raw file injects).

  Final polish gate (apply-ai-code-stream.js):
    shouldRunAsyncPolish =
      !skipPolish && (!isEdit || premiumMode === 'hybrid' || premiumMode === 'strict')
  So: initial builds polish unless skipPolish; **chat edits** skip polish when
  premiumMode === 'off'.

  isMultiPage — from plan JSON; drives render-app-template (HashRouter) and MPA
  prompts in generate-single-component (MPA awareness fragments).

  Planning branch (plan-website-components.js) — which code path runs:
  • If premiumMode === 'hybrid' OR premiumMode === 'strict'
      → V2 ULTRA pipeline: selectComponentsV2 (Supabase + multi-step LLM P04–P08),
        then hybrid may append generated components for missing roles /
        customComponentsNeeded, then copywriter pass P10, deterministic MPA fallback.
  • If premiumMode === 'off'
      → V1 legacy: single generateObject with SYSTEM_PROMPT P09 (full JSON plan
        in one shot), optional cross-provider retry with resolveCrossProviderFallback.

4. MODEL ROUTING
================================================================================

  User-selected **heavy** model (e.g. google/gemini-3.1-pro-preview) is passed as
  `model` on: plan-website-components, select-components, generate-single-component,
  generate-ai-code-stream, derive-design-system (optional model in body), parts of
  apply-ai-code-stream (buildModelId / model for polish).

  web/server/lib/provider-helpers.js — getModel(model):
  • Prefix anthropic/ → @ai-sdk/anthropic
  • Prefix openai/    → @ai-sdk/openai (or Groq for gpt-oss)
  • Prefix google/    → @ai-sdk/google
  • AI_GATEWAY_API_KEY → Vercel AI Gateway base URL for all providers

  generateWithQuality / generateFast (same file):
  • OpenAI **Responses** API: gpt-5.4 (quality) vs gpt-5.4-mini (fast).
  • Default system strings: "You are a senior architect." / "You are a fast
    precision assistant." when system prompt empty.

  web/server/lib/llm-lightweight.js — resolveLightweightModel(heavyModel):
  • openai/    → openai/gpt-5.4-mini, useFast: true (uses generateFast where wired)
  • anthropic/ → anthropic/claude-haiku-4-5-20251001
  • google/    → google/gemini-2.5-flash
  resolveCrossProviderFallback — used when primary model fails (plan V1 retry,
  auto-repair fallback).

  enhance-prompt.js — ENHANCE_MODEL (NOT user main model):
  • Default google/gemini-2.5-flash
  • If user model contains openai/ → openai/gpt-5.4-mini
  • If anthropic/ → anthropic/claude-haiku-4-5-20251001

  Polish parallel path (polish-refinement.js):
  • Design spec: resolveDesignSpecModelId(model) → same lightweight mapping.
  • Per-file polish uses **heavy** model except OpenAI native path uses
    generateWithQuality.

  Auto-repair (auto-repair.js):
  • Primary: resolveLightweightModel(buildModel).id
  • Fallback: resolveCrossProviderFallback(buildModel)

9. DETERMINISTIC / NON-LLM INFRASTRUCTURE
================================================================================

  These steps do **not** call an LLM; they enforce safety and reproducibility.

  • web/server/routes/component-bundle.js — loads premium bundle content from
    registry/DB; no generateText/Object.

  • web/server/lib/render-app-template.js — renderAppTemplate builds App.jsx from
    plan components, isMultiPage, pages, sharedComponents; role sort, SPA vs MPA.

  • web/server/routes/render-app.js — HTTP wrapper calling render-app-template.

  • web/server/lib/verify-sandbox-build.js — runs npx vite build --base=./ in
    sandbox via provider.

  • web/server/routes/validate-imports.js — delegates to lib/import-graph.js
    validateImports(files, premiumComponents).

  • apply-ai-code-stream.js — sanitizeImports (strips non-whitelisted packages /
    bad lucide icon names), PROTECTED_FILES filter (blocks overwriting vite.config,
    package.json, etc.), extractPackages + isAllowedPackage whitelist, file write
    ordering (CSS first, App.jsx ordering in sort).

  • plan-website-components.js — enforcePlanStructure, flatten paths, inject
    header/hero/footer fallbacks if missing, buildDeterministicMultiPagePlan when
    copywriter pages empty.

  • select-components-v2.js — pickStructuredFallback, cached Supabase queries,
    structural heuristics when LLM times out.

  • enhance-prompt.js — extractExplicitComponentNames regex (no LLM).

10. APPLY PIPELINE (SERVER DETAIL)
================================================================================

  File: web/server/routes/apply-ai-code-stream.js

  Stages:
  1. Parse files from generatedCode or explicit files[]; strip protected files;
     sanitizeImports on every file.
  2. Install whitelisted npm packages (union of requested + detected imports).
  3. Write files (CSS first, App.jsx ordering logic in sortedFiles).
  4. verifySandboxBuild → vite build.
  5. On failure (non-permission): attemptRepair up to 5 times; merge all src
     files from sandbox into repair context.
  6. shouldRunAsyncPolish: runPolishStep (P14/P15), parallel fillers (P17),
     verify; on polish break, one repair attempt or rollback prePolishSnapshot.
  7. runMiniPolishStep (P16) if build still green.
  8. restartViteServer; SSE COMPLETE; optional credits; AIBuildNarrator complete.

16.1 QUESTION 1
What is the difference between startGeneration and sendChatMessage, and when does
the UI call each?
--------------------------------------------------------------------------------

  Short answer:
  • startGeneration is the big "initial website build" orchestrator.
  • sendChatMessage is the chat entrypoint that decides whether the user is
    creating the first build or editing an existing build.

  The clean mental model:
  • startGeneration = "do the full builder pipeline"
  • sendChatMessage = "handle what the user just submitted in chat"

  What sendChatMessage does first:
  • Reads the current chat input.
  • Reads pending images.
  • Reads pending community/premium components attached in the composer.
  • Prevents empty submits.
  • Prevents submit while loading.
  • Fires the optimistic credit deduction animation event.
  • Clears the input and pending attachments from UI state.

  Then it asks one very important question:
  • Is this the first generation?
  • Or is this an edit to an already-built project?

  The code decides that with:
  • isEdit = conversationContext.appliedCode.length > 0

  Meaning:
  • If nothing has ever been applied yet, then the user is still on the initial
    creation path.
  • If at least one previous apply happened, the user is now in edit mode.

  If isEdit is false:
  • sendChatMessage does not do edit orchestration itself.
  • It simply delegates to startGeneration.
  • It passes the typed message as the build prompt.
  • It also passes pending images and selected component ids.
  • So on first use, chat submission is basically a front door into the full
    builder pipeline.

  If isEdit is true:
  • sendChatMessage does not call startGeneration.
  • It runs the edit path.
  • It records the user's message in chat.
  • It ensures a sandbox exists.
  • It may inject newly attached component bundles first.
  • It then calls handleAIGeneratedEdit for a streamed AI edit.

  So the UI call relationship is:
  • User presses send in chat
      -> sendChatMessage runs
      -> sendChatMessage decides initial build vs edit
      -> initial build delegates to startGeneration
      -> edit delegates to handleAIGeneratedEdit

  startGeneration is therefore not the universal submit handler.
  It is the specialized orchestration engine used when the user is starting a
  new build, using a template, or triggering other first-build style flows.

  startGeneration also gets called from places other than sendChatMessage:
  • Build from selected community components
  • Template mode
  • URL / location state driven builder entry
  • Possibly other onboarding / import flows

  What startGeneration owns that sendChatMessage does not:
  • Project init
  • Prompt enhancement
  • Design system derivation
  • Premium component selection
  • Planning
  • Dependency install
  • Bundle fetch
  • Single component generation loop
  • Deterministic App.jsx rendering
  • Import validation
  • Final apply

  What sendChatMessage owns that startGeneration does not:
  • Composer clearing
  • Deciding create vs edit
  • Edit-mode chat message creation
  • Injecting attached chat components before integration
  • Building the final edit instruction for handleAIGeneratedEdit

  Why this split matters architecturally:
  • startGeneration is a workflow engine.
  • sendChatMessage is a UI dispatcher.

  If you are debugging:
  • "Why did the app build from scratch?" -> inspect sendChatMessage's isEdit
    decision and whether it called startGeneration.
  • "Why did it try to edit instead of build?" -> inspect
    conversationContext.appliedCode.

  One-sentence rule:
  • The UI always starts at sendChatMessage, and only uses startGeneration if

16.2 QUESTION 2
What does applyGeneratedCode send to /api/apply-ai-code-stream, and why are both
generatedCode and explicitFiles sometimes used?
--------------------------------------------------------------------------------

  Short answer:
  applyGeneratedCode sends one apply request that can carry either:
  • raw AI output as a string of <file path="..."> blocks
  • an explicit normalized files array
  • or both

  Request body fields sent by applyGeneratedCode:
  • response: generatedCode || ''
  • files: filesPayload || []
  • isEdit
  • packages: []
  • sandboxId: activeSandboxId
  • model: aiModel
  • premiumMode
  • buildId
  • prompt: lastPromptRef.current || lastPrompt || ''
  • skipPolish
  • isResume

  generatedCode means:
  • The original streamed or assembled string output.
  • Usually contains <file path="...">...</file> blocks.
  • It is called `response` in the server payload for legacy compatibility.

  explicitFiles means:
  • Already-parsed file objects like:
    { path: 'src/App.jsx', content: '...' }
  • This is the preferred precise payload when the client already has a clean
    file list.

  Why both exist:
  • The system evolved from a pure string-based pipeline.
  • Older server behavior parsed files out of one big AI text blob.
  • Newer behavior prefers structured file arrays because they are safer and
    avoid reparsing.

  The client-side logic is:
  • let filesPayload = explicitFiles
  • if no filesPayload and generatedCode exists
      -> parseFilesFromCode(generatedCode)
      -> convert to { path, content } array

  So explicitFiles has priority.

  Why explicitFiles is important:
  • It avoids depending on regex parsing when the client already knows the exact
    file set.
  • It supports deterministic assembly, like:
    premium bundle files
    generated component files
    deterministic App.jsx
  • It lets apply run even when generatedCode is null.

  Why generatedCode is still useful:
  • Legacy compatibility with server parsing.
  • Logging / history continuity.
  • Some downstream logic still reconstructs or references generatedCode.
  • It preserves the exact raw LLM artifact for debugging.

  Common scenarios:
  • Full initial build after plan/generation:
      generatedCode = combined legacy string
      explicitFiles = allFiles array
      Why both? Safety plus compatibility.

  • Streaming edit from handleAIGeneratedEdit:
      generatedCode = streamed result from /generate-ai-code-stream
      explicitFiles = null
      Why? The edit flow receives one AI code string and lets apply parse it.

  • Injecting fetched premium/community bundles:
      generatedCode = null
      explicitFiles = newFiles
      Why? The files already exist as parsed bundle outputs; no need for the
      AI stream format.

  • Snapshot restore:
      generatedCode = null
      explicitFiles = files restored from saved snapshot map
      Why? This is not AI generation at all; it is replaying known file content.

  Server-side meaning in apply-ai-code-stream:
  • If req.body.files exists and is an array, server uses that.
  • Else it falls back to parseFileBlocks(generatedCode).

  Why this dual transport is a good design:
  • String transport is convenient for streamed AI output.
  • Structured transport is safer for deterministic or recovered files.
  • Supporting both makes the client resilient across multiple workflows.

  Debugging clue:
  • If apply seems to miss files from a known bundle, inspect explicitFiles.
  • If apply seems to fail parsing AI output, inspect generatedCode formatting.

16.3 QUESTION 3
How does premiumMode get into API requests, and where does its default value
come from (URL, state, etc.)?
--------------------------------------------------------------------------------

  Source of premiumMode in Generation.jsx:
  • const [premiumMode, setPremiumMode] =
      useState(queryParams.get('premiumMode') || location.state?.premiumMode || 'hybrid')

  That means the priority order is:
  1. URL query parameter `premiumMode`
  2. React Router `location.state?.premiumMode`
  3. hard fallback string 'hybrid'

  So the effective default at the page level is:
  • hybrid

  This matches the broader product direction:
  • hybrid is also the common default mode documented elsewhere.

  How premiumMode then reaches the server:

  In startGeneration:
  • POST /api/select-components body includes premiumMode
  • POST /api/plan-website-components body includes premiumMode

  In applyGeneratedCode:
  • POST /api/apply-ai-code-stream body includes premiumMode

  That means premiumMode influences at least:
  • selection behavior
  • planning branch choice
  • polish gating during apply

  What it does not directly do in this file:
  • It does not itself generate code.
  • It selects which backend logic branches are used.

  Practical effect by request:
  • select-components:
      if premiumMode === 'off', server returns empty premium selection and does
      not go through the catalog selection path.

  • plan-website-components:
      if premiumMode is 'hybrid' or 'strict', server uses the V2 pipeline.
      if premiumMode is 'off', server uses the V1 legacy full-generateObject plan.

  • apply-ai-code-stream:
      premiumMode affects shouldRunAsyncPolish when isEdit is true.

  How the UI can change premiumMode:
  • The Generation view has a mode toggle in the UI.
  • Cycling it updates local React state.
  • Future requests then carry the new state value.

  Why query param support matters:
  • Deep-linking into the builder can preconfigure mode.
  • External entry points or dashboards can open the builder with a known mode.
  • Refresh-safe state can be encoded in the URL.

  Why location.state support matters:
  • Internal navigation can pass mode without polluting the URL.
  • Example: coming from another page with a preset build intent.

  Why the 'hybrid' fallback matters:
  • The builder still has a sensible behavior even if neither query nor location
    state provides a mode.
  • It keeps premium-assisted building enabled by default.

  Important subtlety:
  • premiumMode is not recomputed on every request from the server.
  • It is a client state value captured and sent explicitly in request bodies.
  • So if the UI state changes, subsequent requests use the new value.

  Failure mode to remember:
  • If someone expects server-side user profile defaulting but the client sends a
    concrete value, the client wins for that request.

  Developer summary:
  • premiumMode enters Generation.jsx from URL or navigation state, falls back to
    hybrid, lives in React state, and is then forwarded into selection, planning,
    and apply requests.

16.4 QUESTION 4
What is skipPolish used for, and when would you pass true instead of false?
--------------------------------------------------------------------------------

  Short answer:
  • skipPolish tells the apply route to skip the expensive final polish block.
  • You pass true when you want to write files quickly without triggering another
    full polish pass.

  Where skipPolish is sent:
  • applyGeneratedCode -> POST /api/apply-ai-code-stream -> body.skipPolish

  Server meaning:
  • apply-ai-code-stream computes shouldRunAsyncPolish
  • If skipPolish is true, heavy polish is skipped no matter what.

  Why the feature exists:
  • Some flows are mechanical file injections, not new creative generations.
  • Running polish every time would be slower, costlier, and may unexpectedly
    restyle content that should remain stable.

  Good times to use skipPolish = true:

  1. Template apply
  • In template mode, startGeneration builds template code and calls:
    applyGeneratedCode(templateData.code, false, buildId, null, true, ...)
  • Reason:
    the template payload is already a resolved package of files.
    immediate application is more important than repolishing.

  2. Direct build from manual selection
  • In manual build mode, after /api/build-from-selection:
    applyGeneratedCode(selectionData.code, false, buildId, null, true, ...)
  • Reason:
    the selected components are already curated bundles.

  3. Appending / injecting community components
  • When the user adds components to an existing project:
    applyGeneratedCode(null, false, buildId, newFiles, true, ...)
  • Reason:
    the first job is to silently write the files into the sandbox.
    integration into App.jsx happens as a second step via AI edit.

  4. Snapshot restore
  • Restoring older checkpoint files uses skipPolish = true.
  • Reason:
    snapshot restore should recreate the exact previous known state, not ask an
    LLM to reinterpret or improve it.

  Why skipPolish is often false on real AI edits:
  • After handleAIGeneratedEdit receives fresh AI code, applyGeneratedCode is
    called with skipPolish = false.
  • Reason:
    user-requested edits often benefit from final consistency cleanup.

  Why skipPolish is false on the main generated build:
  • The initial full website build is the main premium experience.
  • The heavy polish step is one of the major quality layers.

  Things skipPolish does NOT skip:
  • file parsing
  • import sanitization
  • package install
  • file writes
  • verify build
  • auto-repair if verify fails
  • Vite restart
  • completion bookkeeping

  It specifically skips:
  • heavy runPolishStep
  • polish filler narration loop
  • mini polish (because that only runs after heavy polish branch succeeds)

  Tradeoff:
  • skipPolish = true
      faster
      safer for deterministic restores/injections
      less expensive
      less likely to cause style drift
  • skipPolish = false
      slower
      more expensive
      but higher chance of refined copy and visual consistency

  Mental rule:
  • If files are already known-good and you are just injecting or restoring them,
    use true.
  • If fresh AI output needs refinement, use false.

16.5 QUESTION 5
How does handleAIGeneratedEdit relate to /api/generate-ai-code-stream, and what
happens to the streamed result afterward?
--------------------------------------------------------------------------------

  Short answer:
  • handleAIGeneratedEdit is the edit-specific streaming client for
    /api/generate-ai-code-stream.
  • It does not apply code itself directly during streaming.
  • It waits for the complete event with generatedCode, then hands that code to
    applyGeneratedCode.

  Request body sent by handleAIGeneratedEdit:
  • prompt: promptText
  • model: aiModel
  • isMultiPage: isMultiPageProject
  • currentPages: projectPages
  • siteMap: content of src/app/siteMap.js if present
  • context:
      sandboxId
      conversationContext
      recentMessages (last 10 chat messages)
      sandboxUrl
      premiumComponents (derived from generationProgress.files)
  • isEdit: true
  • buildId

  Why this route is separate from startGeneration:
  • The edit path already has a built codebase.
  • It wants surgical changes, not full planning/generation pipeline every time.
  • The server prompt for generate-ai-code-stream has a huge edit-mode appendix
    specifically for this scenario.

  What the server does with this:
  • Builds a large system prompt.
  • Injects catalog context.
  • Adds edit-mode rules.
  • Pulls sandbox file tree and file contents.
  • Optionally injects exact golden App.jsx if plan is present.
  • Streams file-tagged code back.

  What handleAIGeneratedEdit listens for in the stream:
  • status
  • component
  • complete
  • error

  UI effects:
  • status -> generationProgress.status = data.message
  • component -> generationProgress.currentFile = data.path
  • error -> throws

  The critical moment:
  • When data.type === 'complete' and data.generatedCode exists
  • handleAIGeneratedEdit calls:
      applyGeneratedCode(data.generatedCode, true, buildId, null, false, sandbox.sandboxId, false, sandbox.url)

  So the streamed result does not become live automatically.
  It becomes live only after applyGeneratedCode sends it through the apply route.

  Why this second step exists:
  • generate-ai-code-stream only generates text/code.
  • apply-ai-code-stream is the route that:
      parses files
      sanitizes imports
      installs deps
      writes files
      verifies build
      repairs errors
      polishes output
      saves project state

  In other words:
  • handleAIGeneratedEdit = get candidate code
  • applyGeneratedCode = operationalize candidate code into the sandbox

  That separation is very important.

  The edit path therefore is:
  1. collect rich context from current project
  2. stream AI edit proposal
  3. on completion, apply proposal through verified apply pipeline

  Why the context is rich:
  • recentMessages helps preserve conversational continuity
  • premiumComponents tells the LLM what premium files already exist
  • siteMap and currentPages help preserve multi-page routing integrity
  • sandboxId lets the server inspect real files

  If the stream never emits complete:
  • No apply happens.
  • The sandbox remains unchanged.

  If the stream emits complete but generatedCode is malformed:
  • applyGeneratedCode / apply route may fail later.
  • Then the error is surfaced through apply error handling.

  • verify_passed updates the app from "checking" to "build is green".

16.7 QUESTION 7
Why does the code call /api/get-sandbox-files after a successful apply, and what
gets saved to Supabase?
--------------------------------------------------------------------------------

  Short answer:
  • Because the final sandbox state after apply may differ from the original
    client-side generated files.
  • The system wants the exact live files after polish, repair, and any server-
    side modifications.

  This happens inside the complete event handling path in applyGeneratedCode.

  Why client-side generatedCode is not enough:
  • The apply route may sanitize imports.
  • The server may install packages and rewrite things indirectly.
  • Auto-repair may modify files after verification failure.
  • Polish may rewrite many files.
  • Mini polish may also rewrite files.

  So the source of truth after completion is:
  • the sandbox filesystem
  • not the original generatedCode string

  The code therefore fetches:
  • GET /api/get-sandbox-files?sandboxId=${activeSandboxId}

  Expected response:
  • success
  • files = full map of path -> content

  Then it POSTs to /api/snapshots with:
  • projectId: buildId
  • chatIndex: chatMessages.length
  • text: lastPrompt || (generatedCode ? 'Code generated' : 'Files generated')
  • files: fullFilesMap
  • packages: data.packages || []
  • designSystem: designSystemRef.current
  • componentPlan: componentPlanRef.current
  • sandboxUrl: activeSandboxUrl
  • sandboxId: activeSandboxId

  It also separately calls saveProjectUpdates with:
  • generated_files
  • total_files
  • build_status: 'preview'

  So there are two levels of persistence:

  1. Project row update
  • lightweight metadata
  • generated file count
  • build status

  2. Snapshot row save
  • full exact file contents
  • packages
  • design system
  • component plan
  • sandbox coordinates

  Why snapshots are valuable:
  • restore / time-travel
  • auditability
  • debugging build regressions
  • preserving post-polish state
  • associating exact files with a chat point in history

  Why chatIndex is included:
  • It anchors the snapshot to a point in the conversation timeline.
  • This supports revert UX and historical reconstruction.

  Why designSystemRef.current and componentPlanRef.current are included:
  • They preserve high-level semantics alongside raw files.
  • A later restore or analysis can know not just what code existed, but which
    design system and plan produced it.

  Why this is done only when !isResume:
  • Resume flow is about recovering and continuing, not duplicating a new
    snapshot/save event for the same completion.

  The exact problem this solves:
  • If you only stored pre-apply client code, you would miss server-side repair
    and polish results and snapshot restore would not match the live preview.

  Developer summary:
  • /api/get-sandbox-files is called after successful apply because the sandbox
    contains the final authoritative codebase, and that exact codebase is what
    gets snapshotted into Supabase.

16.8 QUESTION 8
What is lastPromptRef for, and why use a ref instead of only lastPrompt state
when calling apply?
--------------------------------------------------------------------------------

  The file defines both:
  • const [lastPrompt, setLastPrompt] = useState('')
  • const lastPromptRef = useRef('')

  The inline comment already tells the reason:
  • synchronous access in useCallback closures

  What problem this solves:
  • React state updates are asynchronous.
  • A callback can close over an older value of lastPrompt.
  • applyGeneratedCode is a useCallback and may run after several async stages.
  • The code wants the freshest prompt string when sending apply request data.

  When the prompt is set:
  • In startGeneration:
      setLastPrompt(prompt)
      lastPromptRef.current = prompt

  Why both are updated:
  • state is for rendering / UI / normal React data flow
  • ref is for immediate closure-safe reads in long async pipelines

  Where the ref is used:
  • prompt: lastPromptRef.current || lastPrompt || ''

  Why that fallback chain exists:
  • Prefer the freshest synchronous ref
  • Fall back to state if needed
  • Fall back to empty string if neither exists

  Why the prompt matters during apply:
  • The apply route passes prompt into polish/narration logic.
  • If the prompt is stale or empty, the polish step loses user-vision context.
  • That can produce generic or incorrect copy refinements.

  Concrete example:
  • User submits prompt
  • startGeneration begins many async network steps
  • React state update for lastPrompt may not be the value captured inside a
    previously memoized callback at the moment apply runs
  • lastPromptRef.current still points to the latest prompt synchronously

  This is especially important in:
  • startGeneration initial build flow
  • rapid chat edit flow
  • cases where applyGeneratedCode is called by another helper after async
    stream completion

  Why state alone could be risky:
  • stale closure
  • timing mismatch during rapid edits
  • useCallback dependency churn
  • polish receiving blank / old prompt

  Why the ref is not enough on its own:
  • refs do not trigger UI rerenders
  • the visible UI still benefits from state

  So the dual structure is intentional:
  • state for React rendering semantics
  • ref for orchestration correctness

  The same design pattern appears elsewhere in complex React async code:
  • current auth token refs
  • latest settings refs
  • current websocket handler refs

  Here its functional purpose is very specific:
  • preserving the exact user vision text all the way into apply/polish even if
    the callback graph is closure-heavy and asynchronous.

16.9 QUESTION 9
When the user attaches community components in chat, what sequence runs: apply
only, generate only, or both?
--------------------------------------------------------------------------------

  Short answer:
  • Usually both.
  • First the files are physically injected into the sandbox.
  • Then an AI edit integrates them into App.jsx and possibly routes/siteMap.

  There are two related attachment scenarios in Generation.jsx:

  Scenario A: initial build with selected components and little/no prompt
  • sendChatMessage sees no previous applied code
  • it calls startGeneration(...)
  • startGeneration may take a direct build path or a normal planned path

  Scenario B: editing an existing build with attached components
  • sendChatMessage sees conversationContext.appliedCode.length > 0
  • it goes down the edit path
  • this is the main scenario the question is asking about

  Edit path detailed sequence:

  1. sendChatMessage collects currentComponents from pendingComponents
  • these are the components staged in the chat composer

  2. It ensures a sandbox exists
  • if not, createSandbox() is called

  3. It fetches bundles for each attached component
  • POST /api/component-bundle for each id

  4. It parses each returned file block bundle
  • parseFilesFromCode(data.fileBlocks)

  5. It determines whether each component is a page or a normal section
  • page -> put under src/pages
  • normal component -> put under src/components/premium

  6. It builds newFiles array
  • concrete file objects ready to write

  7. It calls applyGeneratedCode(null, false, buildId, newFiles, true, ...)
  • this silently injects the files into the sandbox
  • skipPolish = true because this is a mechanical file write stage

  8. It builds an integration hint
  • names the added components
  • tells the AI to integrate them into App.jsx
  • if any is a page component, tells AI to add Route and update siteMap
  • tells AI to keep existing components

  9. It calls handleAIGeneratedEdit(finalInstruction, buildId, sandbox)
  • this requests an AI-generated edit against the now-updated sandbox

  10. That streamed edit eventually calls applyGeneratedCode again
  • this time with generatedCode from /generate-ai-code-stream
  • and skipPolish = false

  So the real answer is:
  • attach components in chat = apply, then generate, then apply again

  More precisely:
  • Step 1 apply raw injected files
  • Step 2 generate integration changes
  • Step 3 apply integration changes

  Why not generate only:
  • The AI needs the actual component files present in the sandbox so imports and
    file tree are real.

  Why not apply only:
  • Physically writing files does not put them into App.jsx.
  • The layout/router still has to be updated.

  Why this two-phase strategy is smart:
  • deterministic component asset injection first
  • semantic integration second
  • avoids asking the LLM to invent the whole bundle contents

  This same pattern also appears in the append/integrate branch inside
  startGeneration when adding manualSelectionIds to an existing project:
  • fetch bundles
  • applyGeneratedCode with explicit files and skipPolish=true
  • build integrationPrompt
  • handleAIGeneratedEdit

  Final conclusion:
  • It is not apply only.
  • It is not generate only.
  • It is a two-stage hybrid flow using both.

16.10 QUESTION 10
What happens if there is no sandboxId when applyGeneratedCode runs - how is a
sandbox created or recovered?
--------------------------------------------------------------------------------

  Short answer:
  • applyGeneratedCode tries to recover or create a sandbox before applying.
  • If no sandboxId is available, it calls createSandbox().
  • If createSandbox fails, apply stops and an error chat message is shown.

  The first lines of applyGeneratedCode do:
  • let activeSandboxId = passedSandboxId || sandboxData?.sandboxId
  • let activeSandboxUrl = passedSandboxUrl || sandboxData?.url

  That means sandbox resolution priority is:
  1. explicit function arguments passed in by caller
  2. current component state sandboxData

  If neither exists:
  • applyGeneratedCode enters booting mode
  • setCodeApplicationState({ stage: 'booting', ... })
  • then calls createSandbox()

  If createSandbox succeeds:
  • activeSandboxId = sb.sandboxId
  • activeSandboxUrl = sb.url
  • apply continues normally

  If createSandbox fails:
  • console.error('[applyGeneratedCode] Sandbox boot failed:', sbErr)
  • addChatMessage('Failed to start preview environment: ...', 'error')
  • return

  So no sandbox means:
  • no silent failure
  • explicit boot attempt
  • explicit user-facing error if boot fails

  Where createSandbox is used elsewhere:
  • startGeneration before the main pipeline if sandboxData absent
  • sendChatMessage edit path if sandboxData absent
  • applyGeneratedCode as the final safety net

  Why applyGeneratedCode still has its own fallback:
  • Callers may forget to create sandbox first
  • The sandbox may have been cleared from local state
  • Resume / restore / delayed callbacks may execute after state loss
  • The apply layer must be robust on its own

  Why passedSandboxId exists:
  • Prevents closure / timing problems
  • Lets callers pass the exact sandbox resolved earlier in the same async flow
  • Useful when sandboxData state might not yet reflect the freshest sandbox

  Common caller patterns:
  • startGeneration often passes sandbox.sandboxId and sandbox.url
  • handleAIGeneratedEdit completion path passes sandbox.sandboxId and sandbox.url
  • restoreSnapshot uses sandboxData if available

  What recovered means here:
  • On the client side in this function, recovery means "obtain a usable sandbox
    reference now", not necessarily "reuse the exact old instance by id" unless
    the caller already passed a known sandboxId.

  The deeper server-side recovery story lives elsewhere:
  • sandbox-manager can reconnect by sandboxId
  • getSandboxFiles / apply route can target known sandbox ids
  • but Generation.jsx's immediate responsibility is simply to ensure there is a
    valid sandbox target before sending the apply request

  UI side effects of booting:
  • codeApplicationState.stage = 'booting'

17.1 QUESTION 1
What is the difference between the V2 path (hybrid / strict) and the V1 path
(off), in terms of which functions run?
--------------------------------------------------------------------------------

  Short answer:
  • V2 path runs when premiumMode is `hybrid` or `strict`.
  • V1 path runs when premiumMode is `off`.

  This is the major branch in the file:
  • if (premiumMode === 'strict' || premiumMode === 'hybrid') -> V2
  • else -> V1 legacy

  V2 path high-level behavior:
  • Builds a compact context object from the design system
  • Extracts explicit component names from prompt text
  • Builds a mandatory selection list from explicit names and manual selections
  • Calls selectComponentsV2(...)
  • Maps database rows from V2 into the planner's expected component shape
  • In hybrid mode only, may add generated placeholders for uncovered roles and
    custom component needs
  • Runs a second generateObject call called the Master Copywriter / MPA
    Architect pass
  • Merges copywriter output back into components
  • Builds a deterministic multi-page fallback
  • Creates planData manually from those merged components
  • Optionally generates aiNarration
  • Records component selections for retention tracking
  • Tracks template usage / reputation if a template was used

  V1 path high-level behavior:
  • Builds one huge SYSTEM_PROMPT string
  • Calls one big generateObject using planSchema
  • If that fails, uses resolveCrossProviderFallback(model) and retries
  • Takes returned object directly as planData
  • Optionally generates aiNarration
  • Records premium selections if any exist in the V1 result

  So the architectural difference is:
  • V2 = multi-step orchestrated planning with DB-backed premium component
    intelligence plus a second copy/architecture pass
  • V1 = one-shot full-plan generation using a single giant prompt

  What V2 adds compared to V1:
  • selectComponentsV2 from web/server/lib/select-components-v2.js
  • premium DB rows mapped into normalized plan components
  • hybrid generated-additions logic
  • copywriter/architect pass for keyContent/props/pages/shared refs
  • template usage tracking
  • stronger separation of "selection" from "copywriting"

  What V1 keeps simpler:
  • no V2 selection pipeline
  • no mapping from DB rows into fake premium paths
  • no custom hybrid merge layer
  • no dedicated second copywriter pass
  • one prompt tries to do all planning at once

  Why the branch matters to the rest of the system:
  • Downstream code expects a consistent component plan shape no matter which path
    produced it.
  • This file is responsible for making V2 results look like V1-shaped plan data
    so the frontend and generation stages do not need to care which planner path
    ran.

  Important nuance:
  • Even when V2 runs, the route still uses some V1-era concepts:
      componentSchema shape
      legacy fields like components/globalStyle/appComposition
      flattened paths and final hardening
  • So V2 is not a separate output format. It is a different internal planning
    engine that still normalizes into the same response shape.

  Developer mental model:
  • V1 answers: "generate me a whole plan from scratch."
  • V2 answers: "select the right premium building blocks first, then assemble a
    coherent plan around them."

17.2 QUESTION 2
What does fairnessRule change across premiumMode values, and why does that
matter for the JSON plan?
--------------------------------------------------------------------------------

  fairnessRule is a dynamic chunk injected into the big SYSTEM_PROMPT.
  It changes based on premiumMode before the plan prompt is sent.

  There are three variants:

  1. strict mode fairnessRule
  • Forbids generating a custom component if a premium component exists in the
    selection context for that role.
  • Forces source: 'premium' and bundleId when a premium option exists.
  • Says violating that rule is a system failure.
  • Only allows source: 'generated' if explicitly no premium option exists.

  2. off mode fairnessRule
  • Forbids using premium components entirely.
  • Forces source: 'generated' and bundleId: null for all components.
  • Tells the model to ignore selectionContext.

  3. hybrid mode fairnessRule
  • Treats premium and generated choices as equal if fit warrants it.
  • Example in prompt: a generated footer can be as valid as a premium footer if
    it fits the request better.

  Why this matters:
  • The planning output is not just descriptive. It drives real downstream
    behavior.
  • The plan's `source` field determines whether the next stage will:
      fetch a premium bundle
      or call generate-single-component
  • The plan's `bundleId` determines which premium component bundle to fetch.

  So fairnessRule changes real execution, not just wording.

  Concrete downstream impact:
  • source: 'premium' + bundleId set
      -> frontend later calls /api/component-bundle for that component
  • source: 'generated' + bundleId null
      -> frontend later sends that component to /api/generate-single-component

  Why the rule is especially important in V1:
  • In V1, one LLM call has to decide everything.
  • fairnessRule is the main mechanism forcing mode-specific behavior inside that
    one JSON-generation call.

  Why it still matters conceptually even when V2 exists:
  • It documents product intent for mode behavior.
  • It explains what strict / off / hybrid are supposed to mean at the planning
    level.
  • It preserves backward-compatible semantics if V1 is used.

  Mode-by-mode planning philosophy:
  • strict:
      maximize premium usage when available
      avoid custom generation if a premium match exists
  • hybrid:
      mix premium and generated based on best fit
      do not force one source family over the other
  • off:
      pure custom generation
      premium catalog should not affect the plan

  Why the JSON plan would be wrong without this:
  • strict mode could return too many generated components
  • off mode could incorrectly return premium bundle ids
  • hybrid mode could be biased too far toward one source type

  In short:
  • fairnessRule is the policy layer that tells the planner how to populate
    source and bundleId, which then governs the real build pipeline.

17.3 QUESTION 3
How does selectComponentsV2 output get mapped into components with source:
'premium' and paths under src/components/premium/?
--------------------------------------------------------------------------------

  selectComponentsV2 returns database component rows, not frontend-ready plan
  objects.

  This route maps those DB rows into the exact planner shape the rest of the
  system expects.

  For each dbComp in v2Result.components:
  • name               <- dbComp.name
  • refId              <- dbComp.component_id
  • exportName         <- sanitized dbComp.name
  • path               <- `src/components/premium/${dbComp.component_id}.jsx`
  • description        <- dbComp.description || dbComp.visual_description || 'Premium component'
  • designFocus        <- dbComp.mood_tone || 'modern'
  • keyContent         <- ''
  • source             <- 'premium'
  • bundleId           <- dbComp.component_id
  • props              <- {}
  • role               <- inferRoleFromComponent(dbComp)

  The important thing to understand:
  • These are not yet real files.
  • They are plan objects that point to future premium bundle injection.

  Why the path is "fake but intentional":
  • The V2 component row comes from a database, not from a real file already in
    the local sandbox.
  • The route assigns a stable synthetic path under src/components/premium/ so
    the rest of the build system can treat the premium component like any other
    planned component.

  Why src/components/premium/ specifically:
  • It clearly separates premium-injected files from generated custom files
  • It matches how Generation.jsx later expects premium bundle files to live
  • It makes import generation and App.jsx rendering consistent

  How exportName is derived:
  • It strips non-alphanumeric characters from dbComp.name
  • If nothing survives, it falls back to Component${idx}

  Why this mapping is needed:
  • The frontend generation pipeline expects a V1-like component shape
  • V2 rows need to be adapted into that universal contract
  • Without this mapping, later stages would not know:
      what path to import
      what source family it belongs to
      which bundle id to fetch
      what role to assign in layout

  Why role inference matters:
  • inferRoleFromComponent uses category/name/description/visual_description
  • header/hero/footer are deduced from text patterns
  • everything else defaults to feature

  That role is later used for:
  • structural dedupe
  • ordering
  • fallback placeholder injection
  • deterministic page distribution

  Important nuance:
  • props starts as {}
  • It is later filled by the Master Copywriter pass if copy output exists
  • So the first mapping establishes shell structure, not final content payload

  Another subtle point:
  • refId and bundleId are both based on component_id, but they serve different
    purposes:
      refId is layout identity inside the plan
      bundleId is retrieval identity for premium bundle lookup

  Developer summary:
  • selectComponentsV2 gives raw premium catalog rows
  • this route wraps them into normalized plan components
  • `source: 'premium'` and `src/components/premium/...` are the key markers
    that tell the rest of the system how to build them later

In hybrid mode only, when are extra generated components added, and what triggers
customComponentsNeeded from V1?

  Hybrid mode has a special merge behavior after V2 selection.

  Why this exists:
  • V2 is strong at choosing premium components from the catalog

  The code enters this block only when:

  • V1 selectionContext customComponentsNeeded descriptions

  Case 1: missing standard roles

  • Because `feature` is included in standardRoles, hybrid mode ensures there is

  • It uses a generated path under src/components/

  • bundleId = null
  • role = 'feature'

  • This route is only planning
  • It is not generating the code yet
  • The generated placeholders tell later stages:

  • If hybrid mode is not active
  • If all standard roles are already covered
  • If customComponentsNeeded is empty
  • If the generated safeName would duplicate an existing mapped or added component

  Why duplicate checks matter:
  • It avoids planning the same component twice under different origins
  • It keeps downstream generate-single-component from producing redundant files

  Role of selectionContext in hybrid:
  • selectionContext is the bridge from the first premium selection pass
  • It lets hybrid mode combine:
      "best premium components we found"
      with
      "gaps that still require custom LLM generation"

  Why this is hybrid-specific:
  • strict mode prefers premium whenever possible, so custom additions are more
    constrained by design
  • off mode avoids premium entirely and just uses V1 generation

  Developer summary:
  • In hybrid mode, the plan is intentionally a blend:
      V2 premium components
      + generated placeholders for missing core roles
      + generated placeholders for customComponentsNeeded from the V1 selector

17.5 QUESTION 5
What does the “Master Copywriter” generateObject call produce, and how is its
output merged back into components?
--------------------------------------------------------------------------------

  The file calls this pass after V2 premium/generation structure is settled:
  • structuredComponents = enforcePlanStructure(mappedComponents)
  • then it builds copyPrompt
  • then it runs generateObject with a dedicated schema

  The copywriter prompt has a dual mission:
  • PART A - ARCHITECTURE
  • PART B - COPYWRITING

  Specifically it asks for:
  • multi-page distribution of component refIds into pages
  • sharedComponentRefIds for header/footer
  • keyContent for each component
  • props for each component

  Output schema fields:
  • components: [
      {
        name,
        keyContent,
        props: [{ key, value }]
      }
    ]
  • isMultiPage
  • pages
  • sharedComponentRefIds

  So the Master Copywriter does not output full component definitions.
  It outputs content and architectural overlays for already-selected components.

  Why this pass exists:
  • The premium / hybrid selection stage decides *which* components exist
  • The copywriter stage decides:
      what those components should say
      what props should be injected
      how they should be distributed across pages

  How merging works:
  • finalComponents = structuredComponents.map(...)
  • For each component c:
      find copyResult.components entry where cc.name === c.name
  • Then return:
      ...c
      keyContent: copy?.keyContent || c.description
      props: copy?.props ? Object.fromEntries(copy.props.map(...)) : {}

  That means:
  • If copywriter provides keyContent, use it
  • Else fallback to component description
  • If copywriter provides props array, convert it into plain object
  • Else fallback to empty props object

  Why props are converted with Object.fromEntries:
  • The AI schema uses an array of key/value pairs for structured output safety
  • Downstream component bundle / generation logic wants a normal object map

  Example transformation:
  • AI returns:
      props: [
        { key: 'title', value: 'Luxury Service, Without the Wait' },
        { key: 'subtitle', value: 'Door-to-door detailing for modern fleets.' }
      ]
  • Route converts to:
      props: {
        title: 'Luxury Service, Without the Wait',
        subtitle: 'Door-to-door detailing for modern fleets.'
      }

  What isMultiPage from copywriter influences:
  • In practice, the route hardcodes final planData.isMultiPage = true for the V2
    branch, but pages/shared refs from copyResult are still used if present
  • If copywriter pages are weak or empty, deterministic fallback fills in

  Why this call is so important:
  • It gives premium components real payload text
  • It gives generated components starter content direction
  • It produces a page map that later render-app-template and edit flows rely on

  Developer summary:
  • The Master Copywriter is not choosing components
  • It is enriching chosen components with meaningful content and routing layout
  • The route merges that enrichment back into the already-normalized plan

17.6 QUESTION 6
What does buildDeterministicMultiPagePlan do when the copywriter’s pages array is
weak or empty?
--------------------------------------------------------------------------------

  buildDeterministicMultiPagePlan is the backup architecture generator.

  Why it exists:
  • The copywriter pass can fail
  • Or it can succeed but return weak / incomplete pages
  • The system still needs a usable multi-page routing map

  Its input:
  • components array, already normalized and enriched enough to inspect roles and
    descriptions/designFocus

  Its first job:
  • Split shared header/footer from content components
  • sharedComponentRefIds = header/footer refIds

  Its second job:
  • Categorize content components by intent using regex over:
      name
      description
      designFocus
  • Buckets:
      pricing
      reviews
      services
      other

  Then it builds candidate page assignments:
  • Home     gets first service-like refs + one "other"
  • Services gets remaining services + more "other"
  • Pricing  gets pricing refs + one review-ish ref
  • Reviews  gets remaining review refs

  It filters out any pages with zero assigned componentRefIds.

  If fewer than 2 pages remain:
  • It enters a fallback-of-the-fallback path
  • It creates:
      Home page with all content refs
      About page with roughly the second half of content refs
  • shared header/footer stay shared across all pages

  So the function guarantees:
  • isMultiPage: true
  • at least some sensible page structure
  • shared header/footer if available

  How the route uses it:
  • const deterministicMpa = buildDeterministicMultiPagePlan(finalComponents)
  • pages = copyResult.pages if they exist and are non-empty
    else deterministicMpa.pages
  • sharedComponentRefIds = copyResult.sharedComponentRefIds if present
    else deterministicMpa.sharedComponentRefIds

  That means the deterministic plan is not always used.
  It is a fallback, but a very important one.

  Why this matters:
  • The builder strongly prefers multi-page sites in this branch
  • A missing pages array would break App.jsx route rendering
  • A weak pages array could create empty or nonsensical routes

  What it does not do:
  • It does not generate copy text
  • It does not rewrite components
  • It only creates route/page assignment metadata

  Design philosophy behind it:
  • Even if the AI copywriter is flaky, the product should still produce a
    coherent route plan instead of collapsing

  Developer summary:
  • buildDeterministicMultiPagePlan is the planner's hard safety net for routing.
  • It turns a set of components into a minimally sane multipage structure when
    the AI page planner is incomplete or absent.

17.7 QUESTION 7
How are enforcePlanStructure and path flattening used before the response is
returned?
--------------------------------------------------------------------------------

  There are two separate hardening layers here:
  • structural hardening
  • path hardening

  1. enforcePlanStructure

  What it does:
  • Deduplicates components by refId
  • Ensures only one header, one hero, and one footer survive
  • Sorts components by role order:
      header -> hero -> feature -> footer

  Where it is used:
  • after V2 mappedComponents are assembled
  • again after flattened components are built
  • again after fallback placeholders are added

  Why it matters:
  • AI output or merged hybrid data can contain duplicate or conflicting
    structural roles
  • The app shell expects a clean top-to-bottom layout shape

  2. path flattening

  What the code does:
  • For every planData.component, derive baseName = path.basename(c.path)
  • Default flattened path = src/components/${baseName}

  Then it preserves special paths:
  • if path already includes src/components/premium/ -> keep it
  • if path includes src/pages/ -> keep it

  Else it normalizes:
  • strips accidental `.jsx .jsx`
  • converts .js or .tsx to .jsx
  • appends .jsx if missing

  Why path flattening exists:
  • It prevents sub-folder hallucinations from LLM output
  • It keeps component generation in the exact file layout the frontend expects
  • It ensures one consistent convention for generated components

  Why premium/page paths are exempt:
  • premium components intentionally live in src/components/premium/
  • page components intentionally live in src/pages/

  The combined effect before return:
  • components are shape-safe
  • roles are deduped and ordered
  • file paths are valid and predictable
  • required routes/page paths are normalized

  The route also normalizes pages:
  • ensures pagePath starts with /
  • converts /home or /index to /
  • ensures root route exists
  • if multipage but pages array empty, creates a root page using all refs

  appComposition is also synchronized:
  • order = flattenedComponents.map(c => ({ refId: c.refId || c.name }))

  Why this is critical for downstream code:
  • render-app-template relies on consistent components and pages
  • generate-single-component needs clean file paths
  • frontend import validation expects stable path conventions

  Developer summary:
  • enforcePlanStructure cleans the component list semantically
  • path flattening cleans it physically
  • both happen before the route responds so downstream stages do not need to
    keep fixing planner mistakes

17.9 QUESTION 9
When does resolveCrossProviderFallback run, and what failure does it recover from?
--------------------------------------------------------------------------------

  resolveCrossProviderFallback is imported from llm-lightweight.js.

  In this file, it runs only in the V1 path.

  Specifically:
  • The route first tries generateObject with getModel(model)
  • If that throws, the catch block logs WEBSITE-PLAN-V1 error
  • Then it computes:
      const fb = resolveCrossProviderFallback(model)
  • Then it retries generateObject using getModel(fb)

  So the trigger is:
  • the primary V1 plan generateObject call fails

  What kind of failure this is meant to recover from:
  • provider overload
  • rate limit / quota issues
  • transient provider-specific API failures
  • any error that causes the initial generateObject call to throw

  Why cross-provider fallback helps:
  • If the chosen provider family is overloaded, a different provider may still
    be healthy
  • Example mapping:
      openai heavy -> google fallback
      anthropic heavy -> google fallback
      google heavy -> openai fallback

  Important nuance:
  • This fallback is not used in the V2 branch in this file
  • V2 has its own robustness inside select-components-v2 and other multi-step
    logic

  Another important nuance:
  • This fallback is for planning, not for apply or repair inside this route
  • Other files use resolveCrossProviderFallback too, but here it specifically
    protects the one-shot WEBSITE-PLAN-V1 call

  What it returns to logs:
  • The response log marks that retry occurred
  • extra: `Retry with ${fb}`

  Why it matters for product behavior:
  • premiumMode off relies on V1 planning
  • Without this fallback, a single provider outage would break that mode much
    more often

  What it does not recover from:
  • bad schema design
  • deterministic code bugs in route logic
  • malformed inputs that are invalid regardless of provider

  It is a model/provider resiliency tool, not a business-logic fix.

  Developer summary:
  • resolveCrossProviderFallback runs when the first V1 planning model fails
  • it retries planning on another provider family to recover from service-level
    or quota-related failures

18.1 QUESTION 1
What is the order of LLM steps: blueprint match, template match, category refine,
final select—and when does each run?
--------------------------------------------------------------------------------

  Short answer:
  The orchestrator starts with template matching, then either short-circuits into
  template mode or continues through the normal component-selection pipeline:

  Full normal order:
  0a. Template match
  0b. Template blueprint load (not an LLM step)
  1. Blueprint match (website type match)
  2. Blueprint load (not an LLM step)
  3. Category refine
  4. Industry filtering (not an LLM step)
  5. Final component select
  6. Compatibility validation (not an LLM step)
  7. Bundle fetch (not an LLM step)

  More precisely:

  Step 0: Community template matching
  • selectComponentsV2 first tries matchTemplateFromDB(...)
  • matchTemplateFromDB:
      fetches top templates from weighted_templates
      sends them to llm.matchTemplate(...)
  • If confidence is high enough and a blueprint can be loaded, the pipeline
    short-circuits and skips Steps 1-5

  Step 1: Website type / blueprint match
  • Runs only if no template short-circuit happened
  • detectWebsiteType(...)
      fetches blueprints
      calls llm.matchWebsiteType(...)
      may trigger dynamic blueprint generation if confidence is low

  Step 2: Blueprint loading
  • Non-LLM
  • loadBlueprint(...) either:
      returns dynamic blueprint data
      or fetches a stored blueprint row by slug

  Step 3: Category refinement
  • refineCategories(...)
      fetches category details
      calls llm.refineCategories(...)
      ensures header and footer are always present

  Step 4: Industry-aware filtering
  • Non-LLM
  • filterByIndustry(...)
      loads candidate components from DB
      optionally filters by suitable_for industry metadata
      may backfill with universal components
      may broaden search for explicit components

  Step 5: Final component selection
  • scoreAndSelect(...)
      computes heuristic scores
      takes top 50
      maps explicit names to component ids
      calls llm.selectFinalComponents(...)
      then maps ids back to component rows

  Why template match comes first:
  • A template is a fully ordered website structure, not just one component
  • If a template is already a strong structural match, there is no reason to do
    expensive component-by-component selection

  Why blueprint match comes after template match:
  • Template is the most complete possible shortcut
  • Blueprint is a looser structural category, not a full preassembled website

  Why category refine comes after blueprint match:
  • Categories depend on the chosen blueprint
  • You first need to know the website type / blueprint family before deciding
    which required and optional categories to keep

  Why final select comes after category refine and filtering:
  • The LLM should pick from a smaller, higher-quality candidate pool
  • This reduces noise and keeps token size manageable

  Special short-circuit paths:
  • Template short-circuit:
      successful template match + template blueprint available
      -> skip Steps 1-5 entirely
  • Strict mode short-circuit:
      if strictMode && explicitNames.length > 0
      -> directly fetch explicit components from DB
      -> skip the standard Steps 1-7 component selection process

  So the true runtime order depends on which branch is triggered.

18.2 QUESTION 2
What happens when matchWebsiteType returns low confidence—how does dynamic
blueprint generation work?
--------------------------------------------------------------------------------

  detectWebsiteType(...) first fetches active blueprints from:
  • website_type_blueprints

  Then it calls:
  • llm.matchWebsiteType(prompt, designSystem, blueprints, aiModel)

  That LLM returns:
  • slug
  • confidence
  • reasoning

  The key threshold:
  • If confidence < 0.6, the pipeline considers the predefined blueprint match
    too weak

  In that case:
  • detectWebsiteType logs:
      No confident blueprint match — entering Dynamic Blueprint Generation
  • Then it calls generateDynamicBlueprint(prompt, designSystem, aiModel)

  generateDynamicBlueprint is not a small patch.
  It creates a brand new blueprint object from live taxonomy data.

  Inputs it fetches first:
  • top-level categories from component_categories
  • industry verticals from industry_verticals
  • color themes from color_themes

  Then it asks the LLM to generate a structured object with fields like:
  • slug
  • name
  • description
  • required_categories
  • optional_categories
  • recommended_component_count
  • default_color_mode
  • default_color_theme
  • default_typography
  • primary_industries
  • component_layout_order
  • generation_confidence

  Important rules in the prompt:
  • slug must start with "ai-generated-"
  • required_categories must include header and footer
  • total category count should be 4-12
  • layout order should put header first and footer last

  After the LLM returns a dynamicBlueprint:
  • The file wraps it into finalBlueprint with metadata:
      is_ai_generated: true
      generated_from_prompt: prompt
      is_active: true
      prompt_keywords: tokenized prompt words

  Then persistence logic runs:
  • if generation_confidence >= 0.7
      -> upsert into website_type_blueprints on conflict slug

  Then detectWebsiteType returns:
  • slug
  • confidence
  • isDynamic: true
  • blueprintData: finalBlueprint

  Why this matters:
  • The pipeline can still behave structurally even when no pre-authored website
    type preset matches the user request
  • Instead of collapsing to a generic fallback, it creates a tailored blueprint
    from taxonomy primitives

  Difference from the normal match flow:
  • Normal flow:
      existing blueprint row chosen from DB
  • Dynamic flow:
      brand-new blueprint object synthesized by LLM using categories, industries,
      and themes as allowed building blocks

  Failure behavior:
  • If blueprint generation itself fails, the error bubbles up and the caller may
    later fall back to a hardcoded safe preset such as saas-landing

  So low confidence does not mean “give up.”
  It means “switch from selecting a preset to authoring a new preset.”

18.3 QUESTION 3
What does pickStructuredFallback do when an LLM step fails or times out?
--------------------------------------------------------------------------------

  pickStructuredFallback is the deterministic backup selector used when the final
  LLM selection step fails.

  It is specifically used in:
  • llm.selectFinalComponents catch block

  Trigger:
  • The generateObject call for FINAL-SELECT throws
  • This may happen due to timeout, provider overload, quota, malformed response,
    or other transient issues

  Inputs:
  • candidates
  • requiredCategories
  • explicitComponents

  What it does:

  1. Sort candidates by computed_score descending
  • So the best heuristic matches rise to the top

  2. Track selection state
  • selected list
  • usedIds set
  • roleCount for header, hero, footer

  3. Force explicit component matches first
  • It tries to match explicit request names/ids against candidates
  • If found, they are added before anything else

  4. Ensure structural shell roles
  • It tries to add one header
  • one hero
  • one footer

  5. Fill by requested categories
  • For each required category, it finds a candidate matching that category hint
  • Category matching uses matchesCategoryHint(...)

  6. Fill remaining slots until target size is reached
  • target size is:
      min(9, max(6, requiredCategories.length + 1))
  • It keeps adding best remaining candidates

  Important constraint:
  • tryAdd() will refuse duplicate component ids
  • It also refuses second header, second hero, or second footer

  So the fallback is not random.
  It is a deterministic architecture-aware heuristic selector.

  Why this is valuable:
  • If the LLM cannot finish the selection step, the pipeline still returns a
    useful, coherent set of premium components
  • It preserves:
      explicit user intent
      one header / one hero / one footer shell
      required category coverage
      score-based quality ordering

  What it does not do:
  • It does not generate new categories
  • It does not reason semantically as deeply as the LLM
  • It only selects from already-scored candidates

  Why that is acceptable:
  • By the time this fallback runs, the candidate pool is already filtered and
    scored
  • The pipeline has enough metadata to make a strong non-LLM guess

  Important distinction:
  • pickStructuredFallback is not the fallback for blueprint matching
  • It is specifically the fallback for final component selection

  Blueprint matching fallback is:
  • low confidence -> generateDynamicBlueprint

  Category refine fallback is:
  • return blueprint.required_categories

  Final select fallback is:
  • pickStructuredFallback(...)

18.4 QUESTION 4
How does inferStructuralRole affect which components can be selected together
(e.g. header/hero/footer)?
--------------------------------------------------------------------------------

  inferStructuralRole is one of the most important non-LLM helpers in this file.

  It inspects:
  • category
  • component_id
  • name
  • description / visual_description

  Then it classifies each component as one of:
  • header
  • hero
  • footer
  • feature

  Why this classification matters:
  • Several parts of the pipeline assume a website should have:
      one header
      one hero
      one footer
      many possible features

  Places where inferStructuralRole affects behavior:

  1. pickStructuredFallback
  • It prevents selecting more than one header/hero/footer in the deterministic
    fallback selector

  2. matchesCategoryHint
  • A category hint like header, hero, or footer maps directly to
    inferStructuralRole(component)

  3. enforceStructuralSelection
  • It drops duplicate structural roles from the selected list
  • If the chosen selection has two heroes, one is removed
  • If no header/hero/footer exists, it tries to add one from the candidate pool

  4. final structural ordering
  • enforceStructuralSelection sorts selected components in role order
    header -> hero -> feature -> footer

  Why this is essential:
  • The LLM might choose multiple premium components that are individually good
    but collectively structurally redundant
  • A website with two headers and no footer would be a broken baseline

  Example:
  • Candidate A = cinematic hero
  • Candidate B = another hero
  • Candidate C = premium header
  • Candidate D = premium footer
  If the LLM or scored fallback would otherwise include both heroes, structural
  enforcement trims the list to one hero shell.

  What counts as feature:
  • Anything not recognized as header, hero, or footer

  Why regex-based role inference is good enough here:
  • The catalog metadata uses descriptive ids/names/categories
  • The role decision only needs to distinguish major shell components

  Important nuance:
  • inferStructuralRole does not itself select or remove anything
  • It is the metadata function that powers higher-level selection constraints

  Developer summary:
  • inferStructuralRole is the structural grammar of the V2 selector
  • It is how the file decides which components can coexist without producing an
    architecturally nonsensical selection

18.7 QUESTION 7
How does matchTemplate differ from matching a single component—what is a
“template” in this code?
--------------------------------------------------------------------------------

  In this codebase, a template is not just one reusable component.

  A template is:
  • a pre-assembled ordered set of sections
  • effectively a full website skeleton
  • composed of multiple components already arranged in a meaningful sequence

  That idea is encoded directly in the system prompt for llm.matchTemplate:
  • "A template is a pre-assembled ordered set of components (hero, features,
    pricing, etc.) that forms a complete website."

  How matchTemplate differs from single-component matching:

  Component matching asks:
  • Which individual components should I combine to build this site?

  Template matching asks:
  • Is there already a whole curated website assembly that matches this request?

  Data source difference:
  • Template matching uses weighted_templates view
  • Component selection uses components table

  Structural difference:
  • Template match returns:
      template_id
      confidence
      reasoning
  • Then getTemplateBlueprint(template_id) loads its ordered template_sections

  Resulting behavior difference:
  • If template match is confident enough (>= 0.75) and blueprint loads
    successfully, the pipeline short-circuits
  • That means it skips:
      website type detection
      blueprint selection
      category refinement
      candidate filtering
      scoreAndSelect

  Why this is powerful:
  • A high-quality template can preserve curated section ordering and stronger
    whole-site coherence than ad hoc component recombination

  What happens after successful template match:
  • It still runs compatibility validation
  • It still fetches bundles
  • It returns templateUsed metadata in the final payload

  What templateUsed contains:
  • templateId
  • confidence
  • reasoning

  So a template is basically:
  • a website-level blueprint made of actual section assignments
  • not just a single hero or footer component

  Developer summary:
  • matchTemplate is website-level structural matching
  • component selection is section-level assembly
  • template success can bypass most of the rest of the pipeline

18.8 QUESTION 8
What does explicitComponents / mandatory IDs change in selectFinalComponents’s
system prompt?
--------------------------------------------------------------------------------

  explicitComponents changes both scoring and the final selection prompt.

  In scoreAndSelect():
  • explicit components get a massive heuristic score boost:
      +100 to computed_score
  • This keeps them in the top 50 candidate pool

  Then before calling llm.selectFinalComponents:
  • explicit names are mapped to actual component_ids where possible

  Inside llm.selectFinalComponents:
  • if explicitComponents.length > 0
      -> it appends a MANDATORY SELECTION block to the system prompt

  That block says:
  • The user explicitly requested these components
  • You MUST include them in selected_component_ids if they appear in the list

  Why this matters:
  • Without it, the LLM might still choose a different component even if the user
    explicitly named one
  • The explicit list makes the selection prompt partly constrained rather than
    purely preference-based

  It also changes candidate pool behavior indirectly:
  • boosted explicit candidates are less likely to be lost before the LLM even
    sees the final top-50 list

  There are multiple sources of explicit component intent in this pipeline:
  • explicitNames argument passed into selectComponentsV2
  • EXPLICIT_COMPONENTS marker parsed from the prompt itself
  • strict mode user-provided ids

  Strict mode is even stronger than explicit selection in the normal scoring path:
  • if strictMode && explicitNames.length > 0
      -> the orchestrator short-circuits and directly fetches those components
      -> it does not even run the normal final-select LLM step

  So explicit components can influence selection in three layers:
  1. candidate scoring boost
  2. mandatory wording in final LLM prompt
  3. strict mode short-circuit that bypasses normal selection entirely

  Developer summary:
  • explicitComponents are not just “nice suggestions”
  • they materially reshape the final selection prompt and candidate ranking so
    user-named components survive into the final chosen set

18.9 QUESTION 9
What are the abort timeouts for the different generateObject calls, and why
might final selection get 60s?
--------------------------------------------------------------------------------

  Timeouts in this file:

  llm.matchWebsiteType
  • 15 seconds

  llm.refineCategories
  • 15 seconds

  llm.selectFinalComponents
  • 60 seconds

  llm.matchTemplate
  • 60 seconds

  generateDynamicBlueprint
  • no explicit AbortController timeout in the shown code

  Why blueprint match and category refine use 15s:
  • They are relatively compact classification steps
  • They operate over smaller inputs
  • They are meant to be quick routing decisions, not long creative synthesis

  Why final selection gets 60s:
  • It operates on up to 50 scored candidates
  • The prompt contains richer metadata and stronger selection reasoning burden
  • The code comment explicitly says:
      60s instead of 15s to withstand load peaks
  • So the timeout is longer both because the task is heavier and because it is
    more likely to hit provider latency spikes

  Why template match also gets 60s:
  • It is selecting among full website templates, not just categories
  • It may need more reasoning about structural fit
  • The author explicitly chose 60s there too

  Why dynamic blueprint generation has no explicit abort in this implementation:
  • It relies on the provider call without controller timeout here
  • It is comparatively rare and treated as a special fallback path

  Operational meaning:
  • If matchWebsiteType or refineCategories hangs, the pipeline degrades quickly
    into fallback logic
  • If final select or template match is slow, the system tolerates more waiting
    before falling back because these are high-value decisions

  Timeout/fallback relationships:
  • matchWebsiteType timeout -> low confidence fallback
  • refineCategories timeout -> use blueprint.required_categories
  • final-select timeout -> pickStructuredFallback
  • template-match timeout -> no-match fallback, continue with standard pipeline

  Developer summary:
  • Short timeout for cheap routing steps
  • Long timeout for high-value, larger-context selection steps
  • 60s on final selection is a deliberate resilience choice for the heaviest
    LLM selection stage in the pipeline

19.1 QUESTION 1
Why does the route return immediately when premiumMode === 'off', and what JSON
shape does it return?
--------------------------------------------------------------------------------

  Short answer:
  • Because premiumMode `off` means the builder should not use premium catalog
    components at all.
  • So this route bypasses Supabase component lookup entirely and returns a
    “no premium selection” result immediately.

  The guard clause exists near the top of the route:
  • if (premiumMode === 'off') { ... return res.json(...) }

  Why it returns early:
  • In `off` mode, the product intent is:
      no premium component selection
      no catalog search
      no DB component matching
      full LLM generation later
  • So touching the premium catalog would waste time and muddy the meaning of the
    mode.

  The file even states this policy explicitly in a comment:
  • If premium mode is OFF, do not even touch the Supabase components table

  JSON shape returned in this branch:
  • {
      success: true,
      selection: {
        selections: [],
        reasoning: 'Premium Mode is OFF - Strictly using LLM generation.',
        customComponentsNeeded: ['Entire page structure']
      }
    }

  What each field means:
  • success: true
      the route itself worked
      it is not an error state
  • selection.selections: []
      no premium components were chosen
  • selection.reasoning
      explains that premium mode is off by design
  • selection.customComponentsNeeded: ['Entire page structure']
      tells downstream logic that nothing premium should be injected and the whole
      site should be generated later

  Why it still returns success instead of error:
  • `off` mode is valid product behavior, not failure
  • Downstream code expects a selection-shaped object regardless of mode

  Why customComponentsNeeded is populated:
  • It gives later planning/generation stages a strong signal that all major
    structure must come from generated components
  • It preserves a consistent contract with the normal success response shape

  Developer summary:
  • The immediate return is a policy decision, not an optimization accident.
  • In `off` mode, this route acts like a no-op selector that explicitly says:
    “use zero premium components and generate everything.”

19.2 QUESTION 2
How is the catalog and category list built before the LLM sees it?
--------------------------------------------------------------------------------

  After the route verifies that prompt exists and premiumMode is not off, it
  builds the context the LLM will use.

  First it reads config:
  • const selectionConfig = appConfig.selection || {}

  • getCatalogForPromptAsync([], maxItems)

  Important point:
  • The route is not asking the LLM to infer premium catalog entries from scratch.
  • It first loads a structured category list and a bounded premium component

  categories becomes:

  catalog becomes:

  • CATEGORIES: JSON.stringify(categories.map(cat => ({ slug, name, description })))

  There is also llmLog.request metadata before the actual call:
  • model

  • temperature

  Additional context layer:
  • imageDescriptions may be converted into a textual imageContext string
  • That imageContext is appended to the user prompt, not to the catalog itself

  Developer summary:
  • The selector LLM sees two curated knowledge blocks before reasoning:
    category taxonomy
    bounded premium catalog entries
  • Those are fetched first, then serialized into the prompt payload.

19.3 QUESTION 3
What does the EXPLICIT_COMPONENTS:[...] pattern do, and where does that text
usually come from?
--------------------------------------------------------------------------------

  The route scans the prompt for:
  • EXPLICIT_COMPONENTS:[...]

  It does this with:
  • prompt.match(/EXPLICIT_COMPONENTS:\s*\[(.*?)\]/i)

  If the pattern exists:
  • it splits the inner comma-separated names
  • trims whitespace
  • removes quotes/backticks
  • stores the result in explicitNames

  What explicitNames is for:
  • It tells the selector that the user did not just ask for a vague style or
    category; they named specific components they want included if available.

  If explicit names are found:
  • the route logs them
  • it builds an additional mandatoryRule string

  That mandatory rule says:
  • the user explicitly requested these components by name
  • you must find and include them if they exist in the catalog
  • search by name case-insensitively
  • assign confidence 1.0

  So this marker upgrades those names from "soft prompt hints" into "mandatory
  selection instructions" inside the system prompt.

  Where the EXPLICIT_COMPONENTS text usually comes from:
  • most commonly from enhance-prompt.js
  • that file has deterministic extraction logic:
      extractExplicitComponentNames(rawPrompt)
  • It can parse phrases like:
      use the X component
      add Y component
      PascalCase component names

  That means the marker may be:
  • directly typed by a user
  • or injected into the prompt upstream by enhancement/orchestration logic

  Why this mechanism exists:
  • Free-form user prompts are messy
  • Named component intent can get lost inside other descriptive text
  • This marker makes explicit component intent machine-readable for downstream
    selection and planning steps

  Why the selector cares:
  • Without the marker, the route might choose a semantically similar but
    different premium component
  • With the marker, the route is pushed to honor the user's named preference

  Developer summary:
  • EXPLICIT_COMPONENTS is a structured prompt marker carrying named component
    intent from upstream prompt enhancement into the premium selector.

19.10 QUESTION 10
How does maxRetries: 7 on generateObject relate to rate limits and reliability?
--------------------------------------------------------------------------------

  The generateObject call is configured with:
  • maxRetries: 7

  The comment says why:
  • Highly resilient config to combat rate limit overloads

  What this means in practice:
  • The AI SDK is allowed multiple retry attempts before the route gives up
  • This is useful for transient failures like:
      429 rate limits
      503 overloads
      short-lived provider hiccups

  Why this route benefits from a high retry budget:
  • It runs early in the build flow
  • A temporary failure here can derail premium-assisted planning
  • The request is structured and deterministic enough that retrying is often
    worthwhile

  Relationship to the catch block:
  • If retries are exhausted and the error still bubbles out:
      overloaded/provider demand style errors -> HTTP 503
      other errors -> graceful success fallback with empty selections

  So maxRetries: 7 improves reliability before the route has to choose between:
  • fail hard with provider unavailable
  • degrade into no premium selection / full generation fallback

  Why not infinite retries:
  • would hurt latency badly
  • would make the UI feel stuck
  • would still not help on persistent failures

  Why not just 1-2 retries:
  • premium selector calls are relatively valuable
  • transient overload is common enough to justify extra persistence

  Reliability strategy of this route:
  1. Try hard with retries
  2. If overload is clear, return 503 so caller knows provider is struggling
  3. Otherwise degrade gracefully into empty premium selection and continue the
     broader builder flow

  Developer summary:
  • maxRetries: 7 is a resilience setting tuned to keep premium selection usable
    under temporary provider stress without making failure the default outcome

20.3 QUESTION 3
What extra system text is appended when isEdit is true, and what is the “STEP 1
— INTENT ANALYSIS” workflow?
--------------------------------------------------------------------------------

  When `isEdit` is true and the route sees an existing applied project context,
  it appends a large edit-mode appendix to the base prompt.

  That block is labeled:
  • EDIT MODE — THINK BEFORE YOU CODE

  Its job:
  • convert the route from general generation mode into surgical modification mode
  • stop the model from unnecessarily regenerating the whole project
  • teach the model how to classify different edit intents before outputting code

  The edit appendix defines a four-step workflow:

  STEP 1 — INTENT ANALYSIS
  • The model must first classify what the user is really asking for.
  • It gives named edit categories:
      CONTENT EDIT
      THEME CHANGE
      ADD COMPONENT
      REPLACE/SWAP
      REMOVE COMPONENT
      ADD PAGE
      STRUCTURAL CHANGE

  Each category includes explicit output expectations.

  Examples from STEP 1:
  • CONTENT EDIT
      change only the specific text/data in 1-2 files
      do not touch unrelated files

  • THEME CHANGE
      update text/colors/imagery across most/all components
      do not remove or restructure components
      do not drop anything from App.jsx

  • ADD COMPONENT
      check catalog first
      use premium if a good fit exists
      else generate from scratch
      update App.jsx to include the new component

  • REPLACE/SWAP
      check catalog first
      output new component file
      update App.jsx import/render to replace old component

  • REMOVE COMPONENT
      output only App.jsx with the removed import/render

  • ADD PAGE
      create page file
      update siteMap.js
      update App.jsx routes
      if first page addition, convert current content into src/pages/Home.jsx and
      rewrite App.jsx as HashRouter shell

  • STRUCTURAL CHANGE
      full regeneration only when the user clearly says rewrite/redo entirely

  STEP 2 — CATALOG CHECK
  • Only applies to ADD COMPONENT and REPLACE/SWAP
  • Prefer a premium catalog component when possible
  • If using premium:
      write to src/components/premium/<id>.jsx
  • If no good fit:
      generate in src/components/

  STEP 3 — PER-FILE EDIT PLAN
  • The model is told to mentally map request type -> exact files to output

  STEP 4 — PRESERVATION CHECK
  • Verify existing components remain in App.jsx unless explicitly removed or
    deliberately swapped

  Why this edit appendix is so important:
  • Without it, edit prompts often lead LLMs to over-regenerate
  • The workflow teaches file-minimality and App.jsx preservation

  Developer summary:
  • STEP 1 is the route's internal decision tree for edit intent
  • It turns a vague edit request into a constrained file-output strategy before
    code generation begins

20.4 QUESTION 4
How does the code load sandbox files when sandboxId is present, and what is the
size limit per file?
--------------------------------------------------------------------------------

  In edit mode, after the prompt appendix is added, the route tries to load real
  sandbox context.

  It starts from:
  • const sandboxId = context.sandboxId

  If sandboxId exists:
  • it calls sandboxManager.getProvider(sandboxId)
  • or falls back to global.activeSandboxProvider

  If a provider is available:

  1. It lists files:
  • provider.listFiles('/home/user/app')

  2. It filters file tree to code-ish files:
  • extensions allowed:
      jsx
      js
      tsx
      ts
      css

  3. It tries to read src/App.jsx specifically:
  • provider.readFile('src/App.jsx')
  • failure is tolerated because App.jsx may not exist yet

  4. It loops all filtered sandbox files and reads content for:
  • .jsx files
  • .css files

  5. It only stores file content if:
  • content exists
  • content.length < 50000

  So the practical per-file size limit in this route is:
  • 50,000 characters

  Why the limit exists:
  • Avoid stuffing enormous files into the system prompt
  • Keep prompt size somewhat bounded
  • Prevent one giant file from dominating the edit context

  Where the loaded data is stored:
  • sandboxFileList
  • currentAppJsx
  • sandboxFileContents[path] = content

  Fallback if sandbox read fails:
  • It logs a warning and continues
  • Later, if sandboxFileContents is empty, it may fall back to
    global.sandboxState.fileCache.files

  Important subtlety:
  • The route is loading the live sandbox, not just client-side remembered files
  • That means the prompt can reflect post-polish or post-repair reality

  Developer summary:
  • With sandboxId present, the route inspects the real codebase through the
    sandbox provider and injects code files under a 50k-char per-file cap.

20.5 QUESTION 5
What is the “COMPONENT MANIFEST” block for, and why list imports relative to
App.jsx?
--------------------------------------------------------------------------------

  The COMPONENT MANIFEST block is built only in edit mode when sandbox files are
  available.

  First the route filters component files:
  • must end with .jsx
  • cannot be App.jsx
  • cannot be main.jsx
  • must live under components/ or premium/

  For each file, it derives:
  • fileName = component name from file
  • importPath = './' + f.replace(/^src\\//, '').replace(/\\.(jsx|tsx)$/, '')

  Example:
  • src/components/HeroSection.jsx
    -> import path becomes ./components/HeroSection

  That relative path is specifically relative to:
  • src/App.jsx

  Why this matters:
  • App.jsx is the shell the model most often needs to update during edits
  • Listing imports relative to App.jsx gives the model exact import syntax it
    should preserve or extend

  The manifest is injected as a readable list like:
  • HeroSection -> import HeroSection from './components/HeroSection';

  Then the route adds App.jsx preservation rules:
  • keep all listed imports if outputting App.jsx
  • only remove components if explicitly requested or intentionally swapped
  • new App.jsx must render all active components
  • if App.jsx does not need changes, do not output it
  • never silently drop components

  So the manifest has two jobs:
  1. inventory
      tell the model what components already exist
  2. preservation contract
      tell the model how App.jsx must relate to that inventory

  Why this is better than showing only raw file tree:
  • A raw file tree says what files exist
  • The manifest says how App.jsx should import those files
  • That directly reduces import breakage and accidental omission

  Developer summary:
  • The manifest is an App.jsx-centric import ledger
  • It teaches the edit model what already exists and what must remain wired in
    unless the user intentionally changes that wiring.

20.6 QUESTION 6
When does the route inject “golden” App.jsx from renderAppTemplate, and what

  The route injects golden App.jsx only when there is structured plan context:
  • const plan = context.plan

  • goldenAppJsx

  • output src/App.jsx exactly as provided

  Why the route still keeps other App.jsx preservation rules too:
  • Sometimes plan context may not exist
  • In those cases, the manifest and preservation instructions still help
  • When plan context does exist, the golden App.jsx becomes the strongest rule

  Developer summary:
  • Golden App.jsx is injected only when structured plan data exists
  • It turns App.jsx from an open generation problem into a deterministic mandate

20.7 QUESTION 7
How are messages built: system, recent chat, images, and current user message?
--------------------------------------------------------------------------------

  The route builds a `messages` array for streamText.

  Step 1:
  • start with one system message:
      [{ role: 'system', content: systemPrompt }]

  Step 2:
  • append recent conversation context from context.recentMessages if provided
  • only the last 10 messages are included

  For each recent message:
  • if msg.type === 'user'
      -> if msg.metadata.images exists
           build multimodal content array:
             [{ type: 'text', text: msg.content }, { type: 'image', ... }, ...]
         else
           push plain user content string
  • if msg.type === 'ai'
      -> push as assistant message

  So recent history is reconstructed as alternating:
  • role: user
  • role: assistant

  Step 3:
  • build currentContent from current prompt
  • always starts with text:
      [{ type: 'text', text: prompt }]
  • if current images exist, append image parts with base64 + mimeType

  Step 4:
  • push the current user message:
      { role: 'user', content: currentContent }

  Final message layout therefore is:
  • system prompt
  • optional prior user/assistant turns
  • current user multimodal message

  Why this matters:
  • system prompt defines global rules
  • recentMessages preserves conversational continuity
  • images preserve multimodal grounding
  • current user message provides the immediate task

  Why only last 10 messages:
  • prompt size control
  • recent edits matter more than ancient conversation

  Developer summary:
  • The route uses a standard chat-style message stack:
      one huge system message
      trimmed recent history
      current user content with optional images

20.9 QUESTION 9
How are npm package names extracted from the streamed code at the end?
--------------------------------------------------------------------------------

  After the full text stream completes, the route has one big string:
  • generatedCode

  Then it runs an import regex over that string:
  • importRegex = /import ... from 'pkg'/g

  For each matched import source:
  • pkg = matched module string

  It then filters out:
  • relative imports starting with .
  • absolute path-ish imports starting with /
  • react
  • react-dom

  For remaining package names:
  • if package starts with @
      -> keep the first two path segments
         example: @react-three/fiber
  • else
      -> keep the first segment before slash

  Examples:
  • framer-motion        -> framer-motion
  • lucide-react         -> lucide-react
  • @react-three/fiber   -> @react-three/fiber
  • react-router-dom     -> react-router-dom

  These are accumulated into:
  • const packages = new Set()

  Then on complete event, the route sends:
  • packages: [...packages]

  Why this exists:
  • Downstream client/apply logic may need to know which npm packages were used
  • The route can expose that dependency list immediately without separately
    parsing files later on the client

  Important nuance:
  • This is a heuristic import-based extraction
  • It does not inspect package.json
  • It does not validate package allowlist here
  • Allowlist enforcement happens later in the apply route

  Developer summary:
  • Package extraction is a regex pass over generated imports that produces a
    unique dependency list for the completion payload.

21.1 QUESTION 1
What is the first transformation applied to incoming files after parsing—
protected files and imports?
--------------------------------------------------------------------------------

  After the route resolves the active sandbox/provider and parses incoming files,
  the first two transformations are:
  • protected-file filtering
  • import sanitization

  Parsing itself happens like this:
  • if req.body.files exists and is an array
      -> use those explicit files
  • else
      -> parseFileBlocks(generatedCode)

  Immediately after parsing, the route filters out protected files:
  • it takes each file path
  • grabs the file name from the last path segment
  • drops any file whose basename is in PROTECTED_FILES

  PROTECTED_FILES contains:
  • vite.config.js
  • tailwind.config.js
  • postcss.config.js
  • package.json
  • package-lock.json
  • tsconfig.json

  Why this matters:
  • The builder wants to generate app code, not mutate sandbox scaffolding
  • These files are foundational and should not be overwritten by AI output

  After protected file filtering, the route sanitizes file contents:
  • files = files.map(f => ({ ...f, content: sanitizeImports(f.content || '') }))

  sanitizeImports does several things:

  1. Removes illegal package imports
  • It checks every ESM import line
  • If the import source is not allowed by isAllowedPackage(pkg)
      -> it replaces the line with a comment noting the strip

  2. Repairs bad lucide-react import sets
  • It checks named imports from lucide-react
  • It removes known non-icon names from NOT_LUCIDE_ICONS
  • If all imported names are invalid, the entire import is stripped
  • If some are valid, it rewrites the line to keep only valid names

  3. Strips CommonJS require() calls
  • Vite ESM projects should not use require() in generated code
  • any non-comment require() line gets replaced with a stripped comment

  So the first meaningful pipeline transformation is:
  • don't let the AI touch protected root config files
  • don't let illegal imports or broken lucide imports into the sandbox

  Why this happens before writing:
  • Once files hit the sandbox, bad imports can break build verification
  • Sanitizing first reduces downstream repair burden

  Developer summary:
  • The route's first safety layer is structural and dependency-oriented:
    drop forbidden files, then rewrite/strip unsafe imports before anything is written.

21.2 QUESTION 2
How is packagesToInstall computed, and what is the relationship to isAllowedPackage?
--------------------------------------------------------------------------------

  package installation is computed from two sources:
  • requestedPackages from the request body
  • detectedPackages extracted from imports

  Exact flow:
  • detectedSet starts with extractPackages(generatedCode || '')
  • then for each file, extractPackages(file.content) is added into the same set
  • detectedPackages = [...detectedSet]

  Then:
  • allPackages = unique union of requestedPackages + detectedPackages

  Next, built-ins are excluded:
  • react
  • react-dom
  • vite
  • tailwindcss
  • postcss
  • autoprefixer
  • @vitejs/plugin-react

  After that, allowlisting is applied:
  • packagesToInstall = allPackages.filter(p => !builtIn.has(p) && isAllowedPackage(p))
  • blockedPackages = allPackages.filter(p => !builtIn.has(p) && !isAllowedPackage(p))

  So isAllowedPackage is the policy gate.

  What isAllowedPackage does:
  • Local imports starting with . or / are always allowed
  • For package imports:
      if scoped package, take first two segments
      else take first segment
  • Then check ALLOWED_PACKAGES set

  ALLOWED_PACKAGES includes:
  • framer-motion
  • lucide-react
  • react-router-dom
  • react-icons
  • clsx
  • tailwind-merge
  • cobe
  • color-bits
  • @radix-ui/react-icons
  • ogl
  • three
  • @react-three/fiber
  • @react-three/drei
  • plus core react entries

  Important relationship:
  • isAllowedPackage is used twice in spirit:
      first indirectly by sanitizeImports to strip illegal import lines
      later directly to decide installable packages

  So even if a package is mentioned in generated code:
  • if it is not allowed, it gets blocked from install
  • and likely stripped from the file contents already

  Why this is good:
  • It prevents dependency hallucination
  • It avoids arbitrary npm installs in the sandbox
  • It keeps the builder inside a curated support surface

  Developer summary:
  • packagesToInstall is the union of requested and detected deps, minus built-ins,
    then filtered through the exact same allowlist policy that guards import safety.

21.3 QUESTION 3
In what order are files written, and why might CSS or App.jsx be ordered specially?
--------------------------------------------------------------------------------

  Before writing, the route sorts files:
  • CSS first
  • App.jsx last among app sources
  • everything else in the middle

  The sort logic is:
  • if a.path endsWith('.css') -> earlier
  • if b.path endsWith('.css') -> later
  • if a includes App.jsx -> later
  • if b includes App.jsx -> earlier
  • else leave relative ordering unchanged

  Why CSS first:
  • style dependencies can be available before components reference them
  • helps reduce transient problems where components land before their styles
  • fits the builder mental model that global styling should exist before shell/UI

  Why App.jsx last:
  • App.jsx imports many other components
  • if App.jsx is written before imported components exist, the sandbox can sit in
    a temporarily broken state
  • writing it last makes the assembled app shell point at files that already
    exist on disk

  So the route is minimizing short-lived invalid intermediate states.

  What happens during writes:
  • provider.writeFile(path, content)
  • file path added to filesCreated
  • SSE file_written event is emitted
  • step event announces current component
  • build manifest is updated
  • sandboxState file cache is updated if present

  Why direct write order matters even though verification happens later:
  • it reduces the chances of weird preview reloads between writes
  • it makes the sandbox filesystem converge toward a valid build more smoothly

  Developer summary:
  • CSS is prioritized as foundational styling
  • App.jsx is delayed because it is the import hub and should point at already-
    written files rather than missing ones.

21.4 QUESTION 4
What does verifySandboxBuild run, and when is auto-repair skipped
(e.g. permission errors)?

  verifySandboxBuild is imported from:
    web/server/lib/verify-sandbox-build.js

  It does the following:
  • resolves the sandbox provider from sandboxManager
  • runs:
      sudo chown -R user:user /home/user/app || true
    to fix permissions for Vite temp writes
  • then runs:
      npx vite build --base=./

  If the build fails:
  • it also runs diagnostics:
      ls -la
      npm list --depth=0
  • those logs are appended to the verification logs

  Back in apply-ai-code-stream.js:
  • STAGE 4 sends VERIFY_STARTED
  • calls verifySandboxBuild(activeSandboxId)

  If verify succeeds:
  • buildPassed = true
  • VERIFY_PASSED SSE event is emitted

  If verify fails:
  • the route considers auto-repair

  But auto-repair is skipped for permission/infrastructure-style failures:
  • if logs contain:
      EACCES
      permission denied
      EPERM

  Why skip repair then:
  • these are sandbox infrastructure issues, not code bugs
  • asking the LLM to rewrite code would be pointless or harmful

  In that case the route sends VERIFY_FAILED with an explanatory excerpt saying
  the failure is likely due to sandbox permissions, not code quality.

  Developer summary:
  • verifySandboxBuild runs a real production Vite build in the sandbox
  • auto-repair only runs for code-type failures, not for permission/infrastructure errors.

21.5 QUESTION 5
How does the repair loop merge sandbox files that were not in the original apply batch?
--------------------------------------------------------------------------------

  When verification fails and auto-repair begins, the route builds repair context
  carefully.

  It starts with:
  • let repairFiles = [...sortedFiles]

  That includes only the files from the current apply batch.

  Then it expands repair context by reading the actual sandbox:
  • list all files under /home/user/app
  • keep only src/ files with extensions:
      jsx
      js
      tsx
      ts
      css

  Then:
  • existingPaths = set of current batch file paths
  • for each src sandbox file not already in existingPaths:
      read the file
      if content exists -> push { path, content } into repairFiles

  So the repair loop merges:
  • current pending writes
  • plus all other existing sandbox source files

  Why this is critical:
  • A build error may be caused by interactions with files not touched in the
    latest apply batch
  • Without the full project context, the repair LLM could make wrong fixes

  Example:
  • You apply a new page component
  • The failure actually comes from App.jsx import mismatch or a pre-existing
    helper file
  • If repair saw only the new page file, it could not reason properly

  After merging, attemptRepair receives:
  • files: repairFiles
  • buildErrors: buildLogs
  • repairLog
  • buildModel

  If repair succeeds:
  • fixedFiles are written back
  • sortedFiles is updated too, so future repair attempts see latest content

  Developer summary:
  • The repair loop is intentionally whole-project-aware.
  • It expands beyond the current apply batch by pulling in any other existing
    sandbox source files before asking the LLM to debug the build.

21.6 QUESTION 6
What is the exact formula for shouldRunAsyncPolish, and how do isEdit and
premiumMode interact?
--------------------------------------------------------------------------------

  Exact formula in the route:
  • const shouldRunAsyncPolish =
      !skipPolish && (!isEdit || premiumMode === 'hybrid' || premiumMode === 'strict')

  This means polish runs only if:
  • skipPolish is false
  • and either:
      this is not an edit
      or it is an edit but premiumMode is hybrid
      or it is an edit but premiumMode is strict

  Simplified interpretation:

  Initial builds (isEdit = false)
  • polish runs unless skipPolish = true

  Edits (isEdit = true)
  • polish runs only in hybrid or strict
  • if premiumMode = off, edits skip final polish

  Why this policy exists:
  • initial builds benefit heavily from full premium refinement
  • edit loops in off mode should stay faster and more surgical
  • hybrid/strict modes are more premium-oriented, so heavier post-processing is
    still considered worthwhile even for edits

  Interaction examples:
  • isEdit=false, skipPolish=false, premiumMode=off
      -> true
  • isEdit=true, skipPolish=false, premiumMode=off
      -> false
  • isEdit=true, skipPolish=false, premiumMode=hybrid
      -> true
  • isEdit=true, skipPolish=true, premiumMode=hybrid
      -> false

  Developer summary:
  • skipPolish is the absolute kill switch
  • otherwise, all initial builds polish
  • only hybrid/strict edits polish

21.7 QUESTION 7
What happens if polish passes but verifySandboxBuild fails afterward—repair,
rollback, or both?
--------------------------------------------------------------------------------

  The polish stage has its own verification loop after writing polished files.

  Flow:
  1. runAndApplyPolish writes heavy-polish output
  2. verifySandboxBuild(activeSandboxId) runs again as polishVerify

  If polishVerify succeeds:
  • buildPassed = true
  • polish is considered clean

  If polishVerify fails:
  • the route attempts exactly one surgical repair-style second polish pass:
      await runAndApplyPolish(polishedFiles or filesToPolish, polishVerify.logs)

  Then it verifies again:
  • finalVerify = await verifySandboxBuild(activeSandboxId)

  If finalVerify succeeds:
  • buildPassed = true
  • polish repair is considered successful

  If finalVerify still fails:
  • the route does NOT continue trying more polish fixes forever
  • it rolls back to prePolishSnapshot
  • then re-verifies after rollback

  So the answer is:
  • both, in sequence
  • first one repair-style second attempt
  • then rollback if still broken

  Why this is smart:
  • give polish one chance to self-correct
  • but prioritize returning to a stable build over endless experimentation

  Developer summary:
  • Post-polish failure triggers one corrective pass
  • if still broken, the route restores the pre-polish state and verifies that instead

21.8 QUESTION 8
What is prePolishSnapshot, and when are files restored from it?
--------------------------------------------------------------------------------

  prePolishSnapshot is created right before the heavy polish pass:
  • const prePolishSnapshot = new Map(filesToPolish.map((f) => [f.path, f.content]))

  So it is:
  • a point-in-time map of path -> original content
  • for the exact files being considered for polish

  Why it exists:
  • heavy polish can improve quality but also introduce build breakage
  • the route needs a known-good rollback baseline

  When restoration happens:
  • polishVerify fails
  • one follow-up repair-like polish attempt also fails
  • finalVerify after that attempt is still unsuccessful

  At that point:
  • the route logs that polish repair failed
  • sends a warning SSE event
  • loops over prePolishSnapshot.entries()
  • writes each original file content back to the sandbox
  • updates sandboxState file cache if present

  Then it runs:
  • rollbackVerify = await verifySandboxBuild(activeSandboxId)

  So rollback is not blind.
  It is verified after restore.

  What if rollbackVerify succeeds:
  • buildPassed = true
  • the route confirms that pre-polish rollback restored a clean build

  What if rollbackVerify still fails:
  • buildPassed may remain false
  • route logs that build is still failing after rollback

  Why this snapshot is per-polish-stage rather than global:
  • it is specifically protecting against polish regressions
  • the earlier apply/repair steps may already have produced the best known stable
    state at that point

  Developer summary:
  • prePolishSnapshot is the exact pre-refinement code image for files under
    polish, restored only if polish and its one follow-up correction still leave
    the build broken.

21.9 QUESTION 9
What runs between heavy polish and mini polish, and which model ids are used for
fillers vs mini polish?
--------------------------------------------------------------------------------

  Heavy polish phase:
  • runPolishStep(targetFiles, prompt, errors, {
      model: buildModelId,
      fileTree,
      isEdit,
      sandboxId
    })

  While heavy polish is running:
  • runPolishFillers(...) runs in parallel
  • filler messages stream casual progress narration to the user

  So between heavy polish start and mini polish, the route does:
  1. heavy polish call
  2. parallel filler loop
  3. stop filler loop when heavy polish finishes
  4. verify polished build
  5. maybe do one repair-style second pass
  6. maybe rollback to prePolishSnapshot
  7. only if build is still green -> enter mini polish

  Which model IDs are used:

  Heavy polish:
  • uses buildModelId (the user's selected heavy model from req.body.model)

  Fillers:
  • runPolishFillers gets { model: modelId, prompt, ... }
  • inside polish-filler.js, resolveLightweightModel(model) is used
  • that means:
      openai/* -> openai/gpt-5.4-mini
      anthropic/* -> anthropic/claude-haiku-4-5-20251001
      google/* -> google/gemini-2.5-flash

  Mini polish:
  • runMiniPolishStep(filesForMini, prompt, { model: modelId, ... })
  • inside mini-polish-refinement.js, resolveLightweightModel(heavyModel) is used
  • so mini polish also uses the lightweight model family, not the heavy model

  Therefore:
  • heavy polish = user-selected heavy model
  • fillers = lightweight companion model
  • mini polish = lightweight companion model

  Why this split makes sense:
  • heavy polish needs deeper reasoning and more context
  • fillers need low-cost, low-latency narration
  • mini polish is intended as a quick reliability sweep, not a second expensive
    full creative rewrite

  Developer summary:
  • Between heavy polish and mini polish, the route verifies, attempts one
    correction if needed, and may rollback
  • fillers and mini polish use lightweight model ids derived from the heavy build model

22.4 QUESTION 4
What retry or fallback behavior exists if generateObject fails (if any)?
--------------------------------------------------------------------------------

  There is a two-step model attempt strategy.

  First attempt:
  • generateObject using getModel(model)
  • uses AbortController timeout of 60 seconds

  If that first attempt fails:
  • catch(err)
  • compute fallbackModel = resolveCrossProviderFallback(model)
  • retry generateObject using getModel(fallbackModel)

  Important details:
  • The first attempt has abortSignal with 60s timeout
  • The fallback attempt does not show an AbortController in the retry block
  • If fallback also fails, the error is thrown to outer catch

  What outer catch does:
  • if error looks like AI provider overload / retry exhaustion / 429 / 503
      -> return HTTP 503 with provider unavailable message
  • otherwise
      -> return HTTP 500 with error.message

  So there is fallback behavior, but not an infinite retry loop.

  Why cross-provider fallback exists here:
  • Component generation is part of the main build queue
  • If the selected provider is overloaded, another provider family may succeed

  Developer summary:
  • The route tries the requested model first, then a cross-provider fallback
    model once, then surfaces a 503/500 if both fail.

What is USE_PARALLEL_POLISH, and how does concurrency differ for Anthropic vs others?

  Meaning:

  • 2-Step Async Parallel execution instead of slow monolithic runs

  • otherwise

  • The code comment says Anthropic org TPM is easy to exceed with 3x Sonnet +

  • In other words, Anthropic is treated as more rate-limit sensitive in this
    heavy polish context

  Why non-Anthropic models get 2:
  • Parallelism speeds up polishing across many files
  • But the code still keeps concurrency modest rather than fully blasting all
    files in parallel

  So USE_PARALLEL_POLISH changes both:
  • the shape of the LLM interaction
  • the way rate limits are managed

  Practical outcomes:
  • parallel mode:
      better throughput on many files
      per-file retry possible
      design-spec-conditioned system prompt reused per file
  • monolithic mode:
      one giant pass over the full fileContext

  Developer summary:
  • USE_PARALLEL_POLISH turns polish into a controlled file-by-file pipeline, and
    Anthropic is deliberately throttled harder (1 concurrent file) than others (2).

23.5 QUESTION 5
How does polishOneFile build roleContext from the file path?

  In parallel mode, polishOneFile derives a human role label from the lowercase
  file path.

  Default:

  Then it checks path keywords in order:
  • hero / splash / landing
      -> 'Hero / Landing Section (Highest visual impact, biggest headline, first impression)'
  • footer
      -> 'Footer (Bottom of page, social links, auxiliary navigation)'
  • header / nav
      -> 'Header / Navigation (Top bar, main navigation routes)'
  • cta / calltoaction / particle
      -> 'Call To Action (Driving the user to sign up, buy, or act NOW)'
  • review / testimonial
      -> 'Social Proof / Reviews (Building trust via testimonials)'
  • feature
      -> 'Features / Services (Explaining what the product/service does in detail)'
  • app.
      -> 'Main Application Shell (Routing, layout stacking, global structure)'
  • main.
      -> 'React Entry Point'

  That roleContext is then injected into the filePrompt:
  • FILE ROLE: ${roleContext}

  Why this matters:
  • It gives the model file-specific intent
  • The same rewrite rules should not apply identically to a hero, footer, and
    testimonial section

  Example:
  • A hero should emphasize first impression and headline impact
  • A footer should focus on auxiliary navigation and completeness
  • A CTA should push conversion urgency

  Developer summary:
  • polishOneFile uses path heuristics to tell the model what job that file plays
    in the site so the rewrite is role-aware, not generic.

23.6 QUESTION 6
What is salvageSingleFileCode for when the model omits <file> tags?
--------------------------------------------------------------------------------

  In parallel mode, each file polish prompt asks the model to wrap output in:
  • <file path="..."> ... </file>

  But models do not always obey perfectly.

  salvageSingleFileCode is the fallback parser for the case where:
  • the model returns raw code
  • but forgets the XML file wrapper

  What salvageSingleFileCode does:
  • reject empty strings
  • reject obvious non-code replies like:
      NO_CHANGES
      sorry / can't / won't
  • strip markdown fences if present
  • accept output only if it looks like source code, e.g. contains:
      import ... from
      export default
      function Name
      const Name =
      class Name

  If salvage succeeds:
  • polishOneFile wraps the salvaged code back into the expected result shape:
      { ok: true, blocks: [{ path: file.path, content: salvaged }] }

  Why this matters:
  • Without salvage, one missing wrapper could cause that file to be skipped
  • The polish engine would lose otherwise-valid code just because formatting was
    slightly wrong

  Developer summary:
  • salvageSingleFileCode is a robustness fallback that rescues valid raw source
    when the model forgets to output the requested <file> wrapper.

23.7 QUESTION 7
What does the monolithic branch do when USE_PARALLEL_POLISH is false?
--------------------------------------------------------------------------------

  If USE_PARALLEL_POLISH is false, the route uses the old whole-codebase mode.

  In that branch:
  • it does not generate a shared design spec for per-file calls
  • it does not run asyncPool over files
  • it sends one large prompt over the entire fileContext

  OpenAI monolithic path:
  • calls generateWithQuality(
      systemPrompt,
      `Perform a Final Polish on the following website files... ${fileContext}`
    )

  Non-OpenAI monolithic path:
  • calls generateText({
      model: getModel(model),
      system: systemPrompt,
      prompt: `Perform a Final Polish on the following website files... ${fileContext}`,
      temperature: 0,
      maxRetries: 7,
      abortSignal
    })

  Then:
  • text = returned full response
  • refinedFiles = parseFileBlocks(text)

  So monolithic mode means:
  • one LLM call for the whole codebase
  • expect many <file> blocks back in one response
  • no per-file retry granularity

  Why the newer parallel mode exists:
  • monolithic mode is slower
  • more context-heavy
  • less resilient when only some files fail formatting

  Developer summary:
  • The monolithic branch is the original all-files-at-once polish implementation
    that produces one big multi-file response instead of many per-file rewrites.

23.9 QUESTION 9
How are missed files retried after the parallel pool finishes?
--------------------------------------------------------------------------------

  After asyncPool completes, the file computes:
  • donePaths = set of polished file paths already produced
  • missed = polishableFiles.filter(f => !donePaths.has(f.path))

  So missed files are:
  • files that never yielded a valid polish result during the first parallel pass

  Then the route performs a sequential retry loop:
  • logs how many missed files exist
  • waits 400ms between retries
  • reruns polishOneFile(file) one by one
  • if successful, pushes the returned blocks into refinedFilesList

  Why sequential retry after parallel pass:
  • the first failure may have been transient
  • serial retries reduce provider pressure
  • gives each missed file one calmer second chance

  The retry does not change the prompt shape.
  It simply reattempts polishOneFile.

  Developer summary:
  • Parallel mode is followed by a sequential cleanup pass for any files that
    failed to produce valid polish output the first time.

23.10 QUESTION 10
What does runPolishStep return to the caller—full file list or only changed files?
--------------------------------------------------------------------------------

  Important answer:
  • runPolishStep returns the full merged file list, not only changed files.

  Here's how:

  First it computes refinedFiles:
  • in parallel mode -> refinedFilesList
  • in monolithic mode -> parseFileBlocks(text)

  If refinedFiles.length === 0:
  • it returns []

  But when refined files do exist:
  • it builds fileMap = new Map(files.map(f => [f.path, f.content]))
  • then overwrites entries in fileMap with each refined file's content
  • then returns:
      Array.from(fileMap.entries()).map(([path, content]) => ({ path, content }))

  That means:
  • unchanged original files remain in the returned array
  • changed refined files replace their old contents in the same array

  So the caller receives:
  • a merged full file set for the scope of the call

  Why return a merged full list:
  • makes downstream writing simpler
  • caller does not need to re-merge changed files against original inputs

  Special return cases:
  • [] means polish produced no modifications
  • null means fatal polish analysis failure and caller should keep existing files untouched

  Developer summary:
  • runPolishStep is a merge-producing function:
    it returns a full file list with refined content patched in, not just a diff list.

23.11 EXTRA polish-refinement.js EXECUTION MAP

  • else:

How does SPA mode differ from MPA mode in terms of router and layout?

  • Useful in sandbox/static-preview environments

24.3 QUESTION 3
What does inferComponentRole do, and why does naming like HeroSplash matter?
--------------------------------------------------------------------------------

  inferComponentRole tries to classify a component into:
  • header
  • hero
  • footer
  • feature

  It uses:
  • explicit role if provided
  • exportName
  • path

  The function builds:
  • text = `${explicitRole} ${name} ${path}`

  Then it checks role rules:
  • explicit role wins if it is header/hero/footer
  • header if name/path text matches header/navbar/navigation/topbar/menu
  • hero if:
      masthead / landing / banner regex matches
      OR name includes hero
      OR name includes splash
      OR name matches patterns like herosplash / videohero
  • footer if name includes footer or text matches copyright/site-footer
  • otherwise feature

  Why naming like `HeroSplash` matters:
  • A simple whole-word regex for `hero` would fail on compound names like
    `HeroSplashCursor` or `VideoHeroBackground`
  • The function explicitly uses substring checks like:
      name.includes('hero')
      name.includes('splash')
      /herosplash|videohero/i
  • That means compound names still classify correctly as hero components

  Why role inference matters:
  • SPA sort order depends on it
  • orphan merge sorting in MPA depends on it
  • header/footer placement in shared layout depends partly on naming

  Developer summary:
  • inferComponentRole is the role-classification heuristic that makes compound
    component names like `HeroSplash...` sort and render correctly as heroes.

24.4 QUESTION 4
How are sharedComponentRefIds applied in MPA—where do header/footer render?
--------------------------------------------------------------------------------

  In MPA mode, sharedComponents are passed directly into renderAppTemplate.

  The function first builds:
  • sharedRefIds = new Set(sharedComponents.map(c => c.refId || c.exportName))

  Then it derives:
  • shared = components.filter(c => sharedRefIds.has(c.refId) || sharedRefIds.has(c.exportName))

  Later it identifies shell chrome:
  • headerComp = shared.find(...)
      role === 'header'
      or exportName includes header/navbar
  • footerComp = shared.find(...)
      role === 'footer'
      or exportName includes footer

  In the final rendered App.jsx:
  • header renders before `<Routes>`
  • footer renders after `</Routes>`

  So the layout becomes:
  • <HashRouter>
      <div className="min-h-screen">
        <Header />
        <Routes>
          page routes
        </Routes>
        <Footer />
      </div>
    </HashRouter>

  Why this matters:
  • shared chrome appears on every page
  • page route elements only render page-specific content sections
  • page components themselves should not include duplicated header/footer

  Relationship to planner data:
  • the planner provides sharedComponentRefIds
  • Generation.jsx turns those ids into actual sharedComponents objects
  • render-app-template uses those shared component objects to place shell layout

  Developer summary:
  • sharedComponentRefIds end up rendering as shared header/footer outside the
    route elements, which is how MPA shared layout is achieved.

24.5 QUESTION 5
What determines sort order of components in a single-page vertical stack?
--------------------------------------------------------------------------------

  In SPA mode, the route:
  • deduplicates components by exportName
  • then sorts the unique list

  Sort order is determined by inferComponentRole with this rank map:
  • header -> 0
  • hero   -> 1
  • feature -> 2
  • footer -> 3

  So SPA rendering order becomes:
  • all header-like components first
  • hero-like next
  • feature/body sections next
  • footer-like last

  Important nuance:
  • Because components are deduplicated first, only one import/render per
    exportName survives in SPA mode

  Why this is useful:
  • Even if the upstream planner order is imperfect, the final App.jsx still gets
    a sane landing-page layout shape

  Developer summary:
  • The SPA vertical stack is deterministically sorted by inferred role:
    header -> hero -> body/features -> footer.

24.7 QUESTION 7
Why is this module intentionally non-LLM—what bugs does it prevent?
--------------------------------------------------------------------------------

  This module is deterministic on purpose.

  Why:
  • App.jsx is one of the highest-risk files for LLM drift
  • Small mistakes in imports, ordering, or routing can break the whole preview

  A deterministic renderer prevents bugs like:
  • missing imports
  • components planned but never rendered
  • duplicated or missing header/footer placement
  • inconsistent route generation
  • broken multi-page shells
  • accidental reordering of sections
  • dead imports for orphan components

  The system already has structured plan data:
  • components
  • pages
  • shared components
  It is much safer to render App.jsx from that structured plan than to ask a
  general LLM to reconstruct it each time.

  This module is especially important because:
  • many other steps are probabilistic / LLM-based
  • App.jsx is better treated as a deterministic assembly problem

  Developer summary:
  • render-app-template is intentionally non-LLM because App.jsx assembly is a
    predictable orchestration task, and determinism prevents a whole class of
    routing/import/layout bugs.

24.8 QUESTION 8
What happens if a refId in pages does not match any component in the plan?

  When building each route, the function maps page.componentRefIds to components:
  • components.find(c => c.refId === refId || c.exportName === refId)

  Then it filters out falsy matches:
  • .filter(Boolean)

  So if a refId does not match any component:
  • that entry is silently dropped from the page's route assembly

  There is also a fallback for the root route:
  • if pageComps.length === 0 and routePath === '/'
      -> dump all non-shared components into the first page

  That means:
  • a bad refId can reduce assigned page content
  • but the root route still has a recovery path to avoid a blank home page

  Developer summary:
  • unmatched refIds are ignored, and root-route fallback logic helps prevent an
    empty home route when assignments are broken.

24.9 QUESTION 9
How does orphan or unused component merging work (if implemented in this file)?
--------------------------------------------------------------------------------

  Yes, this file implements orphan merging explicitly.

  First it builds assignedNames:
  • any component referenced by any page's componentRefIds
  • any component placed in shared layout

  Then it computes orphanSections:
  • any unique component not in assignedNames

  Meaning:
  • these are components that were planned and imported
  • but never mounted in any route or shared shell

  What happens to them:
  • if the current routePath is '/'
  • and orphanSections.length > 0
      -> merge orphan sections into the home page
      -> avoid duplicates with a seen set
      -> sort merged result by role

  Why this exists:
  • A planner may forget to assign some components to page maps
  • Without orphan merging, App.jsx would import those components but never mount
    them
  • That would create dead imports and incomplete landing pages

  The file even explains the intent in comments:
  • Anything in the plan but never mounted in a Route or shell — merge into "/"
    so imports are not dead
  • Home route must show the full landing stack: attach any sections the planner
    forgot to assign

  Developer summary:
  • orphan or unused components are automatically merged into the home route so
    planned sections do not disappear from the final app shell.

25.1 QUESTION 1
Which models run repair first vs fallback, and which helper picks them?
--------------------------------------------------------------------------------

  The repair path uses two model selection helpers from `llm-lightweight.js`:
  • resolveLightweightModel(buildModel)
  • resolveCrossProviderFallback(buildModel)

  First model (primary):
  • primaryId = resolveLightweightModel(buildModel).id

  That means:
  • if buildModel includes `openai/`
      -> primary repair model = `openai/gpt-5.4-mini`
  • if buildModel includes `anthropic/`
      -> primary repair model = `anthropic/claude-haiku-4-5-20251001`
  • otherwise (google/* and default path)
      -> primary repair model = `google/gemini-2.5-flash`

  Fallback model:
  • fallbackId = resolveCrossProviderFallback(buildModel)

  That means:
  • openai heavy model -> fallback `google/gemini-2.5-flash`
  • anthropic heavy model -> fallback `google/gemini-2.5-flash`
  • google heavy model -> fallback `openai/gpt-5.4`
  • anything else -> fallback `google/gemini-2.5-flash`

  Repair attempt order:
  1. Run repair with primaryId
  2. If that throws and fallbackId !== primaryId
      -> try fallbackId

  Important nuance:
  • The fallback is only attempted if the primary repair call throws
  • If the model returns a valid JSON object with `success: false`, that is not a
    provider failure; it is a logical “could not repair” result and does not
    trigger model fallback

  Why lightweight first:
  • Repair should be fast and cheap relative to full generation
  • The task is debugging focused, not open-ended creative generation

  Developer summary:
  • Repair first uses a lightweight same-family model chosen by
    `resolveLightweightModel`, and only falls back to the cross-provider model
    chosen by `resolveCrossProviderFallback` if the first repair call throws.

25.2 QUESTION 2
What is the maximum size of buildErrors and fileContext sent to the model?

  The system prompt explicitly truncates both major context blocks.

  buildErrors:
  • `${buildErrors.substring(0, 3000)}`
  • So the maximum build error log included in the prompt is 3000 characters

  fileContext:
  • The route first builds fileContext from relevant files
  • Then injects:
      `${fileContext.substring(0, 50000)}`
  • So the maximum fileContext passed into the prompt is 50000 characters

  Why these caps exist:
  • Build logs can be huge
  • Whole source trees can exceed useful model context quickly
  • Repair needs enough context to reason, but not unlimited context that causes
    token bloat and slower responses

  So practical prompt sizing here is:
  • up to 3000 chars of error logs
  • up to 50000 chars of source-file context

  Developer summary:
  • Repair sees a truncated but still substantial debugging context:
    3k chars of logs and 50k chars of source content.

25.3 QUESTION 3
What JSON shape must the model return, and what fields are required for success?

  The system prompt tells the model to return a JSON object shaped like:

      "fixedFiles": [
        { "path": "src/App.jsx", "content": "fully rewritten code here..." }
      ]

  It also defines a failure shape:
  • {"success": false, "strategy": "Unfixable Infrastructure Error"}

  For the JavaScript caller to consider the repair successful, all of these must
  be true:
  • result.success is truthy
  • result.fixedFiles exists
  • result.fixedFiles.length > 0

  That logic is explicit in code:
  • if (result.success && result.fixedFiles && result.fixedFiles.length > 0)
      -> return { success: true, fixedFiles, strategy }

  So required-for-success fields are effectively:
  • success: true
  • strategy: useful explanation string
  • fixedFiles: non-empty array

  Each fixedFiles entry must contain:
  • path
  • content

  Why this contract is strict:
  • The caller needs concrete files to write back into the sandbox
  • A “success” without file edits is not actionable

  Developer summary:
  • The repair model must return structured JSON with a non-empty `fixedFiles`
    array, otherwise the repair is treated as unsuccessful even if `success: true`

25.4 QUESTION 4
What multi-page-specific rules are listed in the system prompt (HashRouter,
siteMap, duplicate Router)?
--------------------------------------------------------------------------------

  auto-repair includes a dedicated "MULTI-PAGE SPECIFIC FIXES" section in its
  system prompt.

  These rules are:

  8. Missing page module
  • If error is `Cannot find module './pages/X'`
      -> create the missing page file with a minimal functional default export

  9. Route mismatch
  • If error is `No routes matched location`
      -> check that `siteMap.js` route paths match the Route path props in App.jsx

  10. Duplicate router
  • If error says you cannot render a Router inside another Router
      -> ensure only ONE HashRouter exists in App.jsx
      -> remove any Router from main.jsx or page components

  11. Page components importing chrome directly
  • If page component imports Header/Footer directly
      -> remove those imports
      -> Header and Footer should render in App.jsx outside the Routes block

  12. Router hooks outside router tree
  • If useLocation/useNavigate is outside Router
      -> ensure those hooks are only used inside components rendered within the
         HashRouter tree

  Why this matters:
  • Multipage failures often have different failure modes than single-page builds
  • A generic JSX repair prompt might miss these router-specific architecture rules

  Developer summary:
  • The repair prompt includes explicit MPA-specific guidance around HashRouter,
    `siteMap.js`, duplicate router nesting, shared header/footer ownership, and
    router hook placement.

--------------------------------------------------------------------------------
25.5 QUESTION 5
Why strip markdown fences from the model’s response before JSON.parse?
--------------------------------------------------------------------------------

  The repair code does:
  • let jsonText = text.trim()
  • if (jsonText.startsWith('```'))
      -> remove leading ```json / ``` and trailing ```
  • then JSON.parse(jsonText)

  Why:
  • Even though the prompt says "Output ONLY valid JSON, no markdown blocks,"
    models sometimes still wrap JSON in markdown fences

  Without stripping fences:
  • JSON.parse would fail immediately

  So this is a tolerance layer for minor formatting noncompliance.

  It does NOT mean markdown is desired.
  It means the caller is robust to a common model mistake.

  Developer summary:
  • Markdown fences are stripped because the model may disobey formatting rules,
    and valid JSON inside ```json fences should still be recoverable.

--------------------------------------------------------------------------------
25.6 QUESTION 6
What happens if success is true but fixedFiles is empty?
--------------------------------------------------------------------------------

  The code only treats the result as truly successful if:
  • success is true
  • fixedFiles exists
  • fixedFiles.length > 0

  If `success: true` but fixedFiles is empty or missing:
  • the route does NOT return a success object to the caller
  • it falls through to:
      return { success: false, strategy: result.strategy || 'LLM could not resolve issue' }

  So a success-with-no-files is downgraded to failure.

  Why this is important:
  • The caller has nothing to apply
  • There is no actionable repair patch
  • Treating that as success would falsely imply the build can move forward

  Developer summary:
  • `success: true` is not enough by itself; an empty `fixedFiles` array still
    results in the repair being treated as unsuccessful.

--------------------------------------------------------------------------------
25.7 QUESTION 7
Which files are filtered into fileContext—only src/?
--------------------------------------------------------------------------------

  Yes, fileContext is built only from files whose path starts with `src/`.

  The code does:
  • files.filter(f => f.path.startsWith('src/'))

  Then for each such file, it formats:
  • --- ${f.path} ---
    ${f.content}
    -------------------

  So repair context excludes:
  • root config files
  • node_modules
  • other non-src files

  Why this is reasonable:
  • Most build errors the repair engine is expected to fix live in application
    source files
  • Sending fewer irrelevant files keeps the prompt smaller and more focused

  Important nuance:
  • The caller (`apply-ai-code-stream.js`) may first merge in additional existing
    sandbox `src/` files that were not in the original apply batch
  • But the repair function itself still filters final prompt context down to
    `src/` files only

  Developer summary:
  • Yes, the repair prompt only includes `src/` files, even if the caller passed
    a larger set of sandbox files.

--------------------------------------------------------------------------------
25.8 QUESTION 8
How does previousRepairs / repairLog prevent repeating failed strategies?
--------------------------------------------------------------------------------

  attemptRepair receives:
  • repairLog = []
    by default
  • or a real accumulated repair log from the caller

  It converts that into previousRepairs text:
  • PREVIOUS EXPERIMENT LOG:
      Attempt 1: ...
      Attempt 2: ...
    DO NOT REPEAT THESE STRATEGIES.

  So repairLog acts as memory for the LLM.

  What the caller stores in repairLog:
  • successful repair attempts:
      strategy
      fixedFiles paths
  • failed attempts:
      strategy: 'Failed to formulate fix'
      or thrown exception info

  This means each later attempt can see:
  • what strategy already failed
  • what not to keep trying

  Why this matters:
  • Repair loops can otherwise get stuck repeating the same wrong fix idea
  • Explicit memory nudges the model toward alternative hypotheses

  Developer summary:
  • `repairLog` is converted into a “do not repeat these strategies” block inside
    the repair prompt, helping later attempts avoid looping on the same failed idea.

--------------------------------------------------------------------------------
25.9 QUESTION 9
What temperature is used, and why keep it low?
--------------------------------------------------------------------------------

  The repair generation call uses:
  • temperature: 0.2

  Why low temperature makes sense for repair:
  • repair is a debugging task, not a creative generation task
  • consistency and precision matter more than novelty
  • lower temperature reduces wandering or overly inventive fixes

  Given the prompt's requirements:
  • fix syntax precisely
  • do not invent unavailable imports
  • return valid JSON only
  • respect router/layout constraints

  A conservative temperature is exactly what you want.

  Developer summary:
  • Repair uses a low temperature because the goal is deterministic debugging,
    not creative exploration.

--------------------------------------------------------------------------------
25.10 QUESTION 10
Who calls attemptRepair, and what does the caller do with fixedFiles?
--------------------------------------------------------------------------------

  The main caller is:
  • web/server/routes/apply-ai-code-stream.js

  It calls attemptRepair inside the auto-repair loop after verification fails.

  What the caller passes in:
  • files: repairFiles
  • buildErrors: buildLogs
  • repairLog
  • buildModel: buildModelId

  What `repairFiles` contains:
  • the current apply batch
  • plus any additional existing sandbox src files merged in for context

  What the caller does if repairRes.success is true:
  1. Appends strategy/fixedFiles info to repairLog
  2. Updates the build manifest
  3. Emits SSE REPAIR_STARTED
  4. Emits AI narrator repair message
  5. Writes each fixed file directly back into the sandbox
  6. Updates local `sortedFiles` content so future repair attempts see latest code
  7. Re-runs verifySandboxBuild
  8. If verify passes:
      emits VERIFY_PASSED
      emits REPAIR_DONE
      emits narrator repair_success message
      exits repair loop
  9. If verify fails:
      keeps looping with updated buildLogs until attempts exhausted

  What the caller does if repairRes.success is false:
  • logs the failure
  • records failure strategy into repairLog
  • breaks out or continues according to route logic

  Developer summary:
  • `attemptRepair` is called by the apply route after verification failures, and
    the caller immediately writes `fixedFiles` into the sandbox and re-verifies the build.

--------------------------------------------------------------------------------
25.11 EXTRA auto-repair.js EXECUTION MAP
--------------------------------------------------------------------------------

  Repair flow:
  • derive primary and fallback repair model ids
  • filter files down to src/
  • truncate buildErrors and fileContext
  • build previousRepairs memory block
  • build debugging system prompt
  • runRepairWithModel(primary)
  • if thrown and fallback differs -> runRepairWithModel(fallback)
  • strip markdown fences if present
  • JSON.parse result
  • require success + non-empty fixedFiles for real success
  • otherwise return structured failure object

--------------------------------------------------------------------------------
25.12 EXTRA RETURN CONTRACT SUMMARY
--------------------------------------------------------------------------------

  attemptRepair returns one of:
  • { success: true, fixedFiles, strategy }
  • { success: false, strategy }

  It does not:
  • write files
  • verify build
  • emit SSE
  • manage retry loop count

  Those are all caller responsibilities in apply-ai-code-stream.js.

26. DEEP DIVE: enhance-prompt.js REFERENCE
================================================================================

  This chapter covers:
    web/server/routes/enhance-prompt.js

  Purpose of the file:
  • This is the prompt enrichment route that runs near the beginning of the full
    builder pipeline.
  • Its job is not to generate code.
  • Its job is to transform a vague user brief into a richer creative website
    specification that later planner/generator routes can use more effectively.
  • It also performs one highly important deterministic step:
      extracting explicitly named component references from the raw user prompt

  Important imports:
  • generateText
  • getModel
  • log
  • llmLog

  Main export:
  • default async function enhancePrompt(req, res)

  Important local function:
  • extractExplicitComponentNames(rawPrompt)

--------------------------------------------------------------------------------
26.1 HIGH-LEVEL RESPONSIBILITY
--------------------------------------------------------------------------------

  This file has a two-stage design:

  Stage 1:
  • Deterministically parse the raw prompt for named component references
  • This is NOT delegated to the LLM

  Stage 2:
  • Ask a fast model to expand the prompt into a premium website specification
  • Then append the deterministic component marker back onto the enhanced text

  So the final enhanced prompt is usually:
  • LLM-written strategic design specification
  • plus a machine-appended `EXPLICIT_COMPONENTS: [...]` suffix when applicable

--------------------------------------------------------------------------------
26.2 DETERMINISTIC COMPONENT EXTRACTION
--------------------------------------------------------------------------------

  The helper `extractExplicitComponentNames(rawPrompt)` exists because the system
  does not trust the LLM to reliably preserve exact named component references.

  It uses two detection strategies:

  Pattern family 1:
  • user phrases like:
      use the XYZ component
      include XYZ component
      add XYZ section
      incorporate XYZ from the community

  Those regexes are intentionally bounded:
  • component names can be PascalCase or capitalized word groups
  • maximum of 4 words
  • this was hardened specifically to avoid ReDoS issues from dangerous nested
    quantifiers

  Pattern family 2:
  • PascalCase compound words
  • examples:
      VortexNeonPricing
      HeroBeams
      HeroSplashCursor

  Filtering behavior:
  • removes obvious generic words like:
      The
      This
      That
      React
      Tailwind
      Vite
  • excludes some common non-component PascalCase app-ish names like:
      LandingPage
      WebApp
      WebSite
      HomePage
      ReactApp

  Final output:
  • returns a de-duplicated array of extracted names

  Why this is important:
  • It gives later routes a stable, deterministic marker for explicit component
    intent
  • This survives enhancement even if the enhancement model paraphrases heavily

--------------------------------------------------------------------------------
26.3 MODEL ROUTING
--------------------------------------------------------------------------------

  This route intentionally does not use the full heavy generation model by default.

  Default enhance model:
  • google/gemini-2.5-flash

  Provider-family mapping:
  • if incoming model includes `openai/`
      -> ENHANCE_MODEL = openai/gpt-5.4-mini
  • else if incoming model includes `anthropic/`
      -> ENHANCE_MODEL = anthropic/claude-haiku-4-5-20251001
  • else
      -> ENHANCE_MODEL remains google/gemini-2.5-flash

  Why this routing exists:
  • prompt enhancement is a support step, not the main creative heavy-lift
  • using a lightweight model reduces cost and latency
  • it also reduces RPM collisions with heavy models like Gemini Pro / Sonnet

  Developer summary:
  • This route uses a fast/cheap same-family model rather than the user's full
    heavy build model whenever possible.

--------------------------------------------------------------------------------
26.4 SYSTEM PROMPT PURPOSE
--------------------------------------------------------------------------------

  The system prompt frames the model as:
  • a senior UX strategist at a top-tier design agency
  • transforming vague client briefs into detailed creative specs that win
    Awwwards

  What it asks for:
  • analyze the business / niche first
  • identify target audience
  • identify emotional goal
  • produce industry-specific copy
  • specify color/typography/layout/animation direction
  • include section-by-section direction
  • output 250-500 words
  • use markdown headers
  • avoid generic branding
  • mention explicitly named UI components naturally if the user named any

  So this route is not trying to produce code.
  It is producing a high-quality planning brief for downstream AI routes.

--------------------------------------------------------------------------------
26.5 USER PROMPT & MULTIMODAL CONTENT
--------------------------------------------------------------------------------

  The user-facing task string is:
  • ORIGINAL REQUEST:
    <raw prompt>
    Transform this into a premium website specification...

  The route then builds a multimodal `content` array:
  • first element is text
  • remaining elements are images if provided

  For images:
  • base64 data is extracted
  • mime type is inferred from data URL or object metadata

  That means the enhancement model can use:
  • raw textual brief
  • visual references

--------------------------------------------------------------------------------
26.6 TIMEOUT & RELIABILITY POLICY
--------------------------------------------------------------------------------

  The route uses a hard timeout:
  • TIMEOUT_MS = 15000

  It sets:
  • AbortController
  • setTimeout(() => controller.abort(), TIMEOUT_MS)

  Why:
  • This route is not allowed to block the whole pipeline
  • Enhancement is useful, but not critical enough to halt the builder if the
    provider is slow

  The AI call itself uses:
  • generateText
  • model: getModel(ENHANCE_MODEL)
  • system: systemPrompt
  • messages: [{ role: 'user', content }]
  • maxTokens: 800
  • abortSignal: controller.signal

  Logging:
  • llmLog.request('ENHANCE', ...)
  • llmLog.response('ENHANCE', ...)
  • llmLog.error('ENHANCE', ...)

--------------------------------------------------------------------------------
26.7 OUTPUT CONTRACT
--------------------------------------------------------------------------------

  Successful enhanced output path:
  • If the model returns non-empty text:
      finalOutput = enhancedPrompt.trim()
      if explicitComponents exist:
          append `EXPLICIT_COMPONENTS: [A, B, C]`
      return:
        {
          success: true,
          enhancedPrompt: finalOutput,
          wasEnhanced: true
        }

  Empty enhancement response path:
  • If enhancedPrompt is empty/whitespace:
      return:
        {
          success: true,
          enhancedPrompt: original prompt,
          wasEnhanced: false
        }

  Error path:
  • Even on timeout / rate limit / other error:
      return:
        {
          success: true,
          enhancedPrompt: original prompt,
          wasEnhanced: false
        }

  This is a key design decision:
  • the route never intentionally blocks the main website pipeline

--------------------------------------------------------------------------------
26.8 WHY THE EXPLICIT_COMPONENTS TAG IS APPENDED AFTER THE LLM
--------------------------------------------------------------------------------

  The file does NOT ask the LLM to produce the EXPLICIT_COMPONENTS tag.
  It always appends it deterministically after the enhancement call.

  Why:
  • the enhancement model may paraphrase or drop exact component names
  • later routes need a stable machine-readable marker
  • deterministic append guarantees consistency

  Exact format:
  • EXPLICIT_COMPONENTS: [NameA, NameB, NameC]

  This format is later consumed by:
  • select-components.js
  • select-components-v2.js
  • plan-website-components.js
  • polish/refinement flows strip it back out when it is metadata rather than
    vision text

--------------------------------------------------------------------------------
26.9 FAILURE HANDLING PHILOSOPHY
--------------------------------------------------------------------------------

  The catch block intentionally degrades gracefully.

  It distinguishes:
  • AbortError / aborted timeout
  • rate limit / overload style failures
  • other generic errors

  But regardless of error type, the route still returns:
  • success: true
  • enhancedPrompt: original prompt
  • wasEnhanced: false

  Why:
  • enhancement is optional value-add
  • code generation, planning, and apply should still continue
  • the product would rather lose enrichment than lose the entire build

--------------------------------------------------------------------------------
26.10 RELATIONSHIP TO THE REST OF THE BUILDER
--------------------------------------------------------------------------------

  Upstream:
  • receives raw user prompt and optional image references

  Downstream:
  • Generation.jsx uses enhanced prompt as `finalPrompt`
  • derive-design-system reads the richer enhancement output
  • selection/planning routes may parse the appended EXPLICIT_COMPONENTS tag

  So this route acts as:
  • semantic enrichment layer
  • explicit component intent preservation layer

--------------------------------------------------------------------------------
26.11 EXECUTION MAP
--------------------------------------------------------------------------------

  Full route flow:
  • validate prompt
  • choose ENHANCE_MODEL based on incoming provider family
  • deterministically extract explicit component names from raw prompt
  • build systemPrompt
  • build userPrompt
  • convert prompt + images into multimodal content array
  • run generateText with hard 15s timeout
  • if response empty -> return original prompt
  • else append EXPLICIT_COMPONENTS tag if needed
  • return enhancedPrompt
  • on any failure -> return original prompt, wasEnhanced:false

--------------------------------------------------------------------------------
26.12 WHY THIS FILE IS IMPORTANT
--------------------------------------------------------------------------------

  Even though it is not a codegen file, it strongly influences quality because it:
  • enriches vague prompts into actionable creative specs
  • gives later planner/generator routes better copy direction
  • preserves explicit component names deterministically
  • never blocks the rest of the system when enhancement fails

  State it keeps:
  • res
  • onHeartbeat callback
  • lastPing timestamp
  • keepaliveInterval

  Core methods:
  • send(eventType, payload = {})
  • aiMessage(message, context = {}, style = 'casual')
  • aiThinking(stage = 'analyzing')
  • aiThought(thought)
  • startKeepalive()
  • end()

--------------------------------------------------------------------------------
28.5 HOW send() WRITES EVENTS
--------------------------------------------------------------------------------

  `send(eventType, payload)` builds a data object like:
  • {
      event: eventType,
      timestamp: Date.now(),
      ...payload
    }

  Then it writes:
  • `event: <eventType>`
  • `data: <json>`
  • blank line

  Important design choice:
  • The event name is sent both as the SSE `event:` line and inside the JSON data
    object as `event`

  Why that helps:
  • compatibility with different SSE consumers
  • frontend code can read event type either from transport metadata or parsed JSON

  Error behavior:
  • if response writing fails, it logs `[SSEWriter] Send failed`
  • it does not throw out to the caller here

--------------------------------------------------------------------------------
28.6 AI HELPER METHODS
--------------------------------------------------------------------------------

  `aiMessage(message, context, style)`:
  • wraps `send(SSE_EVENTS.AI_MESSAGE, ...)`
  • used for natural-language narration updates

  `aiThinking(stage)`:
  • wraps `send(SSE_EVENTS.AI_THINKING, { stage })`
  • used to tell the UI the AI is reasoning about a phase

  `aiThought(thought)`:
  • wraps `send(SSE_EVENTS.AI_THOUGHT, { thought })`
  • meant for internal-thought style messages if ever surfaced

  Why these helpers exist:
  • routes do not need to manually build AI-event payloads each time
  • they standardize conversational event emission

--------------------------------------------------------------------------------
28.7 KEEPALIVE / HEARTBEAT BEHAVIOR
--------------------------------------------------------------------------------

  `startKeepalive()` starts an interval every 15 seconds.

  Logic:
  • if Date.now() - lastPing > 15000
      -> write `: keepalive`
      -> update lastPing
      -> call onHeartbeat callback if provided

  Why this matters:
  • long-running SSE requests can appear idle
  • keepalive prevents some proxies/clients from considering the stream dead
  • the onHeartbeat callback allows the caller to keep the sandbox alive too

  Example caller use:
  • `apply-ai-code-stream.js` passes a heartbeat callback that calls provider.keepAlive()

  So this file supports both:
  • SSE transport longevity
  • sandbox session longevity

--------------------------------------------------------------------------------
28.8 end() BEHAVIOR
--------------------------------------------------------------------------------

  `end()`:
  • clears keepalive interval if it exists
  • tries to end the response
  • ignores errors if response is already closed

  Why centralizing this matters:
  • long-running SSE routes need consistent cleanup
  • prevents dangling keepalive intervals

--------------------------------------------------------------------------------
28.9 AIBuildNarrator — WHAT IT IS
--------------------------------------------------------------------------------

  `AIBuildNarrator` is the conversational narrator for the build pipeline.

  It is not:
  • a technical event emitter
  • a code generator

  It is:
  • a small language generation layer that turns build stages into short natural
    language progress messages

  Constructor notes:
  • narration uses the same lightweight routing strategy as polish fillers
  • it is keyed off the user's selected build model family

  Main method:
  • narrate(stage, context = {}, options = {})

  Fallback method:
  • getFallbackMessage(stage, context)

--------------------------------------------------------------------------------
28.10 HOW narrate() CHOOSES MODELS
--------------------------------------------------------------------------------

  narrate() takes:
  • stage
  • context
  • options.buildModelId

  It computes:
  • buildModelId = options.buildModelId || 'google/gemini-3.1-pro-preview'
  • lm = resolveLightweightModel(buildModelId)

  So narrator model routing follows the heavy build model family:
  • OpenAI build -> gpt-5.4-mini via `generateFast`
  • Anthropic build -> claude-haiku via `generateText`
  • Google build -> gemini-2.5-flash via `generateText`

  Why lightweight models:
  • narration should be cheap
  • narration should be fast
  • narration should not compete heavily with main codegen budget

--------------------------------------------------------------------------------
28.11 NARRATOR STAGES

  • planning
  • thinking
  • installing

  • building

  • polish_success
  • rollback
  • complete

  What these do:
  • They transform structured stage/context data into a small natural language
    writing task
  • Example:
      planning prompt includes the user request and component count
      installing prompt includes dependency names
      complete prompt includes file count and asks for an enthusiastic summary

  So the AI narrator is effectively a:
  • stage-aware microcopy generator

--------------------------------------------------------------------------------
28.12 NARRATOR SYSTEM PROMPT
--------------------------------------------------------------------------------

  • You are the Volturiano Builder AI...

--------------------------------------------------------------------------------
28.13 FAST VS STANDARD PATH INSIDE narrate()

  If lm.useFast is true:

  • OpenAI uses the native fast Responses API wrapper

--------------------------------------------------------------------------------
28.14 FALLBACK MESSAGE BEHAVIOR

  • installing -> `Installing N dependencies...`
  • applying -> `Applying N files...`
  • building -> `Building ComponentName...`

  • repairing -> `Auto-repairing build issues...`

  • polish_success -> `Polish complete — your preview is ready.`
  • complete -> `Your project is ready with N files!`

  Why this matters:
  • narration is nice-to-have, not allowed to break the stream

    model fails

28.16 WHY THIS FILE MATTERS

29. DEEP DIVE: mini-polish-refinement.js REFERENCE
================================================================================

  This chapter covers:
    web/server/lib/mini-polish-refinement.js

  Purpose of the file:
  • This is the lightweight post-polish reliability pass.
  • It runs after the heavy polish stage in apply-ai-code-stream.js.
  • It is intentionally conservative:
      prefer no edits
      only fix obvious UX / route / navigation / image / hygiene issues
      avoid broad rewrites

  Important imports:
  • generateText
  • getModel
  • generateFast
  • parseFileBlocks
  • llmLog
  • resolveLightweightModel

  Main export:
  • runMiniPolishStep(files, prompt, options)

--------------------------------------------------------------------------------
29.1 HIGH-LEVEL ROLE
--------------------------------------------------------------------------------

  This file is not a second heavy polish engine.
  It is a quick safety-and-sanity pass after heavy polish already ran.

  The opening file comment says it clearly:
  • single fast-model pass after main polish
  • navigation, routes, UX sanity
  • intentionally conservative
  • NO_CHANGES means zero file writes

  So its job is:
  • not to restyle the whole site
  • but to catch final reliability defects that are small enough to fix surgically

--------------------------------------------------------------------------------
29.2 MODEL ROUTING
--------------------------------------------------------------------------------

  This file uses `resolveLightweightModel(heavyModel)`.

  That means:
  • OpenAI heavy build -> openai/gpt-5.4-mini, useFast: true
  • Anthropic heavy build -> anthropic/claude-haiku-4-5-20251001
  • Google heavy build -> google/gemini-2.5-flash

  So mini polish always uses the lightweight companion model family, not the
  original heavy generation model.

  Why:
  • this is a quick QA pass
  • it should be cheaper and faster than heavy polish

  OpenAI path:
  • uses generateFast(system, userPrompt)

  Non-OpenAI path:
  • uses generateText({
      model: getModel(lm.id),
      system,
      prompt: userPrompt,
      temperature: 0,
      maxRetries: 2,
      maxTokens: 16384,
      abortSignal
    })

--------------------------------------------------------------------------------
29.3 TIMEOUT AND CONTEXT LIMITS
--------------------------------------------------------------------------------

  Timeout:
  • MINI_POLISH_TIMEOUT_MS = 180000
  • so mini polish gets up to 180s before abort

  Context limit:
  • MAX_TOTAL_CONTEXT_CHARS = 220000

  That cap is enforced in buildBoundedFileContext(files):
  • it accumulates file headers + file content
  • if a file would exceed remaining room:
      the file body is truncated and marked
  • if no room remains:
      it emits a truncated marker and stops

  Why this matters:
  • the route can inspect many files
  • but it still bounds the total prompt size so the request stays manageable

--------------------------------------------------------------------------------
29.4 SYSTEM PROMPT PURPOSE
--------------------------------------------------------------------------------

  The SYSTEM_PROMPT frames the model as:
  • a senior React (Vite + Tailwind) release QA engineer

  It injects:
  • the user vision into `{{VISION}}`

  It explicitly says:
  • this is a single reliability pass after heavy final polish
  • default: make NO edits
  • prefer small, surgical diffs
  • do not refactor for style
  • do not rename files
  • if everything is acceptable, respond exactly with `NO_CHANGES`
  • if changes are needed, output only modified files as `<file path="...">` blocks

  So unlike heavy polish, this prompt is fundamentally:
  • conservative
  • defect-oriented
  • low-surface-area

--------------------------------------------------------------------------------
29.5 WHAT IT CHECKS
--------------------------------------------------------------------------------

  The prompt gives a checklist of things worth fixing:

  1. Routes & navigation
  • nav links should point to real routes with real content
  • empty pages with advertised nav should be fixed or hidden
  • missing route targets should be repaired in the smallest consistent way

  2. Duplicate chrome
  • duplicate navbars / headers / footers should be removed

  3. Landing / hero copy
  • hero should have readable title, subtitle, and non-placeholder hero image
  • do not redesign backgrounds/shaders/WebGL

  4. Layout sanity
  • sticky/fixed issues
  • z-index problems covering content
  • but do not rewrite animation/shader code

  5. Images
  • fix empty src
  • fix literal placeholder URLs
  • fix empty alt on important hero images when obvious

  6. Build hygiene
  • keep lucide-react imports valid
  • do not add new dependencies

  So mini polish is basically:
  • route sanity
  • shell duplication cleanup
  • obvious hero/image cleanup
  • final hygiene

--------------------------------------------------------------------------------
29.6 INPUT PREPARATION
--------------------------------------------------------------------------------

  `runMiniPolishStep(files, prompt, options)` takes:
  • files
  • prompt
  • options.model (heavy model id)
  • options.fileTree
  • options.sandboxId

  It derives:
  • visionPrompt = prompt with `[EXPLICIT_COMPONENTS: ...]` metadata stripped out
  • fileTreeContext = a readable list of current sandbox file paths
  • fileContext = bounded file content string from buildBoundedFileContext(files)

  Then it builds the final userPrompt:
  • SANDBOX FILE TREE
  • PROJECT FILES (full stack context)
  • instruction to respond with NO_CHANGES or `<file path="...">` blocks only

--------------------------------------------------------------------------------
29.7 PATH NORMALIZATION HELPERS
--------------------------------------------------------------------------------

  This file contains two path helpers:

  normalizePathToken(str)
  • lowercases and removes all non-alphanumeric chars

  resolveKnownPath(modelPath, knownPaths)
  • exact match first
  • then normalized full-path match
  • then normalized basename match if unique

  Why this exists:
  • the model may output a slightly wrong path
  • examples:
      wrong casing
      minor punctuation differences
      slightly altered full path but same basename

  So after parseFileBlocks, the route tries to resolve model-emitted paths back
  to real known files.

--------------------------------------------------------------------------------
29.8 NO_CHANGES CONTRACT
--------------------------------------------------------------------------------

  The route treats these as "no changes":
  • exact NO_CHANGES response
  • empty response
  • parsed output with zero `<file>` blocks

  In all those cases:
  • it returns []

  It also logs:
  • NO_CHANGES (or empty) — skipping writes
  • or
  • No <file> blocks parsed — treating as no changes

  This is a very important contract because apply-ai-code-stream.js interprets:
  • [] as "mini polish ran but there is nothing to write"

  So mini polish success is not measured by changing files.
  Success can also mean "the site is already good enough."

--------------------------------------------------------------------------------
29.9 PARSING AND MERGING MODEL OUTPUT
--------------------------------------------------------------------------------

  If the response is not NO_CHANGES:
  • parseFileBlocks(trimmed) is used

  Then for each parsed file:
  • if the exact path exists in original files -> use it
  • else try resolveKnownPath(path, knownPaths)
  • if resolved:
      push normalized file into merged list
  • else:
      ignore the unknown path

  Important nuance:
  • unlike heavy polish, mini polish returns only the files to apply, not a full
    merged file set

  Specifically, the function returns:
  • merged
    where merged contains only normalized changed files from the model output

  This differs from heavy polish's `runPolishStep`, which merges polished files
  back into the original input file list before returning.

--------------------------------------------------------------------------------
29.10 RETURN CONTRACT
--------------------------------------------------------------------------------

  runMiniPolishStep can return three kinds of values:

  1. []
  • means no changes
  • NO_CHANGES
  • empty response
  • no valid file blocks

  2. Array<{path, content}>
  • means mini polish produced specific changed files to apply

  3. null
  • means hard failure
  • caught exception
  • timeout
  • model/provider failure severe enough that the caller should treat mini polish
    as failed rather than as "no changes"

  This matters because apply-ai-code-stream.js handles these differently:
  • [] -> nothing to write
  • array -> write files, then verify
  • null -> skip because mini polish errored

--------------------------------------------------------------------------------
29.11 RELATIONSHIP TO apply-ai-code-stream.js
--------------------------------------------------------------------------------

  apply-ai-code-stream.js calls runMiniPolishStep only after heavy polish is
  still in a green build state.

  Caller behavior:
  • if miniResult && miniResult.length > 0
      -> write mini-polish files
      -> verify build
      -> if mini polish broke build:
           revert only those mini-polish files using preMini
           re-verify

  So mini polish has its own safety net:
  • it is verified
  • and its specific changed files are reversible

  That means mini polish is:
  • conservative by prompt
  • lightweight by model choice
  • additionally protected by caller-side verification and revert logic

--------------------------------------------------------------------------------
29.12 WHY THIS FILE MATTERS
--------------------------------------------------------------------------------

  This file matters because it provides a final low-cost sanity sweep that can:
  • catch route/navigation mismatches
  • remove duplicate chrome
  • clean obvious hero/image defects
  • avoid the expense and risk of running another heavy creative polish pass

  It is one of the last quality gates before the preview is declared ready.

--------------------------------------------------------------------------------
29.13 EXECUTION MAP
--------------------------------------------------------------------------------

  runMiniPolishStep flow:
  • strip EXPLICIT_COMPONENTS metadata from prompt
  • choose lightweight model from heavy model family
  • build bounded file context
  • build system prompt + user prompt
  • call generateFast or generateText
  • if NO_CHANGES or empty -> return []
  • parse `<file>` blocks
  • normalize model paths to known real paths
  • return changed-file array
  • on hard failure -> return null

--------------------------------------------------------------------------------
29.14 SUMMARY
--------------------------------------------------------------------------------

  `mini-polish-refinement.js` is the builder's final lightweight QA sweep.
  It is deliberately:
  • fast
  • conservative
  • bounded
  • path-normalizing
  • tolerant of no-op outputs

30. DEEP DIVE: polish-filler.js REFERENCE
================================================================================

  This chapter covers:
    web/server/lib/polish-filler.js

  Purpose of the file:
  • This file generates lightweight interim narration messages while the heavy
    polish LLM call is still running.
  • It is a UX layer only.
  • It does not modify code, files, or build state.
  • It exists to make long polish waits feel alive and intentional instead of
    silent.

  Main export:
  • runPolishFillers({ model, prompt, onMessage, cancelToken })

  Important helpers:
  • buildFillerPrompt
  • generateFillerMessage

--------------------------------------------------------------------------------
30.1 HIGH-LEVEL ROLE
--------------------------------------------------------------------------------

  polish-filler runs alongside heavy polish, not instead of it.

  The intended pairing is:
  • heavy runPolishStep() does the real file refinement
  • runPolishFillers() emits occasional human-feeling progress messages while the
    user waits

  The file comment makes this explicit:
  • async interim message generator
  • fires lightweight context-aware messages every 25-35 seconds
  • completely independent from the polish execution

  The actual timing code later was widened, and now the intervals are more like:
  • roughly 47s - 72s with anti-periodic variation

  So conceptually:
  • it is a slow, sparse, premium-feeling filler system
  • not a spinner-like rapid heartbeat

--------------------------------------------------------------------------------
30.2 MODEL ROUTING
--------------------------------------------------------------------------------

  This file uses `resolveLightweightModel(model)`.

  So the selected heavy build model is transformed into a lightweight companion:
  • google/*    -> google/gemini-2.5-flash
  • openai/*    -> openai/gpt-5.4-mini via generateFast
  • anthropic/* -> anthropic/claude-haiku-4-5-20251001

  Why:
  • filler messages should be cheap
  • filler messages should be fast
  • filler messages should not compete with the expensive heavy polish model

  OpenAI path:
  • uses generateFast with a short system prompt

  Anthropic/Google path:
  • uses generateText with maxTokens: 80 and temperature: 0.85

--------------------------------------------------------------------------------
30.3 FILLER ANGLES
--------------------------------------------------------------------------------

  The file defines four rotating angle categories:
  • contextual_progress
  • design_attention
  • near_completion
  • final_moments

  What they mean:
  • contextual_progress
      talk about what is actively being refined in the content
  • design_attention
      talk about a specific visual/craft detail being calibrated
  • near_completion
      subtly promise the quality will be worth the wait
  • final_moments
      one brief calm sentence suggesting the work is nearly done

  Why these angles matter:
  • They stop filler messages from sounding repetitive
  • They make the polish wait feel like a real craft process rather than a loader

--------------------------------------------------------------------------------
30.4 buildFillerPrompt()
--------------------------------------------------------------------------------

  buildFillerPrompt(prompt, angleIndex, previousMessages) constructs the actual
  filler instruction sent to the model.

  It includes:
  • the user's website vision
  • explanation that files are already written
  • explanation that AI is in the final personalization phase
  • angle-specific task instructions
  • strict style rules
  • previous messages context to avoid repetition

  Key strict rules in the filler prompt:
  • max 1-2 sentences
  • no emojis
  • no markdown
  • do not say "I'm working on..."
  • do not say "I am..."
  • do not use the phrase "final polish"
  • do not sound like a loading spinner
  • sound casual but premium, like a thoughtful senior engineer

  Why previousMessages is included:
  • It explicitly tells the model not to repeat themes or phrases already sent

--------------------------------------------------------------------------------
30.5 generateFillerMessage()
--------------------------------------------------------------------------------

  This helper does one filler-model call.

  Inputs:
  • modelInfo
  • fillerPrompt

  Logging:
  • llmLog.request('POLISH-FILLER', ...)
  • llmLog.response('POLISH-FILLER', ...)
  • llmLog.error('POLISH-FILLER', ...)

  Generation behavior:
  • if useFast -> generateFast(systemPrompt, fillerPrompt)
  • else -> generateText({ model, prompt, maxTokens: 80, temperature: 0.85 })

  Why temperature is higher here:
  • filler messages benefit from slight natural variation
  • unlike repair or schemas, this is expressive microcopy

  Error behavior:
  • any filler-model failure is non-fatal
  • returns null
  • polish itself is unaffected

--------------------------------------------------------------------------------
30.6 TIMING STRATEGY
--------------------------------------------------------------------------------

  runPolishFillers uses a timing strategy that intentionally avoids periodic
  heartbeat-like rhythm.

  Important constants / behavior:
  • range is 47s to 72s
  • mid point is used to push the next interval away from the previous one if too
    similar
  • MAX_FILLERS = 6

  Why:
  • periodic filler messages would feel mechanical
  • the anti-periodic logic helps the sequence feel more organic

  The loop:
  • wait first random delay
  • while not cancelled and under MAX_FILLERS:
      build prompt
      generate filler
      if message exists:
          onMessage(message)
      increment angle index
      wait next delay

--------------------------------------------------------------------------------
30.7 CANCELLATION MODEL
--------------------------------------------------------------------------------

  The function accepts:
  • cancelToken = { cancelled: false }

  This is a mutable object shared with the caller.

  Behavior:
  • the filler loop checks cancelToken before each iteration
  • it also checks again immediately after awaiting the model call

  Why the second check matters:
  • heavy polish may finish while a filler message is still being generated
  • in that case the route should not emit a stale filler message afterward

  So cancellation is cooperative and carefully timed.

--------------------------------------------------------------------------------
30.8 RELATIONSHIP TO apply-ai-code-stream.js
--------------------------------------------------------------------------------

  apply-ai-code-stream.js does:
  • create polishCancelToken = { cancelled: false }
  • start runPolishFillers(...)
  • start heavy polish
  • in finally:
      polishCancelToken.cancelled = true

  That means:
  • filler messages are strictly tied to the active heavy polish wait window
  • they are not a general background chatter system

--------------------------------------------------------------------------------
30.9 WHY THIS FILE MATTERS
--------------------------------------------------------------------------------

  This file matters because:
  • polish can take a while
  • silence feels broken
  • cheap, context-aware narration improves perceived responsiveness without
    changing the actual build process

  It is a good example of:
  • low-cost UX enhancement
  • decoupled from core code execution

--------------------------------------------------------------------------------
30.10 SUMMARY
--------------------------------------------------------------------------------

  `polish-filler.js` is the builder's premium waiting-room voice.
  It rotates filler angles, uses lightweight models, avoids repetition, and
  cleanly cancels when heavy polish completes.

  Main export:
  • verifySandboxBuild(sandboxId)

--------------------------------------------------------------------------------
34.1 CORE RESPONSIBILITY
--------------------------------------------------------------------------------

  verifySandboxBuild answers one question:
  • “Does the current sandbox app actually build successfully?”

  It does not:
  • repair code
  • modify prompts
  • write files
  • emit SSE

  It simply:
  • runs the build
  • captures logs
  • returns success/failure metadata

--------------------------------------------------------------------------------
34.2 PROVIDER LOOKUP
--------------------------------------------------------------------------------

  The helper first resolves the sandbox provider from:
  • sandboxManager.getProvider(sandboxId)

  If no provider exists:
  • returns
    {
      success: false,
      logs: `Sandbox session ... not found...`,
      exitCode: -1
    }

  So it handles missing-session cases gracefully without throwing immediately.

--------------------------------------------------------------------------------
34.3 COMMANDS IT RUNS
--------------------------------------------------------------------------------

  The helper runs two main command phases:

  1. Permission repair:
  • sudo chown -R user:user /home/user/app || true

  Why:
  • Vite may need to write temp files/config during build
  • bad ownership in sandbox can cause permission-related false failures

  2. Actual production build:
  • npx vite build --base=./

  Why `--base=./`:
  • relative asset paths
  • better compatibility with sandbox/static preview contexts

--------------------------------------------------------------------------------
34.4 LOGGING AND DIAGNOSTICS
--------------------------------------------------------------------------------

  The helper collects:
  • stdout
  • stderr

  If the build fails, it also runs diagnostics:
  • ls -la
  • npm list --depth=0

  These are appended into the logs under a diagnostics section.

  After that:
  • logs are truncated to 15000 characters max

  Return shape:
  • {
      success,
      logs,
      exitCode
    }

--------------------------------------------------------------------------------
34.5 ERROR PATH
--------------------------------------------------------------------------------

  If `provider.runCommand(...)` throws:
  • it returns:
    {
      success: false,
      logs: `Execution error: ${error.message}`,
      exitCode: 1
    }

  So the helper prefers returning a structured failure object over throwing.

--------------------------------------------------------------------------------
34.6 WHY THIS FILE MATTERS
--------------------------------------------------------------------------------

  This file is one of the most important deterministic guards in the builder:
  • it is the source of truth for “does the current codebase build?”
  • apply-ai-code-stream.js, polish verification, rollback verification, and mini

  It prevents the builder from trusting generation quality based only on the

--------------------------------------------------------------------------------
34.7 SUMMARY
--------------------------------------------------------------------------------

  This chapter covers:

35.1 parseFileBlocks()

  Input:

35.2 toFileBlocks()
--------------------------------------------------------------------------------

  Input:
  • array of file objects

  Behavior:
  • if not array -> return []
  • normalize path by stripping leading `/`
  • keep content as-is
  • filter out entries where path missing or content not string

  Important note:
  • Despite the name, this helper returns normalized file objects, not one big
    serialized text string
  • It is more “normalize into valid file array” than “stringify to XML blocks”

--------------------------------------------------------------------------------
35.3 WHY THIS FILE MATTERS

  This file matters because the builder uses a custom `<file path="...">` text

36. DEEP DIVE: sandbox-manager.js REFERENCE
================================================================================

  This chapter covers:
    web/server/lib/sandbox/sandbox-manager.js

  Purpose of the file:
  • This is the in-memory sandbox session registry.
  • It tracks active sandbox providers by sandboxId.
  • It also remembers which sandbox is currently “active”.

  Main export:
  • sandboxManager = new SandboxManager()

  Internal state:
  • this.sandboxes = new Map()
  • this.activeSandboxId = null

--------------------------------------------------------------------------------
36.1 getOrCreateProvider(sandboxId)
--------------------------------------------------------------------------------

  Behavior:
  • if sandbox already exists in the map:
      update lastAccessed
      return existing provider

  Otherwise:
  • create a fresh provider via SandboxFactory.create()
  • call provider.reconnect(sandboxId)
  • if reconnect succeeds:
      store in map
      set activeSandboxId
      return provider
  • if reconnect fails:
      return provider anyway

  Important nuance:
  • If reconnect returns false, the function still returns the provider instance
    even though it was not stored in the map
  • So callers need to understand that “got a provider object back” does not
    always mean reconnection succeeded and was registered

  Error path:
  • logs reconnect error
  • rethrows

--------------------------------------------------------------------------------
36.2 registerSandbox(sandboxId, provider)
--------------------------------------------------------------------------------

  Behavior:
  • inserts sandbox record into map
  • stores:
      sandboxId
      provider
      createdAt
      lastAccessed
  • sets activeSandboxId = sandboxId

  Typical use:
  • after a new sandbox is created successfully elsewhere in the system

--------------------------------------------------------------------------------
36.3 getActiveProvider()
--------------------------------------------------------------------------------

  Behavior:
  • if no activeSandboxId -> return null
  • else look up sandbox in map
  • if found:
      update lastAccessed
      return provider
  • else return null

  Why this matters:
  • some routes can operate against the currently active sandbox without always
    being passed a sandboxId

--------------------------------------------------------------------------------
36.4 getProvider(sandboxId)
--------------------------------------------------------------------------------

  Behavior:
  • lookup sandbox by id in the map
  • if found:
      update lastAccessed
      return provider
  • else return null

  This is the most commonly used access path from verification/apply/edit flows.

--------------------------------------------------------------------------------
36.5 terminateSandbox(sandboxId)
--------------------------------------------------------------------------------

  Behavior:
  • if sandbox exists:
      call provider.terminate()
      delete from map
      clear activeSandboxId if it was the active one

  Errors during provider termination:
  • are caught and logged

  So the manager always tries to clean internal state even if provider teardown is noisy.

--------------------------------------------------------------------------------
36.6 terminateAll()
--------------------------------------------------------------------------------

  Behavior:
  • iterate all sandboxes
  • terminate every provider in parallel
  • clear the map
  • clear activeSandboxId

  This is useful for:
  • process shutdown
  • broad cleanup scenarios

--------------------------------------------------------------------------------
36.7 cleanup(maxAge)
--------------------------------------------------------------------------------

  Default maxAge:
  • 3600000 ms
  • 1 hour

  Behavior:
  • scan all sandbox records
  • if now - lastAccessed > maxAge
      -> mark for deletion
  • terminate stale sandboxes one by one

  Why this matters:
  • prevents stale sandbox sessions from living forever in memory
  • provides a lightweight lifecycle management policy

--------------------------------------------------------------------------------
36.8 WHY THIS FILE MATTERS
--------------------------------------------------------------------------------

  This file is core infrastructure because:
  • routes like apply, verify, edit-stream generation, and sandbox reconnection
    all depend on stable provider lookup by sandbox id
  • it is the central in-memory source of truth for active sandbox providers

  Without it:
  • every route would have to manage sandbox provider instances independently
  • reconnection / cleanup logic would be fragmented

--------------------------------------------------------------------------------
36.9 SUMMARY
--------------------------------------------------------------------------------

  `sandbox-manager.js` is the session registry for live sandbox providers. It
  handles lookup, reconnection, registration, active-sandbox tracking, and stale
  cleanup for the builder's runtime environments.

  Purpose of the file:

--------------------------------------------------------------------------------
38.2 OUTPUT SCHEMA
--------------------------------------------------------------------------------

  The route defines `modificationSchema`:
  • modifications: array of objects with:
      filePath
      action = rewrite | replace_block
      content
      targetBlock? (for replace_block)
      reason
  • summary: string

  So the LLM does not output freeform code alone.
  It outputs a structured modification plan.

--------------------------------------------------------------------------------
38.3 CONTEXT GATHERING
--------------------------------------------------------------------------------

  The route resolves the sandbox provider using:
  • sandboxManager.getProvider(sandboxId)
  • or active provider fallbacks

  Then it gathers:
  • file list under /home/user/app/src
  • App.jsx
  • index.css
  • up to 5 critical component files matching Header/Footer/Hero/Nav

  It constructs one `fullContext` string containing:
  • App.jsx
  • index.css
  • a handful of important shell components

  So unlike heavy polish, this route only sends a focused subset of files.

38.4 MODIFICATION PROMPT PURPOSE
--------------------------------------------------------------------------------

  The system prompt is called `MODIFICATION_PROMPT`.

  It frames the model as:
  • the “Final Polish” engine

  It asks it to:
  • align the code with the original user vision
  • replace placeholder text
  • ensure header/footer consistency
  • fix obvious layout issues
  • ensure content matches the original topic

  It also constrains output:
  • output a list of file modifications
  • use rewrite for full safer file replacements
  • use replace_block only for small unique swaps
  • do not hallucinate new files

--------------------------------------------------------------------------------

  After `generateObject` returns:
  • it extracts modifications and summary

  Then for each modification:
  • if action === rewrite
      -> provider.writeFile(filePath, content)
  • else if action === replace_block and targetBlock exists
      -> read current file
      -> currentContent.replace(targetBlock, content)
      -> write back result

  • { success: true, summary, modifiedFiles: modifications.map(m => m.filePath) }

  Error path:
  • 500 with error.message

  multi-provider retries, and a regex-based fallback path.

40. DEEP DIVE: create-ai-sandbox-v2.js REFERENCE
================================================================================

  This chapter covers:
    web/server/routes/create-ai-sandbox-v2.js

  Purpose of the file:
  • This route creates a fresh AI builder sandbox and initializes a Vite React app
    inside it.
  • It also resets global sandbox state and registers the new provider.

  Main export:
  • default async function createAiSandboxV2(req, res)

--------------------------------------------------------------------------------
40.1 HIGH-LEVEL RESPONSIBILITY
--------------------------------------------------------------------------------

  This route is the builder's environment bootstrapper.

  It is responsible for:
  • defensive cleanup of existing sandbox state
  • provider creation through SandboxFactory
  • actual sandbox creation
  • Vite app setup
  • sandbox registration in sandboxManager
  • populating global sandbox state caches

--------------------------------------------------------------------------------
40.2 DEFENSIVE CLEANUP
--------------------------------------------------------------------------------

  Before creating a new sandbox, the route attempts to clean up old ones.

  It does:
  • sandboxManager.terminateAll() if available
  • global.activeSandboxProvider.terminate() if present
  • sets global.activeSandboxProvider = null

  It also resets:
  • global.existingFiles
      -> clear if already exists
      -> or create new Set()

  Why:
  • avoid stale live provider state
  • avoid multiple active sandbox collisions
  • give the builder a clean environment before bootstrapping a new preview

--------------------------------------------------------------------------------
40.3 SANDBOX CREATION
--------------------------------------------------------------------------------

  Preconditions:
  • E2B_API_KEY must exist
  • otherwise route throws:
      E2B_API_KEY is not set in environment variables

  Creation flow:
  • provider = SandboxFactory.create()
  • sandboxInfo = await provider.createSandbox()
  • ensure sandboxInfo.sandboxId exists
  • await provider.setupViteApp()

  So the route does not stop at just creating an E2B sandbox shell.
  It also initializes the actual Vite React app environment inside it.

--------------------------------------------------------------------------------
40.4 REGISTRATION AND GLOBAL STATE
--------------------------------------------------------------------------------

  After creation/setup:
  • sandboxManager.registerSandbox(sandboxInfo.sandboxId, provider)
  • global.activeSandboxProvider = provider
  • global.sandboxData = { sandboxId, url }

  It also sets global.sandboxState:
  • fileCache:
      files: {}
      lastSync: Date.now()
      sandboxId
  • sandbox: provider
  • sandboxData:
      sandboxId
      url

  Why this matters:
  • many later routes use sandboxManager and/or global sandbox references
  • the builder needs a central runtime state for current preview environment

--------------------------------------------------------------------------------
40.5 RESPONSE SHAPE
--------------------------------------------------------------------------------

  Success response:
  • {
      success: true,
      sandboxId,
      url,
      provider,
      message: 'Sandbox created and Vite React app initialized'
    }

  Failure response:
  • HTTP 500
  • {
      success: false,
      error,
      stack? (only in development),
      hint: 'Check E2B_API_KEY and network connectivity.'
    }

--------------------------------------------------------------------------------
40.6 WHY THIS FILE MATTERS
--------------------------------------------------------------------------------

  This route matters because almost every other live-preview step depends on it:
  • code apply
  • file inspection
  • edit generation with sandbox context
  • verification
  • repair
  • polish

  Without this route, there is no live environment to write into.

--------------------------------------------------------------------------------
40.7 SUMMARY
--------------------------------------------------------------------------------

  `create-ai-sandbox-v2.js` is the environment boot route. It tears down stale
  sandbox state, creates a fresh provider-backed sandbox, initializes the Vite app,
  registers the new environment, and exposes its `sandboxId` and preview `url`.

41. COMPLETE SYSTEM PICTURE (GENERAL WALKTHROUGH)
================================================================================

  This chapter is intentionally broader than the file-by-file deep dives above.
  Its goal is to give a developer one end-to-end mental model of:
  • what the builder is
  • what the browser does
  • what the server does
  • what the sandbox does
  • what Supabase does
  • where LLM decisions happen
  • where deterministic logic takes over
  • how failure handling works

  Think of this as the “zoomed out” explanation that connects all the detailed
  chapters into one coherent runtime story.

--------------------------------------------------------------------------------
41.1 WHAT THE PRODUCT ACTUALLY IS
--------------------------------------------------------------------------------

  The Volturiano builder is not one LLM endpoint.
  It is a coordinated runtime made of five interacting layers:

  1. Browser orchestration layer
  • React UI
  • chat composer
  • model selector
  • premium mode selector
  • preview iframe
  • SSE listeners
  • snapshot restore UI

  2. Server orchestration layer
  • Express routes in `web/server/index.js`
  • route-specific LLM prompts
  • deterministic render / validate / repair / verify logic
  • SSE event emission

  3. Registry and metadata layer
  • Supabase catalog
  • blueprints
  • templates
  • component taxonomy
  • compatibility graph
  • project rows
  • snapshots

  4. Sandbox execution layer
  • E2B-backed sandbox provider
  • Vite React app living in `/home/user/app`
  • real file system
  • real npm installs
  • real `vite build`

  5. LLM reasoning layer
  • prompt enhancement
  • design system derivation
  • selection / blueprint matching
  • per-component generation
  • edit streaming
  • repair
  • heavy polish
  • mini polish
  • narration / fillers

  The important architectural truth is:
  • the system is hybrid
  • some steps are AI
  • some steps are deterministic
  • some steps are infrastructure-only

  You cannot understand the builder by looking only at prompts.
  You also cannot understand it by looking only at the sandbox.
  It is the interaction between those layers that defines the product.

--------------------------------------------------------------------------------
41.2 PRIMARY RUNTIME STATES
--------------------------------------------------------------------------------

  At runtime, the builder is almost always moving through some combination of:

  • user prompt state
  • design-system state
  • component-plan state
  • generated file state
  • sandbox state
  • project/snapshot state
  • chat/narration state

  A useful way to think about the product is:
  • prompts create plans
  • plans create files
  • files create sandbox state
  • sandbox state becomes snapshots
  • snapshots feed future edits/restores

  This means the system is not stateless.
  It is an accumulating workflow.

--------------------------------------------------------------------------------
41.3 FIRST-TIME BUILD: COMPLETE STEP-BY-STEP
--------------------------------------------------------------------------------

  A first-time build usually starts in the browser in `Generation.jsx`.

  Step 1: User submits prompt
  • The UI captures:
      text prompt
      selected model
      premiumMode
      strictMode
      optional images
      optional selected community components

  Step 2: Project init
  • The browser calls `/api/projects/init`
  • This establishes or validates the project/build id on the backend
  • It also lets the system attach future snapshots and updates to a stable id

  Step 3: Sandbox creation
  • If no live sandbox exists, the browser calls `/api/create-ai-sandbox-v2`
  • The server:
      tears down old sandbox state
      creates a provider from `SandboxFactory`
      creates a sandbox
      sets up a Vite React app
      registers it in `sandboxManager`
      exposes `sandboxId` + preview URL

  Step 4: Prompt enhancement
  • The browser calls `/api/enhance-prompt`
  • The server:
      deterministically extracts explicit component names
      asks a fast model to expand the brief into a richer creative spec
      appends `EXPLICIT_COMPONENTS: [...]` if needed
      gracefully falls back to original prompt on failure

  Step 5: Design system derivation
  • The browser calls `/api/derive-design-system`
  • The server:
      produces structured palette / typography / imagery / layout preferences
      returns one normalized designSystem object
      or null on graceful degradation

  Step 6: Premium selection
  • If premiumMode is not off, the browser calls `/api/select-components`
  • The server:
      fetches categories + bounded catalog
      asks the selector LLM which premium components fit
      returns selections + customComponentsNeeded
  • If premiumMode is off:
      the selection route returns an intentionally empty premium selection

  Step 7: Planning
  • The browser calls `/api/plan-website-components`
  • The server chooses:
      V2 path for hybrid/strict
      V1 path for off
  • The route returns:
      components
      complexity
      required packages
      isMultiPage
      pages
      sharedComponentRefIds
      aiNarration

  Step 8: Dependency prep
  • The browser may call `/api/install-packages` with required packages
  • This is usually a preparatory install phase before file generation completes

  Step 9: Premium bundle resolution
  • Planned premium components are fetched from `/api/component-bundle`
  • These already contain file-block content and often real export names/paths

  Step 10: Custom component generation
  • Planned generated components go one-by-one through `/api/generate-single-component`
  • The route returns structured content for each file

  Step 11: Deterministic App.jsx synthesis
  • Once all components are known, the browser calls `/api/render-app`
  • The server uses `renderAppTemplate(...)`
  • This avoids LLM drift in the app shell

  Step 12: Import validation
  • The browser calls `/api/validate-imports`
  • The server checks import graph consistency before writing files

  Step 13: Apply
  • The browser calls `/api/apply-ai-code-stream`
  • The server:
      filters protected files
      sanitizes imports
      installs allowed deps
      writes files
      verifies build
      repairs if needed
      polishes
      mini-polishes
      restarts Vite
      emits COMPLETE

  Step 14: Snapshot and project sync
  • The browser fetches exact sandbox files
  • Saves a snapshot to Supabase
  • Updates project metadata and build status

  Step 15: Preview refresh
  • The iframe refreshes to the sandbox URL
  • The user sees the site

--------------------------------------------------------------------------------
41.4 EDIT CYCLE: COMPLETE STEP-BY-STEP
--------------------------------------------------------------------------------

  Once a project has already been applied at least once, the user is no longer
  in first-build mode. They are in edit mode.

  Step 1: Chat submission
  • `sendChatMessage()` checks `conversationContext.appliedCode.length`
  • If non-zero, it routes into the edit workflow instead of `startGeneration`

  Step 2: Ensure sandbox still exists
  • If sandbox state is missing, the client creates a new sandbox
  • Or later apply calls may recover by booting a sandbox if needed

  Step 3: Optional component injection
  • If the user attached new community/premium components in chat:
      fetch bundles
      turn them into explicit file objects
      apply them silently with `skipPolish = true`

  Step 4: AI edit generation
  • The client calls `/api/generate-ai-code-stream` with:
      prompt
      recentMessages
      sandboxId
      current siteMap
      premium component inventory
      optionally current file contents from sandbox

  Step 5: Streamed result becomes apply input
  • On `complete`, the streamed generatedCode is handed to `applyGeneratedCode`

  Step 6: Apply route operationalizes the edit
  • Same apply route as initial build
  • But policy changes may differ:
      `isEdit = true`
      polish gating now depends on premiumMode

  Step 7: Snapshot / update
  • Updated sandbox state can be re-snapshotted and restored later

  So edits are not a separate system.
  They are a different entry path into the same apply/sandbox lifecycle.

--------------------------------------------------------------------------------
41.5 WHAT THE SERVER IS RESPONSIBLE FOR
--------------------------------------------------------------------------------

  The server is the orchestrator and policy enforcer.

  It is responsible for:
  • model prompt construction
  • schema validation for structured AI outputs
  • provider/model routing
  • registry lookups
  • sandbox lifecycle
  • file protocol parsing
  • dependency allowlisting
  • build verification
  • repair and rollback logic
  • SSE event emission
  • persistence handoff

  A good mental model:
  • the browser decides what to ask for
  • the server decides how to safely turn that request into a build

--------------------------------------------------------------------------------
41.6 WHAT THE SANDBOX IS RESPONSIBLE FOR
--------------------------------------------------------------------------------

  The sandbox is where generated intent becomes executable reality.

  It is responsible for:
  • holding real files
  • running npm installs
  • running Vite
  • serving the preview
  • running `vite build`

  Without the sandbox:
  • there is no real preview
  • no real verification
  • no real repair target

  This is why the sandbox layer is central, not optional.

--------------------------------------------------------------------------------
41.7 WHAT SUPABASE IS RESPONSIBLE FOR
--------------------------------------------------------------------------------

  Supabase is doing multiple jobs in this product:

  Product/data jobs:
  • project records
  • snapshots
  • published sites
  • user settings
  • credits/billing RPCs

  Registry/catalog jobs:
  • components
  • component_categories
  • component_compatibility
  • website_type_blueprints
  • templates / template_sections / weighted_templates
  • industry_verticals
  • color_themes

  Feedback/evolution jobs:
  • usage_count
  • retention tracking
  • author reputation updates

  So Supabase is not just storage.
  It is part of the builder's reasoning substrate.

--------------------------------------------------------------------------------
41.8 WHERE THE LLM IS USED VS WHERE IT IS NOT
--------------------------------------------------------------------------------

  Common mistake:
  • assuming the builder is “just one big LLM”

  In reality, LLM use is concentrated in:
  • enhance prompt
  • derive design system
  • premium selection
  • blueprint matching / category refinement
  • per-component generation
  • edit generation
  • repair
  • heavy polish
  • mini polish
  • narration / filler

  Deterministic logic is concentrated in:
  • App.jsx rendering
  • file-block parsing
  • package allowlisting
  • build verification
  • path normalization
  • structural dedupe
  • snapshot restore
  • sandbox state management

  That split is very important:
  • LLMs propose
  • deterministic code constrains, validates, or operationalizes

--------------------------------------------------------------------------------
41.9 WHY THERE ARE SO MANY STAGES
--------------------------------------------------------------------------------

  The many stages are not accidental complexity.
  They exist because each stage solves a different class of failure:

  • enhancement
      solves vague prompts
  • design system
      solves visual drift
  • premium selection
      solves reuse vs from-scratch choice
  • planning
      solves structure / component decomposition
  • deterministic App.jsx rendering
      solves shell drift
  • import validation
      solves broken references before sandbox write
  • apply verification
      solves “looks plausible but does not build”
  • auto-repair
      solves ordinary code breakage
  • heavy polish
      solves generic copy / design mismatch
  • mini polish
      solves last-mile UX/reliability defects

  If you collapse everything into one prompt:
  • quality drops
  • determinism drops
  • observability drops
  • recovery gets harder

--------------------------------------------------------------------------------
41.10 MAIN DATA CONTRACTS THAT MATTER MOST
--------------------------------------------------------------------------------

  If a developer only remembers a few core contracts, they should remember these:

  1. File-block protocol
  • `<file path="...">...</file>`
  • used across generation, bundle delivery, polishing, and apply parsing

  2. Design system object
  • normalized aesthetic contract used by many routes

  3. Plan object
  • components
  • complexity
  • requiredPackages
  • isMultiPage
  • pages
  • sharedComponentRefIds

  4. Apply SSE contract
  • technical events + conversational narrator events

  5. Snapshot object
  • exact file map + package/design/plan metadata

  These contracts are what let the whole system stay coherent across many steps.

--------------------------------------------------------------------------------
41.11 HOW PREMIUM MODE CHANGES THE WHOLE SYSTEM
--------------------------------------------------------------------------------

  premiumMode is not a cosmetic toggle.
  It changes the shape of the pipeline.

  `off`
  • selection route exits early
  • planning uses V1 legacy path
  • edits do not get final polish by default
  • everything leans more toward generated-only output

  `hybrid`
  • V2 selection path
  • premium + generated can coexist
  • customComponentsNeeded can create generated placeholders
  • edit polish is enabled

  `strict`
  • V2 selection path
  • stronger preference/requirement for premium components when available
  • edit polish is enabled

  So premiumMode affects:
  • what the planner plans
  • what the generator generates
  • what the apply route polishes

--------------------------------------------------------------------------------
41.12 WHY APP.JSX IS SPECIAL
--------------------------------------------------------------------------------

  Many routes treat App.jsx differently from ordinary files.

  Reasons:
  • it is the shell
  • it is where imports converge
  • it controls routing/layout
  • small mistakes there can break the whole preview

  That is why the system:
  • renders App.jsx deterministically
  • preserves it carefully during edits
  • often writes it late
  • excludes it from heavy polish
  • injects golden App.jsx into edit prompts when plan data exists

  App.jsx is not “just another component.”
  It is the assembly boundary between plan and runtime.

--------------------------------------------------------------------------------
41.13 WHY THE SYSTEM KEEPS SO MUCH CONTEXT
--------------------------------------------------------------------------------

  The builder stores and reuses context in many places:
  • recentMessages
  • conversationContext
  • lastPromptRef
  • designSystemRef
  • componentPlanRef
  • sandbox file contents
  • snapshots

  This is necessary because edits are path-dependent.

  A build is not just:
  • prompt -> code

  It is more like:
  • prompt -> plan -> code -> snapshot -> edit -> repair -> snapshot -> restore

  Later steps need to know what earlier steps did.

--------------------------------------------------------------------------------
41.14 FAILURE PHILOSOPHY
--------------------------------------------------------------------------------

  The system generally uses one of three failure strategies:

  1. Hard fail
  • used when a step is essential and cannot be sensibly bypassed
  • example:
      no sandbox
      missing prompt in required routes
      some provider-critical failures

  2. Retry/fallback
  • used when another model/provider may rescue the request
  • example:
      cross-provider fallback
      repair fallback
      retry-heavy selection/design-system calls

  3. Graceful degradation
  • used when the feature is valuable but not worth blocking the whole pipeline
  • example:
      enhance-prompt returns original prompt
      derive-design-system returns null
      cinematic-response returns default copy
      filler messages silently fail

  Understanding which category each route uses is key to understanding product
  reliability behavior.

--------------------------------------------------------------------------------
41.15 WHY THERE ARE MULTIPLE POLISH LAYERS
--------------------------------------------------------------------------------

  There are at least three polish-ish concepts in the system:
  • finalize-codebase.js style finalization
  • heavy polish (`polish-refinement.js`)
  • mini polish (`mini-polish-refinement.js`)

  Their purposes differ:
  • heavy polish
      high-impact refinement of content and aesthetic consistency
  • mini polish
      conservative QA/sanity sweep
  • finalize-codebase
      structured targeted modification route

  So “polish” is not one feature.
  It is a family of refinement strategies with different scope and cost.

--------------------------------------------------------------------------------
41.16 MENTAL MODEL FOR DEVELOPERS NEW TO THE CODEBASE
--------------------------------------------------------------------------------

  If you are new to the project, the simplest useful mental model is:

  • The browser orchestrates
  • The server decides and verifies
  • The sandbox executes
  • Supabase stores memory and catalog knowledge
  • Deterministic helpers keep the LLM from drifting too far

  More concretely:
  • Prompt enhancement makes the request smarter
  • Design system makes the style consistent
  • Selection/planning decide structure
  • Generation produces files
  • Deterministic App.jsx glues structure together
  • Apply turns files into a real preview
  • Verify/repair/polish make it trustworthy
  • Snapshots make it resumable and editable

--------------------------------------------------------------------------------
41.17 IF YOU HAD TO RECREATE THE SYSTEM
--------------------------------------------------------------------------------

  If a developer had to rebuild the product from scratch, the key sequence would be:

  1. Build a React browser UI with:
  • chat
  • model selector
  • preview iframe
  • file/snapshot state

  2. Build an Express backend with:
  • prompt enhancement
  • design system derivation
  • premium selection
  • planning
  • per-component generation
  • edit generation stream
  • apply stream
  • sandbox create/inspect routes

  3. Build a provider abstraction with:
  • createSandbox
  • setupViteApp
  • writeFile
  • readFile
  • listFiles
  • installPackagesOnly
  • runCommand
  • restartViteServer
  • terminate
  • reconnect

  4. Build deterministic guards:
  • App.jsx renderer
  • import validation
  • package allowlist
  • build verification
  • file-block parser

  5. Build persistence:
  • projects
  • snapshots
  • component registry
  • blueprints/templates
  • billing/credits if needed

  6. Add polish/repair/narration layers last
  • because they improve quality, but the core product is the
    browser -> plan -> sandbox -> verify loop

--------------------------------------------------------------------------------
41.18 FINAL GENERAL SUMMARY
--------------------------------------------------------------------------------

  The Volturiano builder is best understood as:
  • a staged compiler for websites
  • with LLMs acting as multiple specialized compiler passes
  • deterministic code acting as validators, normalizers, and assemblers
  • a sandbox acting as the execution target
  • Supabase acting as long-term memory and catalog substrate

  The most important design principle running through the whole codebase is:
  • never trust one model call to do everything correctly

  Instead the system:
  • decomposes tasks
  • validates structure
  • renders key shells deterministically
  • verifies with a real build
  • repairs when possible
  • rolls back when needed
  • preserves exact outputs through snapshots

  That is what makes it a builder system rather than just an AI text generator.
