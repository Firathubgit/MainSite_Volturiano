================================================================================
VOLTURIANO BUILDER - GDPR CONTEXT & IMPLEMENTATION KNOWLEDGE BASE
================================================================================

This document serves as the master record of how Volturiano handles personal data,
designed to prove GDPR compliance for audits and to guide future feature development.

--------------------------------------------------------------------------------
1. DATA INVENTORY (WHAT WE STORE & WHY)
--------------------------------------------------------------------------------
Based on our SQL Schema, we process the following Personally Identifiable Information (PII):

Table: `profiles`
- PII: id, display_name, full_name, username, avatar_url, stripe_customer_id, stripe_subscription_id
- Purpose: Account creation, authentication, billing linkage.
- Lawful Basis: Performance of a Contract.
- Retention: Until account deletion (except Stripe IDs, kept 7 years for tax/Bokföringslagen).

Table: `projects` & `snapshots`
- PII: user_id (link to profile), chat_history (free-text prompts)
- Purpose: Providing the core AI generation service.
- Lawful Basis: Performance of a Contract.
- Retention: Until user deletes the project or their account.

Table: `credit_transactions`
- PII: user_id, stripe_payment_id
- Purpose: Financial ledger and anti-fraud.
- Lawful Basis: Legal Obligation (Swedish Accounting Act / Bokföringslagen).
- Retention: 7 years. MUST NOT be deleted upon account deletion.

--------------------------------------------------------------------------------
2. THIRD-PARTY PROCESSORS (DATA TRANSFERS)
--------------------------------------------------------------------------------
Volturiano uses sub-processors. You (Firat) must accept their Data Processing Agreements (DPA) in their respective dashboards:
- Supabase (Database & Auth Hosting) -> EU/Global data centers.
- Vercel (Frontend Hosting) -> Logs IP addresses temporarily for DDoS protection.
- Stripe (Payments) -> Highly regulated, PCI-DSS compliant.
- AI Providers (OpenAI, Anthropic, Gemini, Morph) -> We send user prompts here.
  *CRITICAL:* We rely on their API "Zero Data Retention" policies, meaning they do not use Volturiano API data to train their models.

--------------------------------------------------------------------------------
3. SECURITY ARCHITECTURE (SUPABASE RLS)
--------------------------------------------------------------------------------
Every table containing user data MUST have Row Level Security (RLS) turned on.
Rule of thumb for all future SQL migrations:
`CREATE POLICY "Users can only view their own data" ON table_name FOR SELECT USING (auth.uid() = user_id);`
`CREATE POLICY "Users can only insert their own data" ON table_name FOR INSERT WITH CHECK (auth.uid() = user_id);`

--------------------------------------------------------------------------------
4. THE "RIGHT TO BE FORGOTTEN" STRATEGY (ACCOUNT DELETION)
--------------------------------------------------------------------------------
When a user clicks "Delete Account" in Settings:
1. We delete their rows in `projects`, `snapshots`, `published_sites`.
2. We delete their row in `profiles` and `auth.users`.
3. We DO NOT delete `credit_transactions`. We must retain financial history to comply with Swedish Skatteverket.

--------------------------------------------------------------------------------
5. COOKIES & TRACKING
--------------------------------------------------------------------------------
- Essential: Supabase session cookies (sb-*-auth-token), Stripe security cookies.
- Non-essential: Vercel Analytics and Speed Insights (blocked by Cookie Consent Banner).

--------------------------------------------------------------------------------
6. INCIDENT RESPONSE PLAN (DATA BREACH PROTOCOL)
--------------------------------------------------------------------------------
If a data breach occurs (e.g., unauthorized access to Supabase or Stripe), the following 72-hour protocol must be followed:

1. DETECTION & ISOLATION:
   - Identify the source (Vercel logs, Supabase Auth logs, Stripe Dashboard alerts).
   - Immediately rotate all compromised API keys (Supabase JWT secret, Stripe Secret, AI provider keys).
   - If necessary, pause the Railway backend deployment to stop data exfiltration.

2. CLASSIFICATION:
   - Low Risk: Encrypted data leaked, but encryption keys are safe. Non-sensitive data (e.g., component names).
   - High Risk: Plaintext PII leaked (Emails, Names, Auth tokens, Billing history).

3. REPORTING (Within 72 Hours):
   - By law, IMY (Integritetsskyddsmyndigheten, datainspektionen.se) must be notified of High Risk breaches within 72 hours via their e-service.
   - You must have this information ready: Nature of breach, number of users affected, consequences, and mitigation steps taken.

4. USER NOTIFICATION:
   - If High Risk, affected users must be emailed immediately.
   - Template: "Security Notice: Volturiano Data Breach. [Date]. We detected unauthorized access to [Data Type]. We have secured the system by [Actions Taken]. We recommend you change your password and monitor your accounts. We have reported this to IMY."

5. POST-MORTEM:
   - Document the breach in a permanent internal log for accountability.
