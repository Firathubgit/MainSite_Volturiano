1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------

The Volturiano Builder pipeline is a sophisticated, multi-stage distributed system designed to transform high-level natural language user inputs into fully functional, production-ready React applications within seconds. 

Unlike simple "text-to-code" snippets, this pipeline orchestrates a complete software development lifecycle (SDLC) in real-time. It acts as an automated engineering team, performing roles of:
- Product Manager (Prompt Enhancement)
- Software Architect (Component Planning)
- Frontend Developer (Component Implementation)
- DevOps Engineer (Sandbox Provisioning & Deployment)

The system leverages a micro-chaining architecture where distinct AI agents (powered by LLMs) handle specific stages of the generation process. State is managed optimistically on the client-side (`Generation.jsx`) while the backend (`web/server`) handles the heavy lifting of orchestration, sandboxing, and file manipulation.

Key Performance Indicators (KPIs):
- End-to-end generation time: Target < 45 seconds
- Code validity rate: Target > 95%
- UI/UX Quality: "Award-winning" standard (enforced via system prompts)

--------------------------------------------------------------------------------

The pipeline follows a "Plan-Execute-Apply" pattern.

3. FRONTEND INITIATION (Client-Side Trigger)
--------------------------------------------------------------------------------

Location: `web/src/pages/Agency/pages/Builder/Generation/Generation.jsx`

The process begins when the user lands on the Generation page, typically via a navigation event carrying a `prompt` in the location state.

Initialization Logic:
- The `useEffect` hook detects the presence of `location.state.prompt`.
- A `startGeneration` function is triggered.
- `generationProgress` state is initialized to track the multi-stage process.

State Management:
- `sandboxData`: Stores the `sandboxId` and public `url`.
- `generationProgress`: Tracks status ('Planning...', 'Generating...', 'Applying...'), component list, and thinking states.
- `conversationContext`: Maintains a history of applied code and generated files for context-aware iterations.

The frontend acts as the orchestrator. It does not send one massive request to the backend. Instead, it makes sequential and parallel calls to different endpoints, maintaining control over the UX and allowing for granular progress updates (e.g., "Generated Hero.jsx").

4. INFRASTRUCTURE PROVISIONING (Sandbox V2)
--------------------------------------------------------------------------------

Endpoint: `POST /api/create-ai-sandbox-v2`
Handler: `web/server/routes/create-ai-sandbox-v2.js`

Before any code is generated, the system ensures a runtime environment exists. This is critical for the "Design without limits" promise—we don't just generate text; we generate a running app.

The `createAiSandboxV2` function performs the following operations:

1.  **Sanitization**:
    - Calls `sandboxManager.terminateAll()` to clean up any stale sandboxes associated with the server instance or session. This prevents resource leaks and ensures a fresh start.

2.  **Instantiation**:
    - Uses `SandboxFactory.create()` to instantiate a new E2B sandbox provider.
    - The provider spins up a secure, ephemeral Linux microVM in the cloud.

3.  **Environment Setup**:
    - `provider.setupViteApp()` is called.
    - This creates a standard Vite React project structure inside the sandbox.
    - It ensures `index.html`, `vite.config.js`, and `package.json` are present.
    - It installs base dependencies (React, ReactDOM, TailwindCSS).

4.  **Global Registry**:
    - The new sandbox is registered in `sandboxManager` and `global.activeSandboxProvider`.
    - This global reference is crucial for subsequent API calls (like `apply-ai-code-stream`) to know *where* to write the files.

5.  **Return**:
    - Returns `{ success: true, sandboxId, url }`.
    - The `url` is the public HTTPS endpoint for the running Vite dev server, which the frontend will eventually load into an iframe.

5. PHASE 1: INTENT ANALYSIS & ENHANCEMENT
--------------------------------------------------------------------------------

Endpoint: `POST /api/enhance-prompt`
Handler: `web/server/routes/enhance-prompt.js`

Users often provide vague inputs like "make a dentist site." To achieve high-quality results, we first pass this input through a "Product Designer" agent.

Mechanism:
- **Input**: User prompt, Model (default: `gpt-4o`).
- **System Persona**: "Expert UX writer and product designer."
- **Objective**: Transform brief requests into "AWARD-WINNING" specifications.

System Prompt Strategy:
- **Preservation**: Explicit rules to preserve the user's core intent.
- **Expansion**: Instructs the model to add compelling copy, clear section descriptions, and design nuances.
- **Aesthetic Direction**: Enforces terms like "premium," "glassmorphism," "typography hierarchy."
- **Output Format**: Pure text specification, 200-500 words.

Example Transformation:
Input: "Dentist site"
Output: "Create a pristine, reassuring digital experience for 'Lumina Dental'. Use a calming palette of soft teals and white. The Hero section should feature a smiling patient with the headline 'Modern Care, Timeless Smiles'. Include sections for..."

This enhanced prompt becomes the `overallContext` for all subsequent steps, ensuring consistency.

--------------------------------------------------------------------------------
6. PHASE 2: ARCHITECTURAL PLANNING
--------------------------------------------------------------------------------

Endpoint: `POST /api/plan-website-components`
Handler: `web/server/routes/plan-website-components.js`

With a detailed spec in hand, the system needs a technical blueprint. This phase determines *what* files need to be created.

Mechanism:
- **Input**: Enhanced prompt.
- **Output**: JSON object (enforced via `zod` schema).

The `planSchema` defines:
- `components`: Array of objects `{ name, path, description, designFocus, keyContent }`.
- `globalStyle`: String describing the overall CSS theme.
- `appImports`: List of component names to be imported in `App.jsx`.

System Prompt Constraints:
- **Scoping**: Breaks the request into 5-12 discrete components (e.g., Header, Hero, Services, Footer).
- **File mapping**: Enforces 1 component = 1 file.
- **Mandatory items**: Always includes `src/index.css` (implicitly) and `src/App.jsx`.
- **Library Blacklist**: Explicitly forbids `react-leaflet`, `leaflet`, `mapbox-gl`, `three.js` due to known sandbox context/WebGL issues.
- **Image Policy**: Mandates real Unsplash/Picsum URLs, strictly creating a "no placeholder" rule for assets.

This step effectively generates the "ticket list" for the next phase.

--------------------------------------------------------------------------------
7. PHASE 3: PARALLEL COMPONENT GENERATION
--------------------------------------------------------------------------------

Endpoint: `POST /api/generate-single-component`
Handler: `web/server/routes/generate-single-component.js`

This is the core implementation phase. To minimize latency, the frontend calls this endpoint *in parallel* for every component identified in the planning phase.

Mechanism:
- **Input**: Component definition (name, path, description), global style context, overall project context.
- **Differentiation**: 
    - Logic branches based on file extension.
    - **CSS Mode**: Generates `index.css` with `@tailwind` directives and custom CSS variables.
    - **React Mode**: Generates `.jsx` files.

React Generation Persona:
- System Prompt: "Award-winning React frontend developer."
- **Constraint Checklist**:
    1.  **Output Format**: `<file path="...">CODE</file>` (XML-like wrapping for easy parsing).
    2.  **Completeness**: No markdown fences, no "rest of code" comments. Code must be syntactically complete.
    3.  **Styling**: Pure Tailwind CSS classes.
    4.  **Responsiveness**: Mobile-first (`sm:`, `md:`, `lg:` classes).
    5.  **Media**: Enforced use of `images.unsplash.com`.

Error Handling:
- If a generation fails, the frontend catches the error for that specific component `verify_file_content` logic often retries or reports the failure without halting the entire pipeline.
- The `generate-single-component` logic includes regex fallbacks to extract code if the LLM accidentally includes markdown text around the `<file>` tags.

--------------------------------------------------------------------------------
8. PHASE 4: CODE SYNTHESIS & ASSEMBLY
--------------------------------------------------------------------------------

Location: Frontend (`Generation.jsx`)

Once all parallel requests complete, the frontend holds an array of file contents.

Synthesis Logic:
1.  **Aggregation**: Joins all component strings into a single text block.
2.  **App.jsx Check**:
    - The system checks if `src/App.jsx` was successfully generated by the AI.
    - **Fallback Synthesis**: If the AI failed to generate `App.jsx` (or if it was skipped), the frontend *synthesizes* one content locally.
    - It iterates through the planned components, generates `import` statements, and creates a basic layout wrapping them.
    - This guarantees the app will at least render *something*, preventing a "blank screen" error due to a missing root component.

The result is a massive string block containing every file needed for the application, wrapped in `<file>` tags.

9. PHASE 5: SANDBOX APPLICATION & HOT RELOAD
--------------------------------------------------------------------------------

Endpoint: `POST /api/apply-ai-code-stream`
Handler: `web/server/routes/apply-ai-code-stream.js`

This endpoint is responsible for treating the generated code as a "patch" to the running sandbox. It uses Server-Sent Events (SSE) to stream progress back to the UI.

Step-by-Step Execution:

1.  **Connection & Validation**:
    - Establishes SSE connection (`Content-Type: text/event-stream`).
    - Validates presence of a `sandboxId` and `provider`.

2.  **Parsing**:
    - Uses regular expressions to extract `<file path="...">...` blocks.
    - Filters out protected files (`package.json`, `vite.config.js`) to prevent the AI from breaking the build configuration.

3.  **Dependency Analysis**:
    - Scans all file contents for `import ... from '...'` statements.
    - Compares imported packages against a whitelist of built-ins (`react`, `vite`, `tailwindcss`).
    - Identifies *new* external packages (e.g., `framer-motion`, `lucide-react`, `date-fns`).

4.  **Package Installation**:
    - If new packages are found, it commands the sandbox provider to run `npm install`.
    - **Optimization**: It installs packages *before* writing files to minimize the window where imports might be missing.

5.  **FileSystem Writes**:
    - Writes files to the sandbox's virtual filesystem.
    - **Order Matters**: It specifically sorts files to write CSS first, then components, then `App.jsx` last. This is a heuristic to help Vite's HMR (Hot Module Replacement) handle the updates more gracefully.

6.  **Vite Server Restart**:
    - Once all files are written, it sends a command to restart the Vite server process.
    - This is often necessary when adding new dependencies or changing global configurations.
    - The SSE stream sends a 'complete' event.

On the frontend, the `iframe` is refreshed (with a timestamp query param to bust cache) once the 'complete' signal is received, displaying the newly built site.

10. FALLBACK MECHANISMS (Streaming)
--------------------------------------------------------------------------------

Endpoint: `POST /api/generate-ai-code-stream`
Handler: `web/server/routes/generate-ai-code-stream.js`

While the parallel generation (Plan -> Generate Multi) is the primary path, the system retains a monolithic streaming path.

Use Cases:
1.  **Edits**: When the user asks to "make the button blue," we don't re-plan the whole site. We use this endpoint with the existing file context.
2.  **Fallback**: If parallel generation fails (e.g., network issues), the frontend falls back to this endpoint.

Logic:
- Accepts `context` (existing files, file structure).
- Uses `streamText` from the Vercel AI SDK.
- Streams tokens directly to the client.
- The client accumulates tokens and parses `<file>` tags in real-time.

Edit Mode Specifics:
- Injected System Prompt: "You are modifying an existing application. Output ONLY the files that need to change."
- Context Injection: Reads `global.sandboxState.fileCache` to inject the content of relevant files into the prompt, so the LLM "sees" the code it is editing.

11. ERROR HANDLING & RESILIENCE
--------------------------------------------------------------------------------

The pipeline is designed to be resilient to common AI and network failures.

**Frontend Resilience:**
- **Retry Logic**: If `startGeneration` fails, it catches the error and attempts the fallback streaming method.
- **Synthesized App.jsx**: As mentioned, ensures the app serves *something* even if the root component generation fails.

**Backend Resilience (`web/server/index.js`):**
- **Global Error Handlers**: `process.on('uncaughtException')` and `unhandledRejection` prevent the Node.js server loop from crashing due to a stray error in a specific request.
- **Sandbox Cleanup**: `create-ai-sandbox-v2` aggressively cleans up old sandboxes (`terminateAll`) before starting new ones to avoid hitting E2B concurrency limits.

**Sandbox Resilience:**
- **Protected Files**: The file parser ignores attempts to overwrite `vite.config.js`. This prevents the AI from hallucinatively changing the build settings (e.g., changing ports or plugins) which would break the preview connection.

--------------------------------------------------------------------------------
12. SECURITY & CONSTRAINTS
--------------------------------------------------------------------------------

**Sandboxing:**
- The primary security boundary is the E2B sandbox. Code runs in an isolated Firecracker microVM.
- No code executes on the host Volturiano server.

**Package Constraints:**
- The system allows `npm install` for most packages, but the system prompt discourages heavy libraries (Three.js) that might exceed the memory limits of the microVM or cause rendering issues in the iframe.

**Content Safety:**
- This relies on the upstream provider's (OpenAI) safety filters. The backend does not implement additional content filtering on the prompt itself, assuming the authenticated user is trusted within the application context.

14. FRONTEND COMPONENT BREAKDOWN (Generation.jsx)
--------------------------------------------------------------------------------

The frontend controller `Generation.jsx` is a complex state machine. Below is a breakdown of its internal logic.

14.1 STATE VARIABLES

- `sandboxData`: { sandboxId: string, url: string }
  - Holds the reference to the active cloud environment.
  - Sourced from `/api/create-ai-sandbox-v2`.

- `generationProgress`: {
    isGenerating: boolean,
    status: string,         // "Planning...", "Enhancing...", "Generating Hero..."
    components: Array<{ name, path, completed }>,
    streamedCode: string,   // Accumulator for fallback streaming
    currentFile: string     // Currently active file in UI
  }
  - Drives the UI feedback loop.
  - The `components` array renders the "chip" visualization in the sidebar.

- `codeApplicationState`: {
    stage: 'analyzing' | 'installing' | 'applying' | 'complete',
    packages: string[],
    filesGenerated: string[]
  }
  - Tracks the progress of the `/api/apply-ai-code-stream` phase.
  - Used by `CodeApplicationProgress` component to show spinner and package names.

- `conversationContext`: {
    appliedCode: Array<{ files: [], timestamp: Date }>,
    lastGeneratedCode: string
  }
  - Memory of what has been built.
  - Passed back to the backend during "Edit" flows to ensure continuity.

14.2 KEY FUNCTIONS

- `startGeneration(prompt)`:
  - The main entry point.
  - Orchestrates the sequential API calls.
  - Handles the fallback logic: `try { parallel } catch { streaming }`.

- `applyGeneratedCode(code)`:
  - Handles the SSE connection to `/api/apply-ai-code-stream`.
  - Uses `fetch().body.getReader()` to consume the stream.
  - Dispatch actions based on event types (`step`, `file-progress`, `complete`).

- `buildFileTree(files)`:
  - Utility to transform flat file array into a nested object for the file explorer UI.
  - Handles nested paths like `src/components/ui/Button.jsx`.

17. DETAILED API REFERENCE
--------------------------------------------------------------------------------

This section provides a rigorous specification of the backend endpoints involved in the generation pipeline.

17.1 POST /api/create-ai-sandbox-v2

**Description**: Provisions a specific cloud environment for the session.
**Auth**: Session-based.

**Request Body**:
- (Empty) - The user's session ID is inferred from cookies/headers.

**Response (200 OK)**:
```json
{
  "success": true,
  "sandboxId": "sbx-1a2b3c4d",
  "url": "https://sbx-1a2b3c4d.e2b.dev",
  "provider": "E2B",
  "message": "Sandbox created and Vite React app initialized"
}
```

**Response (500 Internal Server Error)**:
```json
{
  "error": "Failed to create sandbox: E2B API timeout"
}
```

**Implementation Details**:
- **Timeout**: 60s hard limit. E2B provisioning usually takes 2-5s.
- **Concurrency**: Terminates any existing sandbox for the user before creation to enforcing a singleton pattern per session.
- **Lifecycle**: Sandbox is kept alive for 1 hour of inactivity.

**Request Body**:

17.5 POST /api/apply-ai-code-stream

**Description**: Applies a batch of files to the sandbox. Uses Server-Sent Events (SSE).

**Headers**:
- `Content-Type: text/event-stream`
- `Cache-Control: no-cache`
- `Connection: keep-alive`

**Event Stream Format**:
1. `data: {"type": "start", "message": "Applying..."}`
2. `data: {"type": "step", "step": 1, "message": "Installing packages: framer-motion"}`
3. `data: {"type": "package-progress", "installedPackages": ["framer-motion"]}`

18. ERROR HANDLING & TROUBLESHOOTING GUIDE
--------------------------------------------------------------------------------

This table outlines common failure modes and the system's automated responses.

| Error Code / Scenario | Cause | System Response / Recovery |
|-----------------------|-------|----------------------------|
| **E2B_INIT_TIMEOUT** | Cloud provider latency > 60s. | Frontend shows "Sandbox creation failed". No automated retry logic currently (user must refresh). |
| **LLM_RATE_LIMIT** | OpenAI 429 Too Many Requests. | Backend logs error. Frontend receives 500. Currently hard-fails; future improvement: exponential backoff. |
| **INVALID_JSON_PLAN** | LLM outputs malformed JSON for plan. | `plan-website-components` throws Zod parse error. The user sees "Planning failed". |
| **MISSING_FILE_TAG** | Component generator outputs raw code without tags. | Regex fallback wraps the entire text in a `<file>` tag with the requested path. |
| **VITE_CRASH** | Generated code has syntax error. | `apply-ai-code-stream` restarts Vite. Use defaults to error overlay in the iframe. User can "Fix with AI" to repair. |
| **PACKAGE_INSTALL_FAIL** | NPM constraint violation. | The installation step logs a warning but proceeds to write files. The app may runtime error, but data is preserved. |
| **HMR_DISCONNECT** | Sandbox idle timeout. | Frontend detects disconnect via polling `/api/sandbox-status`. Prompts user to "Resume Session" (recreates sandbox). |

19. PERFORMANCE & SCALABILITY ANALYSIS
--------------------------------------------------------------------------------

19.1 PARALLELIZATION STRATEGY
The decision to distinct `plan` and `generate` phases allows for massive parallelism.
- **Sequential**: Plan (5s) -> Generate Loop (10 components * 10s = 100s) = ~105s Total.
- **Parallel (Current)**: Plan (5s) -> Generate All (max(10s)) = ~15s Total.
This 7x speedup is the "magic" that makes the builder feel interactive.

19.2 SANDBOX RESOURCE LIMITS
- **CPU**: 2 vCPU per sandbox.
- **RAM**: 512MB - 1GB dynamic.
- **Storage**: 1GB ephemeral.
- **Concurrency**: E2B supports 100s of concurrent sandboxes per API key tier.
- **Impact**: We expressly forbid `npm install` of massive datasets or ML models to respect these limits.

19.3 CACHING LAYERS
- **Prompt Caching**: Currently disabled to ensure freshness.
- **File Caching**: `global.sandboxState.fileCache` maintains the authoritative state of the project in Node.js memory. This prevents us from needing to read back from the E2B filesystem for every small edit, significantly speeding up the "Edit" loop.

20. CRITICAL UTILITY FUNCTIONS (REFERENCE IMPLEMENTATION)
--------------------------------------------------------------------------------

Understanding the specific regex and parsing logic is crucial for debugging generation issues.

20.1 FILE PARSER (parseFiles)
This function is responsible for robustly extracting code blocks from the LLM's sometimes-messy output.

```javascript
// Located in: web/server/routes/apply-ai-code-stream.js
function parseFiles(code) {
  const files = [];
  // Regex Explanation:
  // <file path="([^"]+)"> capture group 1: the file path
  // ([\s\S]*?)           capture group 2: content (non-greedy, matches newlines)
  // <\/file>             closing tag
  const regex = /<file path="([^"]+)">([\s\S]*?)<\/file>/g;
  let m;
  while ((m = regex.exec(code)) !== null) {
    let path = m[1].replace(/^\/+/, ''); // Strip leading slashes
    const content = m[2].trim();
    files.push({ path, content });
  }
  return files;
}
```

**Known Issues**: 
- If the LLM generates nested file tags (rare), this regex breaks.
- If the LLM forgets the closing `</file>`, the content is lost.
- **Mitigation**: We instruct the LLM via system prompt to be extremely strict about this format.

20.2 PACKAGE EXTRACTION (extractPackages)
This function ensures we don't crash on missing dependencies.

```javascript
function extractPackages(code) {
  // Matches: import ... from "package-name"
  const importRegex = /import\s+(?:(?:\{[^}]*\}|\*\s+as\s+\w+|\w+)(?:\s*,\s*(?:\{[^}]*\}|\*\s+as\s+\w+|\w+))*\s+from\s+)?['"]([^'"]+)['"]/g;
  const packages = new Set();
  let m;
  while ((m = importRegex.exec(code)) !== null) {
    const pkg = m[1];
    // Filter relative imports
    if (!pkg.startsWith('.') && !pkg.startsWith('/')) {
      // Handle scoped packages like @radix-ui/react-slot -> @radix-ui/react-slot
      // Handle deep imports like lodash/debounce -> lodash
      const rootPkg = pkg.startsWith('@') 
        ? pkg.split('/').slice(0, 2).join('/') 
        : pkg.split('/')[0];
      packages.add(rootPkg);
    }
  }
  return [...packages];
}
```

20.3 VITE RESTART LOGIC
Why do we restart Vite? Because adding new dependencies via `npm install` while the server is running often leads to "Missing dependency" errors in the pre-bundler.

```javascript
/* Pseudocode for provider.restartViteServer() */
async restartViteServer() {
  // 1. Find the PID of the vite process
  const pid = await this.exec('pgrep -f vite');
  
  // 2. Kill it properly
  if (pid) await this.exec(`kill -TERM ${pid}`);
  
  // 3. Wait for port 5173 to free up
  await this.waitForPortFree(5173);
  
  // 4. Start it again in background
  await this.startBackgroundProcess('npm run dev -- --host');
  
  // 5. Wait for health check
  await this.waitForHttp('http://localhost:5173');
}
```

21. SECURITY ARCHITECTURE DEEP DIVE
--------------------------------------------------------------------------------

The Builder handles untrusted code execution. Security is paramount.

21.1 ISOLATION LAYERS
Layer 1: **Cloud Isolation (E2B)**
- Every user session gets a dedicated, isolated microVM.
- These VMs are ephemeral and destroyed after 1 hour of inactivity.
- There is NO shared state between users. User A cannot access User B's files.

Layer 2: **Runtime Isolation (Firecracker)**
- E2B uses Firecracker microVMs (same tech as AWS Lambda).
- This provides hardware-level virtualization, significantly more secure than Docker containers.
- Kernel attacks are contained within the microVM.

Layer 3: **Network Policy**
- Outbound: Allowed (needed for `npm install` and accessing APIs).
- Inbound: Restricted. Only specific ports (5173, 3000) are exposed via secure tunnels (HTTPS) dynamically generated by E2B.
- Use of `localhost` in the browser code is proxied securely.

21.2 DATA PRIVACY
- **Code retention**: We do not persistently store generated user code on our servers. It lives in the ephemeral sandbox and the user's browser memory (Context).
- **Prompt retention**: Prompts are sent to OpenAI but not used for model training (Enterprise agreement/API settings).

21.3 THREAT MODEL & MITIGATIONS
- **Threat**: User generates a crypto miner.
  - **Mitigation**: CPU limits (2 vCPU) make this inefficient. E2B monitoring kills high-load processes.
- **Threat**: User attacks internal network.
  - **Mitigation**: Subnet isolation. The VM cannot see other VMs or the main Volturiano backend server (which runs in a different VPC/environment).

22. FUTURE ROADMAP & IMPROVEMENTS
--------------------------------------------------------------------------------

This pipeline is V1. The following improvements are slated for Q4 2026.

22.1 GRANULAR STREAMING
Currently, we wait for a component to be fully generated before showing it.
**Goal**: Stream the component code token-by-token into the file explorer as it generates.
**Blocker**: Requires a more complex Vite plugin to handle partial files without crashing the build.

22.2 PERSISTENT STORAGE
Currently, refreshing the page destroys the session if the sandbox expires.
**Goal**: Background sync of `src/` folder to S3/Supabase Storage.
**Benefit**: "Resume later" functionality.

22.3 GIT INTEGRATION
**Goal**: "Push to GitHub" button.
**Implementation**:
1. Authenticate user via OAuth.
2. `git init` in sandbox.
3. `git add . && git commit`.
4. `git push origin main`.

22.4 PREVIEW SNAPSHOTS
**Goal**: Automatically take screenshots of the preview iframe.
**Use Case**: Show "Version History" with visual thumbnails to the user.

22.5 MULTI-FILE EDITS (Refactoring)
Currently, `generate-ai-code-stream` edits file-by-file.
**Goal**: Allow "Rename component X to Y" which requires updating X.jsx, and all its importers.
**Solution**: Use a stronger "Refactor Agent" that queries `grep` in the sandbox to find all usages before generating patches.

23. GLOSSARY OF TERMS
--------------------------------------------------------------------------------

- **E2B**: Edge-to-Browser. The cloud infrastructure provider used for sandboxing.
- **HMR**: Hot Module Replacement. Vite feature allowing modules to be updated in the browser without a full page reload.
- **LLM**: Large Language Model (e.g., GPT-4o).
- **MicroVM**: A lightweight virtual machine (Firecracker) starting in milliseconds.
- **Context Window**: The limit of tokens the LLM can "see". We manage this by only sending relevant file contents during edits.
- **System Prompt**: The hidden "instructions" sent to the LLM to define its persona and rules.
- **Zod**: TypeScript-first schema declaration and validation library.

APPENDIX F: IN-MEMORY STATE SCHEMA
--------------------------------------------------------------------------------
The server maintains a global state object `global.sandboxState` to track the active session. This acts as a pseudo-database.

```javascript
/* Global server state structure */
global.sandboxState = {
  // 1. File Cache
  // Acts as the "Source of Truth" for the project.
  // We write to this BEFORE writing to E2B to ensure consistency.
  fileCache: {
    sandboxId: "sbx-123...",
    lastSync: 1715000000000,
    files: {
      "src/App.jsx": {
        content: "import React from 'react'...",
        lastModified: 1715000000100,
        version: 1
      },
      "src/index.css": {
        content: "@tailwind base...",
        lastModified: 1715000000100,
        version: 1
      }
      // ...all other files
    }
  },

  // 2. Active Provider Instance
  // The direct reference to the E2B class instance.
  // NOT serializable (contains socket connections).
  sandbox: [Object E2BProvider],

  // 3. Metadata
  sandboxData: {
    sandboxId: "sbx-123...",
    url: "https://sbx-123.e2b.dev",
    createdAt: "2024-05-06T12:00:00Z",
    template: "react-vite-v1"
  }
};
```

**State Management Rules**:
1. **Singleton**: Only one sandbox is active per server instance in this V1 implementation.
2. **Volatility**: If the Node.js server restarts, this state is lost. The frontend must recreate the sandbox.
3. **Concurrency**: `fileCache` updates are synchronous to prevent race conditions during parallel generation.
