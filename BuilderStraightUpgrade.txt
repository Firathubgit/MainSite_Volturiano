# 1. THE FIVE REAL PROBLEMS

These are not hypothetical. Each one is traced to exact lines of code.

PROBLEM 1: Polish Destroys Premium Components
  Location: `web/server/lib/polish-refinement.js` L9, L106
  Evidence: Server logs show polish broke build TWICE, rolled back to
            unpolished code. User gets zero copywriting on premium components.
  Root:     NON_POLISHABLE_SHELL_FILES only excludes App.jsx and main.jsx.
            Premium components under src/components/premium/ get FULL LLM
            rewrites — shaders, WebGL, complex Framer Motion — all at risk.

PROBLEM 2: Premium Copy Hydration is Broken
  Location: `web/server/lib/registry/registry.js` L369-391 (bundleToFileBlocks)
            `web/server/routes/plan-website-components.js` L496-504 (merge)
  Evidence: propsOverrides does regex on `key = 'value'` patterns — this only
            hits prop defaults, NOT hardcoded JSX strings like "Rivelon" or
            "Welcome to Our Platform". Premium components have copy BAKED into
            JSX body text, not as default prop values.
  Root:     Master Copywriter produces keyContent + props, but merge matches
            by `cc.name === c.name`. Name mismatch = empty props = no copy.

PROBLEM 3: Hardcoded 5-9 Component Cap
  Location: `web/server/routes/plan-website-components.js` L183-189
            `web/server/lib/select-components-v2.js` L107-111, L248-249, L279
  Evidence: Zod schema allows max(30) at L38. The limit is PURELY in prompt
            text: "Simple: 5-6, Medium: 6-7, Complex: 8-9".
  Root:     V2 also caps: "best 5-11 components" (L279), fallback targetSize
            Math.min(9, ...) (L107-111). Both are just strings.

PROBLEM 4: No Intent Classification for Initial Builds
  Location: `web/server/routes/analyze-edit-intent.js` (edit-only)
  Evidence: "Build me an app that manages money" gets the same
            header-hero-features-footer layout as "Coffee shop landing page".
  Root:     No pre-build classification exists. The enhance-prompt route
            enriches text but does not extract layout type or app category.

PROBLEM 5: No Visual Verification
  Location: `web/server/lib/verify-sandbox-build.js` (vite build only)
            `web/server/lib/screenshot.js` (thumbnails only, post-completion)
  Evidence: Blue/blank screens pass verification because vite build succeeds.
            Puppeteer exists but is only used for Supabase thumbnail uploads.
  Root:     Compile-time check catches syntax errors but not runtime rendering
            failures, z-index issues, or blank-screen regressions.

# 2. THE CURRENT PIPELINE (what actually happens today)

  Client (Generation.jsx) orchestrates the full build:

  Step 1: POST /api/enhance-prompt          — LLM enriches user text
  Step 2: POST /api/derive-design-system    — LLM extracts palette/typography
  Step 3: POST /api/select-components       — V1 catalog pick (if premium on)
  Step 4: POST /api/plan-website-components — Produces flat component list +
                                              MPA pages + copywriter pass (merge uses
                                              fuzzy component name match for copy rows)
  Step 5: POST /api/component-bundle (x N)  — Fetch premium component files
          with propsOverrides from plan
  Step 5b: POST /api/hydrate-premium-copy    — Per premium .jsx/.tsx: LLM replaces
          baked-in demo/body copy using keyContent + props + vision (before apply) ✅
  Step 6: POST /api/generate-single-component (x M) — Generate custom JSX
  Step 7: POST /api/render-app              — Deterministic App.jsx shell
  Step 8: POST /api/validate-imports        — Regex import validation
  Step 9: POST /api/apply-ai-code-stream    — SSE pipeline:
          9a. Parse files, sanitize imports, install packages
          9b. Write files to E2B sandbox
          9c. npx vite build (verify)
          9d. Auto-repair loop (up to 5 attempts if build fails)
          9e. Final Polish: full rewrite for non-premium src; copy-only for
              src/components/premium/* (optional explicit premiumPolishPaths) ✅
          9f. Verify again after polish
          9g. If polish broke build: run polish AGAIN with error logs
          9h. If still broken: ROLLBACK to pre-polish snapshot
          9i. Mini-polish (non-premium src only; premium paths skipped) ✅
          9j. Restart Vite, emit COMPLETE

  REMAINING RISK (if hydrate or copy merge fails):
  - Step 5: propsOverrides still does regex on defaults in bundle (hydrate fixes body)
  - Step 9h: Rollback can still drop polish fixes — mitigated by hydrate + premium copy-only polish

  EXPECTED OUTCOME: Copywriter keyContent/props + hydration land user text in premium JSX
  before apply; polish refines without tearing down shaders.

# 3. PREMIUM COPY: WHY IT NEVER LANDS

  THE PROP OVERRIDE ILLUSION
  --------------------------
  `bundleToFileBlocks()` in registry.js L369-391:

    for (const [key, value] of Object.entries(propsOverrides)) {
        const defaultPattern = new RegExp(
            `(${key}\\s*=\\s*)(['"\`])([^'"\`]*)\\2`, 'g'
        );
        content = content.replace(defaultPattern, `$1'${safeValue}'`);
    }

  This regex targets: `propName = 'default value'` patterns.
  It does NOT touch: <h1>Welcome to Rivelon</h1> or text inside JSX body.

  A typical premium component has:
    export default function HeroSplashCursor({ title = "Rivelon" }) {
      return (
        <div>
          <h1>{title}</h1>
          <p>Discover the future of innovation with Rivelon...</p>  // MISSED
          <span>Trusted by 10,000+ Rivelon users</span>             // MISSED
        </div>
      );
    }

  The regex catches `title = "Rivelon"` but misses every hardcoded string
  in the JSX body. The Master Copywriter step (plan-website-components.js
  L425-504) generates replacement text, but it's passed as props that only
  override DEFAULTS. The body text stays "Rivelon" until polish tries to
  fix it — and polish often breaks the build trying.

  THE NAME MISMATCH BUG
  ---------------------
  Plan merge at L496-504:

    const copy = copyResult.components?.find(cc => cc.name === c.name);

  If the copywriter returns "HeroSplash" but the DB component is named
  "HeroSplashCursor", the find() returns undefined. Result: keyContent
  falls back to c.description (generic), props becomes {} (empty).

  FIX: Phase 0 + Phase 1 (below)

# 4. THE POLISH DEATH SPIRAL

  WHAT THE LOGS SHOW (from the "skibidi sigma" build):

  Timeline:
    04:57:17 — Polish starts (15 files, Haiku, concurrency 1)
    04:57:17 to 05:00:21 — 181 seconds polishing 15 files one at a time
    05:00:21 — Polish done. 93,634 chars of output. vite build → EXIT CODE 1
    05:00:21 — "Polish introduced errors, attempting ONE repair pass..."
    05:00:21 to 05:03:21 — SECOND full polish pass (183 seconds)
    05:03:21 — Still fails. ROLLBACK to pre-polish snapshot.
    05:03:21 — Rollback build passes. Mini-polish says NO_CHANGES.
    05:03:56 — Complete. Total duration: 447,461ms (7.4 minutes)

  The user waited 7+ minutes. The result: ZERO copy changes on premium
  components. The entire polish cycle was wasted because:

  1. Polish rewrites ALL files at full depth (restructures, adds CSS, modifies
     shader code) when it should only be fixing TEXT content
  2. "Salvaged raw code response" (L305-310) accepts loose code-like text as
     full file replacement — high risk of breaking imports/exports
  3. Haiku at concurrency 1 serializes ALL 15 files — 12-25s each
  4. The "repair" path is just running polish AGAIN with error logs appended
     to the prompt — it's not a targeted fix, it's another full rewrite
  5. Rollback restores the ORIGINAL files — no copy changes survive

  WHY POLISH BREAKS BUILDS:
  - Model rewrites shader/WebGL math despite instructions not to
  - Model removes or reorganizes imports
  - Model generates responses without <file> tags → "salvage" takes raw
    output as full file content → broken exports
  - Long file names (100+ chars) confuse the output formatter

  FIX: Phase 0 (protect premium) + Phase 4 (targeted polish) + Phase 8
       (efficiency)

  STATUS (2026): Phase 0 + Phase 4 + Phase 8 implemented in code — triage + copy-only
  for standard files, no salvage on repair passes, Haiku concurrency 2 / others 3,
  skip files &lt;500 chars and optional polishSkipPaths, design spec pre-cached in
  apply (repair reuses), mini-polish narrowed to paths changed by main polish.

# 5. THE COMPONENT COUNT CEILING

  HISTORICAL ISSUE (pre–Phase 2):
  - V1 planning used fixed simple/medium/complex bands (~5–9) in prose only.
  - V2 selection used a low targetSize cap and "5–11" wording, limiting variety.

  CURRENT STATE (Phase 2 — implemented):
  - V1 (`plan-website-components.js`): `planSchema` includes `layoutType` with described
    per-archetype bands (e.g. marketing-landing 5–8, web-app 8–20, e-commerce 10–18);
    `SYSTEM_PROMPT` repeats adaptive LAYOUT TYPE & COMPONENT COUNTS; server fills missing
    `layoutType` via `inferLayoutTypeFromPrompt` when needed. Zod still allows
    `.min(1).max(30)` — the model is steered by bands, not by max(30) alone.
  - V2 (`select-components-v2.js`): `targetSize = Math.min(18, Math.max(6, …))`; final
    selection prompts say "6–20 components"; structural selection respects `layoutType`
    (e.g. web-app does not inject hero/footer from the pool the same way as marketing).
  - `enforcePlanStructure(components, layoutType)` dedupes header/hero/footer and orders
    roles; web-app is dedupe-only (no hero/footer injection in that helper).

  COST / QUALITY NOTE (unchanged):
  - More components still mean more polish time and tokens — bands exist so the model
    picks a sane count per layout type instead of racing to the schema max.

  REMAINING IMPROVEMENT:
  - Phase 3 (intent classification route): deterministic layout/complexity hints *before*
    plan + selection, so routing does not rely only on the planner + heuristics.

  STATUS (2026): §5 ceiling addressed by Phase 2 in code. Phase 3 is optional hardening.

# 6. THE INTENT GAP

  HISTORICAL ISSUE (pre–Phase 2 / early prompts):
  - Planning text treated every site like a marketing page: header → hero →
    features → footer, with no first-class “app / dashboard” path.
  - V2 structural enforcement injected header + hero + footer from the pool for all runs.

  CURRENT STATE (partially mitigated — Phase 2 + structural guards):
  - `layoutType` on the plan (`plan-website-components.js` / `planSchema`) and an
    adaptive `SYSTEM_PROMPT`: for `web-app`, copy explicitly says dashboard-style
    sections, hero optional, footer optional; marketing layouts still use header /
    hero / footer when appropriate.
  - `inferLayoutTypeFromPrompt` (`layout-type.js`) heuristically maps prompts such as
    “money management”, “dashboard”, “expense tracker” → `web-app` when the model
    omits `layoutType`.
  - `enforcePlanStructure(…, layoutType)`: dedupe/sort only; `web-app` does not add
    hero/footer in the flatten/mandatory fill — `needHero` / `needFooter` are false
    for `web-app`.
  - `enforceStructuralSelection(…, layoutType)` in `select-components-v2.js`: for
    `web-app`, only **header** is required from the candidate pool; hero/footer are
    not injected from the pool (see `[BUILDER-VERIFY] v2 structural inject`).

  WHAT IS STILL MISSING (why Phase 7 remains on the roadmap):
  - `enhance-prompt.js` does not embed structured intent (Phase 3 uses a dedicated
    `/api/classify-intent` call before plan instead).
  - `derive-design-system.js` still does not set layout type.
  - Blueprint / category bias toward dashboard widgets vs marketing sections is not
    fully encoded in DB presets — V2 selection still depends on catalog tags and LLM
    scoring (`suggestedCategories` from Phase 3 is not wired into V2 yet).

  FIX (roadmap): Phase 7 (stronger app-mode catalog / blueprint bias; optional use
    of `suggestedCategories` / `needsPremiumCatalog` from classify-intent).

  STATUS (2026): Phase 3 steers `layoutType` / `mandatoryStructure` into planning;
  brochure-vs-app is further constrained. Remaining: catalog depth (Phase 7).

# 7. THE BLIND BUILD

  STILL TRUE (compile-only verify):
  `verify-sandbox-build.js` runs `npx vite build --base=./` and returns success,
  logs, exit code — it cannot see runtime rendering.

  WHAT THAT MISSES (unchanged):
  - Blank or near-empty DOM, z-index traps, broken client-only errors, etc.

  MITIGATION (Phase 6 — implemented):
  - `captureForVerification(sandboxUrl)` in `screenshot.js` opens the live sandbox
    URL (same Puppeteer stack as thumbnails), waits for load, and checks DOM heuristics:
    scroll height, visible text length, and presence of img/canvas/svg/video.
  - `apply-ai-code-stream.js` runs this after a **successful** vite verify (post-repair),
    before polish. On likely blank: `SSE_EVENTS.WARNING` + `[BUILDER-VERIFY] visual verify`
    logs. Does **not** fail the build (non-fatal); user still gets a preview.
  - Thumbnail upload (`captureAndUploadScreenshot`) remains separate (Supabase).

  NOT COVERED YET:
  - No auto-repair loop from blank-screen detection (optional follow-up).
  - No VLM aesthetic scoring (roadmap “optional future”).

  STATUS (2026): Phase 6 baseline gate in place; compile-only path is no longer the
  only signal before polish.

# 12. VISION SUMMARY

The Volturiano builder already has the hardest part figured out: a living
community catalog of premium components, a working E2B sandbox pipeline,
cross-provider LLM fallback, deterministic App.jsx rendering, and a multi-
page routing system. These are real, production-grade pieces that competitors
like Lovable do not have.

The gap was never a recursive agent topology or an AST transformation
engine. The gap was reliability — and the Straight Upgrade phases are the
surgical answers, shipped in code for Phases 0–8 and Phase 6:

  - Premium components should arrive in the sandbox with correct copy
    (not "Rivelon") — Phase 0 + Phase 1
  - The system should understand "dashboard app" vs "landing page" and
    plan accordingly — Phase 2 + Phase 3 + Phase 7 (optional catalog / V2
    wiring follow-ups remain where noted in Phase 7)
  - Polish should improve the site, not break it — Phase 0 + Phase 4 + Phase 8
    (optional client `polishSkipPaths` remains)
  - Build verification should catch what users actually see — Phase 6
  - Common LLM mistakes should be caught deterministically — Phase 5

Incremental work still on the roadmap: Phase 9 (duplicate /projects/update
debounce) and the optional items above — quality-of-life, not a different
architecture.

Every phase is a surgical fix to a specific, code-traced problem. No
rewrites. No new frameworks. No academic patterns. Just making the existing
Toyota engine actually run on all cylinders.

The goal is simple: one prompt, one build, one result that looks right
and reads right. Every time.
