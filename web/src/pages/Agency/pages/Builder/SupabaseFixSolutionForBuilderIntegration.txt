## Executive Summary

The Volturiano Builder currently operates with:
- **Local JSON files** for component catalog (52 bundles in `server/lib/registry/bundles/`)
- **Local filesystem** for published sites (`server/pub_sites/`)
- **No authentication** — anyone can build without limits
- **No user data persistence** — builds are ephemeral
- **No community features** — only founder-created components exist

This document defines **18 phases** to migrate the entire builder ecosystem to Supabase, transforming it from a single-user local tool into a scalable, community-driven platform.

**Key Transformations:**

| Area | Current State | Supabase Target |
|------|--------------|-----------------|
| Authentication | None | Email + Google + GitHub OAuth |
| User Profiles | None | Full profiles with avatars, bios, plans |
| Component Storage | Local JSON (52 files) | Supabase `components` table (150 → 10,000+) |
| Component Categories | ~11 basic categories | 40 top-level + 200+ sub-categories with Website-Type Blueprints (100 preselected + unlimited dynamic AI generation) |
| Template Storage | Local JSON (4 files) | Supabase `templates` table (10 → unlimited) |
| Published Sites | Local `pub_sites/` folder | Supabase Storage bucket |
| Build History | None (ephemeral) | `projects` + `snapshots` tables |
| Credits/Billing | None | Stripe + `credit_transactions` table |
| Community | None | Component submissions, template sharing, ratings |
| AI Selection | Single catalog JSON dump | Multi-step progressive narrowing via Supabase queries |

**Supabase Project Details:**
- **Project Name:** VolturianoBuilder
- **Region:** Europe (eu-central-1)
- **URL:** https://bfmqeuczlipocjqtzawj.supabase.co
- **Auth Providers:** Email/Password, Google OAuth, GitHub OAuth
- **Storage Buckets:** `published-sites`, `component-previews`, `user-avatars`, `template-previews`

## Phase S2: Database Schema — Core Tables

**Status:** ✅ COMPLETED
**Timeline:** 2-3 days
**Priority:** CRITICAL
**Dependencies:** Phase S1

### S2.1 Overview & Architectural Vision

The transition to Supabase is not merely about moving from local JSON files to a cloud database; it is a fundamental architectural shift that transforms the Volturiano Builder from a single-user prototype into a scalable, multi-tenant B2B SaaS platform.

Creating the core database tables is the most critical step in this entire migration. These tables form the unshakable backbone of every single feature in our ecosystem:
- **User Identity & Progression:** Moving beyond anonymous sessions to rich user profiles that track credits, reputation, and subscription tiers.
- **Persistent Project State:** Every prompt, component selection, and design system tweak must be safely stored so users can leave and return to their work seamlessly, without losing the context of the AI generation pipeline.
- **The "Published" Source of Truth:** A highly optimized table for live sites, ensuring zero downtime and rapid routing for any published URL. By enforcing uniqueness here, we prevent devastating slug collisions.
- **Monetization Engine:** Precise tracking of credit usage, Stripe transactions, and guest rate limits is absolutely essential to build a profitable, sustainable business model.

By getting this schema perfectly right the first time, we eliminate massive technical debt down the road and empower developers to build robust frontend features with total confidence in the backend constraints.

---

### Ÿ›️ IMPLEMENTATION DIRECTIVE FOR DEVELOPERS Ÿ›️
**(Read this before writing code for Phase 2)**

This phase requires binding the new Supabase tables to the actual React frontend and Node.js backend. Creating the tables in the Supabase Dashboard is only 50% of the work. The remaining 50% is wiring the codebase to securely read and write to these tables.

**What MUST be implemented NOW in the codebase (Phase 2 core):**
1. **Projects Integration:** The AI Generation pipeline (`Generation.jsx`) must create a `projects` row when a generation starts. It must continually update the row as the `design_system` and `generated_files` are created by the streaming API.
2. **Snapshots Integration:** The chat orchestrator must save a row to the `snapshots` table every time the AI delivers a code response, allowing the user to seamlessly scrub backward in time to previous iterations.
3. **Publishing Integration:** The `/api/publish-site` backend endpoint must be rewritten to insert a row into `published_sites` when a site goes live, validating slug uniqueness against the database rather than the local filesystem.
4. **Basic Credit Checking:** When the user clicks "Generate", the frontend should check their profile (`daily_credits_used` vs `daily_credits_limit`). If they have exceeded their limit and are not on a premium plan, the generation must be blocked with an upgrade prompt.

**What is DEFERRED to future phases (DO NOT BUILD YET):**
1. **Stripe Billing Webhooks (Deferred to Phase S12):** Do not build the Stripe checkout session or the associated webhook handler yet. The `stripe_customer_id`, `stripe_subscription_id`, and `plan` fields exist in the database schema strictly to future-proof the design. For now, simply mock a user's premium status by manually editing their `plan` field to `'pro'` in the Supabase dashboard.
2. **GitHub OAuth Repository Pushing (Deferred to Phase S14):** The `github_access_token` column is ready, but the logic to automatically create repositories and push generated React code to the user's personal GitHub account will be built later.
3. **Custom Domains (Deferred indefinitely):** The `custom_domain` field in the `published_sites` table is present, but the complex DNS provisioning logic and automated SSL certificate generation via Vercel/Cloudflare is deferred.

### S2.2 Table: profiles
**Priority:** Critical

**Why this matters:** The `profiles` table is the heart of the user experience. It bridges the barebones Supabase `auth.users` identity with Volturiano-specific business logic. By tracking `total_credits_remaining`, `plan`, and `reputation_score` directly on the profile, frontend developers can instantly conditionalize UI elements (e.g., hiding Premium components for Free users, or showing a "Top Contributor" badge in the community hub) without needing multiple complex joins. This table is automatically populated via a PostgreSQL trigger the exact millisecond a user signs up.

```sql
CREATE TABLE profiles (
  -- Identity (linked to Supabase Auth)
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,

  -- Personal Information
  display_name TEXT,
  full_name TEXT,
  username TEXT UNIQUE,
  bio TEXT,
  avatar_url TEXT,
  website_url TEXT,
  location TEXT,

  -- Plan & Credits
  plan TEXT DEFAULT 'free' CHECK (plan IN ('free', 'pro', 'enterprise', 'admin')),
  total_credits_remaining INTEGER DEFAULT 0,
  daily_credits_used INTEGER DEFAULT 0,
  daily_credits_limit INTEGER DEFAULT 15,
  daily_credits_reset_at DATE DEFAULT CURRENT_DATE,

  -- Stripe Billing
  stripe_customer_id TEXT,
  stripe_subscription_id TEXT,

  -- GitHub Integration
  github_access_token TEXT,   -- encrypted at rest
  github_username TEXT,

  -- Community Stats
  components_submitted INTEGER DEFAULT 0,
  templates_created INTEGER DEFAULT 0,
  total_builds INTEGER DEFAULT 0,
  reputation_score INTEGER DEFAULT 0,

  -- Preferences
  preferred_mode TEXT DEFAULT 'premium' CHECK (preferred_mode IN ('free', 'hybrid', 'premium')),
  preferred_theme TEXT DEFAULT 'dark',
  onboarding_completed BOOLEAN DEFAULT FALSE,

  -- Timestamps
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  last_active_at TIMESTAMPTZ DEFAULT NOW()
);

-- Auto-create profile on user signup
CREATE OR REPLACE FUNCTION handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO profiles (id, display_name, avatar_url, full_name)
  VALUES (
    NEW.id,
    COALESCE(NEW.raw_user_meta_data->>'name', NEW.raw_user_meta_data->>'full_name', split_part(NEW.email, '@', 1)),
    COALESCE(NEW.raw_user_meta_data->>'avatar_url', NEW.raw_user_meta_data->>'picture'),
    COALESCE(NEW.raw_user_meta_data->>'full_name', NEW.raw_user_meta_data->>'name')
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION handle_new_user();
```

### S2.3 Table: projects
**Priority:** Critical

**Why this matters:** A "Project" is an overarching workspace. It is where the user iterates on their AI prompt, configures the `design_system`, and builds a component plan. By storing `generated_files` as a robust JSONB object, our backend engineers can instantly spin up the preview sandbox simply by passing this payload to the E2B MicroVM, completely removing the need for fragile, complex file-system gymnastics on our Node server.

```sql
CREATE TABLE projects (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES profiles(id) ON DELETE CASCADE,

  -- Project Info
  name TEXT NOT NULL,
  prompt TEXT,
  enhanced_prompt TEXT,
  industry TEXT,

  -- AI Pipeline State
  design_system JSONB,
  component_plan JSONB,
  selected_components JSONB,
  generated_files JSONB,

  -- Build State
  sandbox_id TEXT,
  build_status TEXT DEFAULT 'draft' CHECK (build_status IN (
    'draft', 'generating', 'building', 'preview', 'published', 'failed', 'archived'
  )),
  build_mode TEXT DEFAULT 'premium' CHECK (build_mode IN ('free', 'hybrid', 'premium')),

  -- Publishing
  published_url TEXT,
  published_slug TEXT,
  published_at TIMESTAMPTZ,

  -- GitHub
  github_repo_url TEXT,
  github_pushed_at TIMESTAMPTZ,

  -- Metadata
  thumbnail_url TEXT,
  total_components INTEGER DEFAULT 0,
  total_files INTEGER DEFAULT 0,
  build_duration_ms INTEGER,

  -- Timestamps
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Index for fast user lookups
CREATE INDEX idx_projects_user_id ON projects(user_id);
CREATE INDEX idx_projects_build_status ON projects(build_status);
CREATE INDEX idx_projects_published_slug ON projects(published_slug);
```

### S2.4 Table: published_sites
**Priority:** Critical

**Why this matters:** This is the highest-stakes table in the production environment. When a visitor goes to a Volturiano-hosted URL, our routing edge function will immediately hit this table using the `slug`. It also explicitly links back to the `user_id` so we can give creators a comprehensive dashboard showing their live, active sites alongside accurate view-count analytics.

```sql
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;
```

## Phase S7: ULTRA Mega-Category Taxonomy & Website-Type Blueprint System (200+ Categories)

**Status:** COMPLETED ✅ (2026-02-27)
**Timeline:** 2-3 weeks
**Priority:** CRITICAL — Enables infinite scaling
**Dependencies:** Phase S6

### S7.1 Overview & Vision

Build the most comprehensive, hierarchical component taxonomy system ever created for an AI website builder. This system goes far beyond simple categories — it introduces **Website-Type Blueprints** that define exactly which component categories a given website type needs, **Industry Verticals** that map real-world business sectors to component preferences, and a **Component Compatibility Graph** that tells the AI which components work well together.

**The goal:** When a user types "Build me a SaaS landing page for a fintech startup," the system instantly knows:
- Website type = SaaS Landing Page → needs hero, features, pricing, testimonials, CTA, footer
- Industry = Fintech → prefer dark mode, corporate-trust palette, stats-heavy, compliance-friendly
- Compatible components → these 5 hero components pair well with these 3 pricing components

This is the difference between 100 components and 100,000 components scaling gracefully.

**CRITICAL — Dynamic Blueprint Generation (No Hard Limits):**

The 100 preselected Website-Type Blueprints defined in S7.4 are **guiding presets** — a curated starting point covering the most common website archetypes. They are NOT a ceiling or a hard limit on what users can build. If a client requests a website type that falls **outside** the predefined 100 blueprints (e.g., "Build me a marine biology research portal with interactive specimen catalogs" or "Create a drone racing league hub with live telemetry dashboards"), the system's AI **dynamically generates a custom blueprint on-the-fly** by:

1. **Analyzing the user prompt** to extract the intent, industry context, and functional requirements
2. **Reasoning over the full 40-category taxonomy** (S7.2) and 200+ sub-categories (S7.3) to determine which component categories are required vs. optional for this unique website type
3. **Cross-referencing Industry Verticals** (S7.6) to infer style preferences, compliance needs, and component priorities — even if the exact industry isn't in the predefined list, the AI maps it to the closest vertical(s)
4. **Consulting the Component Compatibility Graph** (S7.7) to ensure the dynamically assembled set of components will work well together visually and functionally
5. **Generating a complete ephemeral blueprint** with `required_categories`, `optional_categories`, `recommended_component_count`, style defaults, and layout order — structurally identical to a preseeded blueprint, but created in real-time

This means the system can build **literally any type of website** — the 100 preselected blueprints simply accelerate the process for common cases by skipping the dynamic generation step and going straight to a known-good recipe. For novel or niche requests, the AI is fully capable of assembling the perfect blueprint from scratch, using the taxonomy, verticals, and compatibility data as its knowledge base.

> **Think of it this way:** The 100 blueprints are like recipes in a cookbook. They make cooking faster because you don't have to think. But the AI is a master chef — if you ask for a dish not in the book, it knows every ingredient (category), every flavor pairing (compatibility), and every dietary restriction (industry vertical) to create a perfect custom recipe on the spot.

### S7.4 Top 100 Website Types — The Blueprint Matrix (Guiding Presets)

This is the core scaling innovation. The **100 preselected website types** below serve as **guiding presets** — curated, battle-tested blueprints covering the most commonly requested website archetypes across all major industries. Each blueprint maps a website type to a predefined list of component categories it typically needs, giving the AI a massive head-start.

**In practice, this means:**
- **~80% of requests** will match one of these 100 presets (fast path — instant blueprint lookup)
- **~20% of requests** will trigger dynamic blueprint generation (creative path — AI assembles a custom recipe)

### S7.5 Website Type Blueprints Table

```sql
CREATE TABLE website_type_blueprints (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  slug TEXT UNIQUE NOT NULL,                  -- e.g., 'saas-landing', 'restaurant', 'portfolio'
  name TEXT NOT NULL,                          -- e.g., 'SaaS Landing Page'
  description TEXT,
  
  -- Component Recipe
  required_categories JSONB NOT NULL,          -- ["hero","header","feature","pricing","footer"]
  optional_categories JSONB,                   -- ["blog","newsletter","stats"]
  recommended_component_count INTEGER DEFAULT 6,
  min_components INTEGER DEFAULT 4,
  max_components INTEGER DEFAULT 12,
  
  -- Style Defaults
  default_color_mode TEXT DEFAULT 'dark',
  default_color_theme TEXT,                    -- FK slug to color_themes
  default_typography TEXT DEFAULT 'modern-sans',
  
  -- Industry Mapping
  primary_industries JSONB,                    -- ["tech","startup","saas"]
  secondary_industries JSONB,                  -- ["fintech","edtech"]
  
  -- Popularity & Quality
  popularity_score FLOAT DEFAULT 5.0,          -- How often users build this type
  usage_count INTEGER DEFAULT 0,
  
  -- AI Hints
  prompt_keywords JSONB,                       -- Keywords that trigger this blueprint
  negative_keywords JSONB,                     -- Keywords that should NOT match
  example_prompts JSONB,                       -- ["Build me a SaaS landing page", ...]
  
  -- Scaling
  component_layout_order JSONB,                -- ["header","hero","feature","pricing","testimonial","faq","cta","footer"]
  
  -- Dynamic Generation Tracking
  is_ai_generated BOOLEAN DEFAULT FALSE,       -- TRUE if this blueprint was dynamically created by AI
  generated_from_prompt TEXT,                   -- The original user prompt that triggered dynamic generation
  generation_confidence FLOAT,                 -- AI's confidence score when it generated this blueprint
  
  is_active BOOLEAN DEFAULT TRUE,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_blueprints_slug ON website_type_blueprints(slug);
CREATE INDEX idx_blueprints_popularity ON website_type_blueprints(popularity_score DESC);
CREATE INDEX idx_blueprints_keywords ON website_type_blueprints USING GIN(prompt_keywords);
CREATE INDEX idx_blueprints_ai_generated ON website_type_blueprints(is_ai_generated);
```

### S7.5.1 Dynamic Blueprint Generation (AI Fallback for Unknown Website Types)

When the AI pipeline (Phase S8, Step 1) cannot confidently match a user's prompt to any of the 100 preselected blueprints (confidence < 0.6), the system enters **Dynamic Blueprint Generation** mode. This is the mechanism that makes the builder truly unlimited.

**How Dynamic Blueprint Generation Works:**

```
User prompt: "Build me a marine biology research portal with interactive specimen catalogs and field data collection"

→ Step 1: AI scans 100 preselected blueprints → no confident match (confidence = 0.3)
→ Step 2: AI enters Dynamic Blueprint Generation mode
→ Step 3: AI analyzes the prompt and reasons:
    - Primary purpose: Research portal → needs content display, data organization
    - "specimen catalogs" → gallery, card, table, filter categories
    - "interactive" → interactive features, 3D/media elements  
    - "field data collection" → forms, application shell, dashboard widgets
    - Research context → clean academic feel, data-heavy, professional
→ Step 4: AI assembles a custom blueprint:
    {
      slug: "ai-generated-marine-research-portal",
      name: "Marine Biology Research Portal",
      required_categories: ["header", "hero", "gallery", "card", "table", "contact", "footer"],
      optional_categories: ["feature", "sidebar", "dashboard-widget", "map", "blog"],
      recommended_component_count: 8,
      default_color_mode: "light",
      default_color_theme: "ocean-breeze",
      default_typography: "modern-sans",
      primary_industries: ["education", "science"],
      is_ai_generated: true,
      generation_confidence: 0.87
    }
→ Step 5: Pipeline continues with this custom blueprint exactly like a preselected one
```

**The AI has all the data it needs to generate perfect blueprints:**
- **40 categories with descriptions** (S7.2) — it knows what each category contains
- **200+ sub-categories** (S7.3) — it can be granular about specific component types
- **Industry Verticals** (S7.6) — it knows style preferences per industry, even for novel industries by mapping to the closest known vertical
- **Component Compatibility Graph** (S7.7) — it knows which components pair well
- **Color Themes** (S7.8) — it can select the perfect visual theme

**Dynamic blueprints can optionally be persisted:**
If a dynamically generated blueprint is used successfully (build completes, user is satisfied), it can be saved to the `website_type_blueprints` table with `is_ai_generated = TRUE`. Over time, popular AI-generated blueprints can be promoted to official presets, making the system self-improving.

```sql

  'marine-research-portal',
  'Marine Biology Research Portal',
  'AI-generated blueprint for academic/scientific research portals with specimen catalogs and data collection',
  '["header","hero","gallery","card","table","contact","footer"]',
  '["feature","sidebar","dashboard-widget","map","blog"]',
  8, 5, 11,
  'light', 'ocean-breeze', 'modern-sans',
  '["education","science","research"]',
  '["research","portal","biology","specimen","catalog","academic","science"]',
```

### S7.7 Component Compatibility Graph

```sql
CREATE TABLE component_compatibility (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  component_a_id TEXT NOT NULL,                -- component_id from components table
  component_b_id TEXT NOT NULL,
  compatibility_score FLOAT DEFAULT 0.5,       -- 0.0 = incompatible, 1.0 = perfect pair
  relationship TEXT DEFAULT 'neutral' CHECK (relationship IN (
    'perfect-pair',      -- These two look amazing together
    'complementary',     -- Good combo
    'neutral',           -- No strong preference
    'style-clash',       -- Colors/typography conflict
    'incompatible'       -- Never pair these (e.g., two heroes)
  )),
  notes TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(component_a_id, component_b_id)
);

CREATE INDEX idx_compat_a ON component_compatibility(component_a_id);
CREATE INDEX idx_compat_b ON component_compatibility(component_b_id);
CREATE INDEX idx_compat_score ON component_compatibility(compatibility_score DESC);
```

### S7.9 Component Variant System

```sql
-- Add variant support to existing components table
ALTER TABLE components
ADD COLUMN IF NOT EXISTS variant_of TEXT,            -- Parent component_id (NULL if original)
ADD COLUMN IF NOT EXISTS variant_label TEXT,          -- e.g., 'dark', 'compact', 'animated'
ADD COLUMN IF NOT EXISTS variant_order INTEGER DEFAULT 0;

CREATE INDEX IF NOT EXISTS idx_components_variant_of ON components(variant_of);
```

## Phase S8: ULTRA Multi-Step AI Selection Pipeline (Supabase-Backed)

**Status:** ✅ COMPLETED
**Timeline:** 3-4 weeks (Completed early via Multi-Agent Prompting)
**Priority:** CRITICAL (Future Architecture)
**Dependencies:** Phase S6, Phase S7

### S8.1 Overview & Architecture Vision

Transform the "dump entire catalog JSON to LLM" approach into an intelligent, progressive, multi-step selection pipeline. The new pipeline uses **7 steps** instead of 5, incorporating the new Website-Type Blueprints, Industry Verticals, and Component Compatibility Graph from Phase S7. This pipeline is designed to scale from 61 components today to 50,000+ components without degradation.

**Key Principle:** At every step, the data sent to the LLM gets *smaller and more relevant*, never bigger. The LLM only sees what it needs to make the next decision.

```
Current Approach (BAD at scale):
  1 step → dump 73KB of ALL component metadata → LLM picks 6 → done
  Problem: At 10,000 components this would be 14MB of JSON

New Approach (SCALES INFINITELY):
  Step 1: Detect website type → ~1KB (blueprint name)
  Step 2: Load blueprint categories → ~2KB (category list)
  Step 3: LLM refines categories → ~2KB (subset)
  Step 4: Query matching components → ~10KB (metadata only)
  Step 5: Industry + style scoring → ~8KB (top 30)
  Step 6: Compatibility check → ~5KB (validated set)
  Step 7: Bundle fetch → ~60KB (only selected code)
  Total to LLM: ~28KB vs 14MB = 500x reduction
```

### S8.2 The 7-Step Selection Pipeline

```
Step 1: WEBSITE TYPE DETECTION + DYNAMIC FALLBACK (NEW)
  Input: User prompt + design system
  Query: SELECT slug, name, prompt_keywords, required_categories 
         FROM website_type_blueprints WHERE is_active = true
  LLM matches: User prompt → 1-2 blueprints from 100+ available (preselected + AI-generated)
  Data to LLM: ~3KB (blueprint names + keywords only)
  Output: Blueprint slug (e.g., 'saas-landing')
  
  DYNAMIC FALLBACK (confidence < 0.6):
    If no preselected blueprint matches confidently, the AI dynamically
    generates a custom blueprint on-the-fly using the full category taxonomy,
    industry verticals, and compatibility data (see S7.5.1).
    The pipeline continues seamlessly with the AI-generated blueprint.
    Output: Ephemeral or persisted custom blueprint

Step 2: BLUEPRINT CATEGORY LOADING (NEW)
  Input: Matched blueprint slug
  Query: SELECT required_categories, optional_categories, 
         recommended_component_count, default_color_mode
         FROM website_type_blueprints WHERE slug = ?
  Result: Pre-defined category list (e.g., ["hero","header","feature","pricing","testimonial","faq","cta","footer"])
  Data: ~1KB (no LLM call needed — deterministic lookup)

Step 3: CATEGORY REFINEMENT (LLM)
  Input: Blueprint categories + user prompt specifics
  Query: SELECT slug, name, component_count, description
         FROM component_categories WHERE slug IN (blueprint.required + blueprint.optional)
  LLM refines: Adds/removes 1-2 categories based on user's unique needs
  Data to LLM: ~2KB (category names with counts)
  Output: Final 5-10 category slugs

Step 4: INDUSTRY-AWARE COMPONENT FILTERING (Database-side)
  Input: Final categories + detected industry vertical
  Query: SELECT component_id, name, description, visual_description, 
                mood_tone, color_mode, suitable_for, quality_score
         FROM components 
         WHERE category IN (...final_categories)
           AND status = 'active'
           AND (suitable_for @> '["detected-industry"]' 
                OR suitable_for IS NULL)
         ORDER BY quality_score DESC
         LIMIT 80
  Result: 10,000 → ~80 components (metadata only, no code)
  Data: ~15KB

Step 5: THEME & STYLE SCORING (Database + LLM)
  Input: 80 candidates + design system (colors, typography, mood)
  Query: Apply scoring formula:
    score = (quality_score * 0.3) 
          + (color_mode_match * 0.2) 
          + (warmth_match * 0.15) 
          + (industry_match * 0.2) 
          + (usage_count_normalized * 0.15)
  LLM reviews top 30 and selects 6-10 finalists
  Data to LLM: ~10KB (top 30 with visual descriptions)

Step 6: COMPATIBILITY VALIDATION (NEW — Database-side)
  Input: 6-10 selected component IDs
  Query: SELECT component_a_id, component_b_id, compatibility_score, relationship
         FROM component_compatibility
         WHERE component_a_id IN (...selected) AND component_b_id IN (...selected)
  Check: Flag any 'style-clash' or 'incompatible' pairs
  Auto-swap: Replace incompatible components with next-best alternative
  Data: ~2KB (no LLM call)

Step 7: BUNDLE FETCH (Database-side)
  Input: Final 6-10 validated component IDs
  Query: SELECT component_id, bundle_code, requires
         FROM components WHERE component_id IN (...)
  Result: Actual code for 6-10 selected components
  Data: ~50-100KB (only what's needed)
```

```javascript
/**
 * Step 1: Detect website type from user prompt
 */
async function detectWebsiteType(prompt, designSystem) {
  const { data: blueprints } = await supabaseAdmin
    .from('website_type_blueprints')
    .select('slug, name, prompt_keywords, primary_industries, description')
    .eq('is_active', true)
    .order('popularity_score', { ascending: false });

  // Send compact blueprint list to LLM for matching
  const match = await llm.matchWebsiteType(prompt, designSystem, blueprints);
  
  // DYNAMIC BLUEPRINT GENERATION FALLBACK
  // The 100 preselected blueprints are guiding presets, not a hard limit.
  // If the user's request doesn't match any preset confidently,
  // the AI dynamically generates a custom blueprint on-the-fly.
  if (!match || match.confidence < 0.6) {
    console.log('[Pipeline] No confident blueprint match — entering Dynamic Blueprint Generation');
    const dynamicBlueprint = await generateDynamicBlueprint(prompt, designSystem);
    return dynamicBlueprint; // { slug: 'ai-generated-...', confidence: 0.85, isDynamic: true }
  }
  
  return match; // { slug: 'saas-landing', confidence: 0.92 }

/**
 * Step 2: Load blueprint — deterministic, no LLM needed

async function loadBlueprint(blueprintSlug) {

    .from('website_type_blueprints')
    .select('*')
    .eq('slug', blueprintSlug)
    .single();
  return blueprint;
}

/**
 * Step 3: Refine categories with LLM
 */
async function refineCategories(blueprint, prompt, designSystem) {
  const allCategories = [
    ...blueprint.required_categories,
    ...(blueprint.optional_categories || [])
  ];

  const { data: categoryDetails } = await supabaseAdmin
    .from('component_categories')
    .select('slug, name, component_count, description')
    .in('slug', allCategories)
    .eq('is_active', true);

  const refined = await llm.refineCategories(prompt, designSystem, categoryDetails, blueprint);
  return refined; // ['hero', 'header', 'feature', 'pricing', 'testimonial', 'faq', 'footer']
}

/**
 * Step 4: Industry-aware filtering
 */
async function filterByIndustry(categories, industrySlug) {
  const query = supabaseAdmin
    .from('components')
    .select('component_id, name, description, visual_description, mood_tone, color_mode, color_warmth, suitable_for, quality_score, usage_count, variant_of, variant_label')
    .in('category', categories)
    .eq('status', 'active')
    .is('variant_of', null)  // Only originals, not variants
    .order('quality_score', { ascending: false })
    .limit(80);

  // Optionally filter by industry suitability
  if (industrySlug) {
    query.contains('suitable_for', [industrySlug]);
  }

  const { data } = await query;
  return data;
}

/**
 * Step 5: Theme & style scoring + LLM final selection
 */
async function scoreAndSelect(candidates, designSystem, prompt) {
  // Score each candidate
  const scored = candidates.map(c => {
    let score = (c.quality_score || 5) * 0.3;
    
    // Color mode match
    if (designSystem.colorMode && c.color_mode === designSystem.colorMode) score += 2;
    
    // Warmth match
    if (designSystem.warmth && c.color_warmth === designSystem.warmth) score += 1.5;
    
    // Usage popularity
    score += Math.min((c.usage_count || 0) / 100, 1.5);
    
    return { ...c, computed_score: score };
  });

  // Sort by computed score, take top 30
  scored.sort((a, b) => b.computed_score - a.computed_score);
  const top30 = scored.slice(0, 30);

  // LLM picks final 6-10 from top 30
  const selected = await llm.selectFinalComponents(prompt, designSystem, top30);
  return selected;
}

 * Step 6: Compatibility validation
 */

    .select('component_a_id, component_b_id, relationship, compatibility_score')
    .in('component_a_id', selectedIds)
    .in('component_b_id', selectedIds)
    .in('relationship', ['style-clash', 'incompatible']);

  if (conflicts && conflicts.length > 0) {
    console.warn('[Pipeline] Compatibility conflicts detected:', conflicts);
    // Auto-swap logic: replace lower-quality component in conflicting pair
    // ... swap logic here ...
  }
  
  return selectedIds; // validated (or swapped) IDs
}

/**
 * Step 7: Fetch bundles
 */
async function fetchBundles(componentIds) {
  const { data } = await supabaseAdmin
    .from('components')
    .select('component_id, bundle_code, requires')
    .in('component_id', componentIds);
  return data;
}

 * MAIN PIPELINE ORCHESTRATOR
 */
export async function selectComponentsV2(prompt, designSystem) {

  // Step 1: Detect website type (preselected preset OR dynamic AI-generated blueprint)
  const websiteType = await detectWebsiteType(prompt, designSystem);
  console.log(`[Pipeline] Detected: ${websiteType.slug} (${(websiteType.confidence * 100).toFixed(0)}%)${websiteType.isDynamic ? ' [DYNAMIC — AI-generated blueprint]' : ' [PRESET]'}`);

  // Step 2: Load blueprint (works identically for preselected and AI-generated blueprints)
  const blueprint = websiteType.isDynamic
    ? await loadOrCreateDynamicBlueprint(websiteType.slug, prompt, designSystem)
    : await loadBlueprint(websiteType.slug);

  // Step 3: Refine categories
  const categories = await refineCategories(blueprint, prompt, designSystem);

  console.log(`[Pipeline] Selected: ${selected.length} components`);

  // Step 6: Compatibility check
  const validated = await validateCompatibility(selected.map(c => c.component_id));

  // Step 7: Fetch bundles
  const bundles = await fetchBundles(validated);

  console.timeEnd('[Pipeline] Total selection time');
  
  return {
    websiteType: websiteType.slug,
    blueprint: blueprint.name,

}
```

```javascript
const CACHE_TTL = {

// Cache implementation
const cache = new Map();

async function cachedQuery(key, ttl, queryFn) {
  const cached = cache.get(key);
  if (cached && Date.now() - cached.time < ttl * 1000) {
    return cached.data;
  }
  const data = await queryFn();
  cache.set(key, { data, time: Date.now() });
  return data;
}

// Usage in pipeline:

  supabaseAdmin.from('website_type_blueprints').select('*').eq('is_active', true)
```

### S8.6 Fallback Strategy

```
Step 3 fails → Skip refinement, use blueprint categories as-is
Step 4 fails → Fetch ALL active components (capped at 200), no industry filter
Step 5 fails → Skip scoring, select by quality_score only
Step 6 fails → Skip compatibility check, proceed with selection
Step 7 fails → Fatal error — cannot proceed without code bundles
```

### S9.2 Component Lifecycle State Machine

Every community component follows a strict state machine. Transitions are enforced at the database level via CHECK constraints and at the application level via the API.

```
                                ┌─────────────┐
                    ┌──────────→│  DEPRECATED │──────────→ ARCHIVED
                    │           └─────────────┘
                    │                  ↑
                    │           (admin/author)
                    │
 ┌──────┤     ┌────────────┤     ┌──────────┤     ┌────────┤     ┌────────┐
 │ DRAFT│────→│ PROCESSING │────→│ PENDING  │────→│APPROVED│────→│ ACTIVE │
 └──────┘     └────────────┘     │  REVIEW  │     └────────┘     └────────┘
   ↑                             └──────────┘          │               │
   │                                  │                │               │
   │                                  ↓                │               ↓
   │                             ┌──────────┤          │         ┌──────────┐
   └─────────(resubmit)─────────│ REJECTED │          │         │ FLAGGED  │
                                 └──────────┘          │         └──────────┘
                                                       │               │
                                                       ↓               ↓
                                                 ┌──────────┤   (admin review)
                                                 │ ARCHIVED │
                                                 └──────────┘
```

**State definitions and allowed transitions:**

| State | Description | Who Can Transition | Next States |
|-------|-------------|-------------------|-------------|
| `draft` | User is editing, not yet submitted | Author | `processing` |
| `processing` | Async LLM analysis running | System only | `pending_review`, `rejected` (auto, quality <4) |
| `pending_review` | Awaiting admin review (quality 4-7.9) | System only | `approved`, `rejected` |
| `approved` | Passed review, waiting for auto-activation | Admin, System (auto, quality ‰8) | `active` |
| `active` | Live, visible to AI pipeline and browse UI | System (auto after approval) | `deprecated`, `flagged`, `archived` |
| `rejected` | Failed review or auto-rejected | Admin, System | `draft` (resubmit allowed) |
| `flagged` | Reported by users, under admin review | Admin (after user report) | `active` (false flag), `archived` (confirmed) |
| `deprecated` | Author disabled, but templates still referencing it can use it | Author, Admin | `archived`, `active` (re-enable) |
| `archived` | Fully removed from all queries | Author, Admin | — (terminal state for components; authors can resubmit as new) |

**Database enforcement:**

```sql
-- Status CHECK constraint on community_submissions
ALTER TABLE community_submissions
  ADD CONSTRAINT valid_status_transition
  CHECK (status IN ('draft', 'processing', 'pending_review', 'approved', 'rejected', 'flagged', 'active', 'deprecated', 'archived'));
```

### S9.3 The Complete Submission Flow — Sync/Async Split

The submission is split into **synchronous** (Steps 1-5, <500ms) and **asynchronous** (Steps 6-8, 10-30s) phases. The user gets immediate feedback and real-time progress updates via SSE.

```
┌──────────────────────────────────────────────────────────────────────┐
```

### S9.4 Synchronous Submission Handler (Fast Path, <500ms)

This route validates, deduplicates, persists the submission record, and enqueues the async analysis job. It returns immediately so the user is never blocked.

```javascript
// server/routes/community/submit-component.js

import { supabaseAdmin } from '../../lib/supabase-admin.js';
import { createHash } from 'crypto';

// ─── Import whitelist must match apply-ai-code-stream.js EXACTLY ───
const ALLOWED_PACKAGES = new Set([
  'react', 'react-dom', 'react/jsx-runtime', 'react/jsx-dev-runtime',
  'framer-motion', 'lucide-react', 'react-router-dom', 'react-icons',
  'clsx', 'tailwind-merge', 'cobe', 'color-bits',
  '@radix-ui/react-icons', 'ogl', 'three',
  '@react-three/fiber', '@react-three/drei'
]);

// ─── Dangerous patterns that MUST NOT appear in submitted code ───
const DANGEROUS_PATTERNS = [
  /\beval\s*\(/,
  /\bnew\s+Function\s*\(/,
  /\bdocument\.cookie\b/,
  /\bwindow\.location\s*=/,
  /\blocalStorage\b/,
  /\bsessionStorage\b/,
  /\bfetch\s*\(\s*['"`]https?:\/\//,  // external fetch
  /\bXMLHttpRequest\b/,
  /\bnew\s+WebSocket\s*\(\s*['"`]ws/,
  /\bimport\s*\(/,                     // dynamic import
  /\bdangerouslySetInnerHTML\b/,
  /\.innerHTML\s*=/,
  /\brequire\s*\(/,
  /\bchild_process\b/,
  /\bprocess\.env\b/,
];

/**
 * POST /api/community/submit-component
 * 
 * SYNCHRONOUS — Returns submission_id in <500ms.
 * Actual LLM analysis runs asynchronously via job queue.
 * 
 * Body: { name, description?, categoryHint?, code, thumbnail? (base64), video? (base64) }
 * Auth: Required (JWT in Authorization header)
 * Response: { success, submissionId, message }
 */
export default async function submitComponent(req, res) {
  const userId = req.user?.id; // Extracted from JWT by auth middleware
  if (!userId) return res.status(401).json({ success: false, error: 'Authentication required' });

  const { name, description, categoryHint, code, thumbnail, video } = req.body;

  // ─── VALIDATION (all sync, <50ms) ───

  // 1. Required fields
  if (!name || !code) {
    return res.status(400).json({ success: false, error: 'name and code are required' });
  }
  if (name.length < 3 || name.length > 100) {
    return res.status(400).json({ success: false, error: 'Name must be 3-100 characters' });
  }
  if (code.length < 100) {
    return res.status(400).json({ success: false, error: 'Code must be at least 100 characters' });
  }
  if (code.length > 100000) {
    return res.status(400).json({ success: false, error: 'Code must be under 100KB' });
  }

  // 2. Must contain a valid JSX export
  if (!/export\s+default\s+/m.test(code)) {
    return res.status(400).json({
      success: false,
      error: 'Code must contain an export default statement',
      fixHint: 'Add "export default function YourComponent() { ... }" to your code'
    });
  }

  // 3. Code security scan — match ALLOWED_PACKAGES from apply-ai-code-stream.js
  const importRegex = /import\s+(?:[\s\S]*?\s+from\s+)?['"]([^'"]+)['"]/g;
  let match;
  const violations = [];
  while ((match = importRegex.exec(code)) !== null) {
    const pkg = match[1];
    if (pkg.startsWith('.') || pkg.startsWith('/')) continue; // relative imports OK
    const basePkg = pkg.startsWith('@') ? pkg.split('/').slice(0, 2).join('/') : pkg.split('/')[0];
    if (!ALLOWED_PACKAGES.has(basePkg)) {
      violations.push(`Disallowed import: "${pkg}" — only whitelisted packages are allowed`);
    }
  }

  // 4. Dangerous pattern scan
  for (const pattern of DANGEROUS_PATTERNS) {
    if (pattern.test(code)) {
      violations.push(`Dangerous pattern detected: ${pattern.source}`);
    }
  }
  if (violations.length > 0) {
    return res.status(400).json({
      success: false,
      error: 'Code contains disallowed patterns',
      violations,
      fixHint: 'Remove disallowed imports and dangerous patterns. Only use: ' + [...ALLOWED_PACKAGES].join(', ')
    });
  }

  // 5. Rate limiting — max 10 submissions per user per day
  const { count } = await supabaseAdmin
    .from('community_submissions')
    .select('*', { count: 'exact', head: true })
    .eq('user_id', userId)
    .gte('created_at', new Date(Date.now() - 86400000).toISOString());

  if (count >= 10) {
    return res.status(429).json({
      success: false,
      error: 'Daily submission limit reached (10/day). Try again tomorrow.'
    });
  }

  // 6. Content hashing — deduplication
  const normalizedCode = code.replace(/\s+/g, ' ').trim();
  const contentHash = createHash('sha256').update(normalizedCode).digest('hex');

  const { data: existingDupe } = await supabaseAdmin
    .from('community_submissions')
    .select('id, status')
    .eq('content_hash', contentHash)
    .not('status', 'in', '("rejected","archived")')
    .limit(1)
    .maybeSingle();

  if (existingDupe) {
    return res.status(409).json({
      success: false,
      error: 'A component with identical code already exists in the library',
      existingSubmissionId: existingDupe.id
    });
  }

  // ─── INSERT SUBMISSION (status='processing') ───
  const { data: submission, error: insertError } = await supabaseAdmin
    .from('community_submissions')
    .insert({
      user_id: userId,
      submission_type: 'component',
      name: name,
      description_hint: description || null,
      category_hint: categoryHint || null,
      original_code: code,
      content_hash: contentHash,
      code_size_bytes: new TextEncoder().encode(code).length,
      thumbnail_base64: thumbnail || null,  // stored temporarily, moved to Storage by async job
      video_base64: video || null,
      status: 'processing',
      submission_ip: req.ip,
      user_agent: req.headers['user-agent'],
    })
    .select('id')
    .single();

  if (insertError) {
    console.error('[submit-component] Insert failed:', insertError);
    return res.status(500).json({ success: false, error: 'Failed to save submission' });
  }

  // ─── ENQUEUE ASYNC JOB ───
  // In production: use pg_notify, Bull queue, or Supabase Edge Function trigger
  // For MVP: use a simple database-polled job queue
  await supabaseAdmin.from('submission_jobs').insert({
    submission_id: submission.id,
    job_type: 'analyze_component',
    status: 'pending',
    attempts: 0,
    max_attempts: 3,
  });

  console.log(`[submit-component] Submission ${submission.id} created, job enqueued for async analysis`);

  return res.json({
    success: true,
    submissionId: submission.id,
    message: 'Component submitted! Analysis in progress...',
    statusEndpoint: `/api/community/submission-status/${submission.id}`
  });
}
```

### S9.5 Asynchronous Analysis Worker (Background Job, 10-30s)

This runs as a background worker (polled from `submission_jobs` table or triggered by pg_notify). It performs the expensive LLM analysis and screenshot capture without blocking the user's HTTP request.

```javascript
// server/workers/submission-analyzer.js

import { supabaseAdmin } from '../lib/supabase-admin.js';
import { captureComponentScreenshot } from '../lib/screenshot-service.js';
import { generateObject } from 'ai';
import { getModel } from '../lib/provider-helpers.js';
import { z } from 'zod';

/**
 * WORKER: Picks pending jobs from submission_jobs, processes them.
 * Runs on a 5-second poll interval (or triggered by pg_notify for low-latency).
 * 
 * Processing pipeline per job:
 *   1. Screenshot the component (headless browser)
 *   2. LLM multimodal analysis (code + screenshot → metadata)
 *   3. Quality gate decision
 *   4. Insert into components table
 *   5. Upload media to Supabase Storage
 *   6. Update submission status
 *   7. Notify user via SSE / Supabase Realtime
 */
async function processSubmissionJob(job) {
  const startTime = Date.now();
  const { submission_id } = job;

  // Mark job as in-progress
  await supabaseAdmin.from('submission_jobs')
    .update({ status: 'running', started_at: new Date().toISOString() })
    .eq('id', job.id);

  try {
    // 1. Fetch the submission
    const { data: submission } = await supabaseAdmin
      .from('community_submissions')
      .select('*')
      .eq('id', submission_id)
      .single();

    if (!submission) throw new Error(`Submission ${submission_id} not found`);

    // 2. Screenshot the component
    let screenshotBuffer = null;
    let screenshotUrl = null;
    try {
      screenshotBuffer = await captureComponentScreenshot(submission.original_code, {
        timeout: 10000,    // 10s max for screenshot
        viewport: { width: 1280, height: 720 },
      });
    } catch (err) {
      console.warn(`[Analyzer] Screenshot failed for ${submission_id}:`, err.message);
      // Continue without screenshot — LLM can still analyze code-only
    }

    // 3. Upload screenshot to Storage (if captured)
    if (screenshotBuffer) {
      const screenshotPath = `submissions/${submission_id}/preview.png`;
      await supabaseAdmin.storage.from('component-previews')
        .upload(screenshotPath, screenshotBuffer, { contentType: 'image/png', upsert: true });
      screenshotUrl = supabaseAdmin.storage.from('component-previews')
        .getPublicUrl(screenshotPath).data.publicUrl;
    }

    // 4. Upload user-provided media (moved from base64 to Storage)
    let thumbnailUrl = screenshotUrl; // fallback to auto-screenshot
    let videoUrl = null;

    if (submission.thumbnail_base64) {
      const thumbBuffer = Buffer.from(submission.thumbnail_base64, 'base64');
      const thumbPath = `submissions/${submission_id}/thumbnail.png`;
      await supabaseAdmin.storage.from('component-previews')
        .upload(thumbPath, thumbBuffer, { contentType: 'image/png', upsert: true });
      thumbnailUrl = supabaseAdmin.storage.from('component-previews')
        .getPublicUrl(thumbPath).data.publicUrl;
    }

    if (submission.video_base64) {
      const videoBuffer = Buffer.from(submission.video_base64, 'base64');
      const videoPath = `submissions/${submission_id}/preview.mp4`;
      await supabaseAdmin.storage.from('component-previews')
        .upload(videoPath, videoBuffer, { contentType: 'video/mp4', upsert: true });
      videoUrl = supabaseAdmin.storage.from('component-previews')
        .getPublicUrl(videoPath).data.publicUrl;
    }

    // 5. LLM Multimodal Analysis (see S9.6 for full prompt)
    //    Cost control: check daily LLM budget before calling
    const dailyLlmCost = await getDailyLlmCost();
    let llmAnalysis;

    if (dailyLlmCost >= 50.00) { // $50/day budget cap
      console.warn('[Analyzer] Daily LLM budget exhausted. Using basic extraction fallback.');
      llmAnalysis = basicMetadataExtraction(submission.original_code, submission.name);
    } else {
      llmAnalysis = await analyzeCommunityComponent({
        code: submission.original_code,
        screenshotUrl,
        userProvidedName: submission.name,
        userProvidedDescription: submission.description_hint,
        userCategoryHint: submission.category_hint,
      });

      // Track LLM cost (approximate: ~$0.03-0.08 per multimodal call)
      await supabaseAdmin.from('llm_cost_log').insert({
        operation: 'submission_analysis',
        model: 'gemini-2.0-flash',
        estimated_cost_usd: 0.05,
        submission_id,
        tokens_used: llmAnalysis._tokenUsage || null,
      });
    }

    // 6. Quality Gate Decision
    const qualityScore = llmAnalysis.quality_score || 0;
    let componentStatus;

    if (qualityScore >= 8.0) {
      componentStatus = 'active';      // Auto-approve, immediately live
    } else if (qualityScore >= 4.0) {
      componentStatus = 'pending_review'; // Needs admin review
    } else {
      componentStatus = 'rejected';     // Auto-reject with tips
    }

    // 7. Build component_id with version
    const slugifiedName = submission.name.toLowerCase().replace(/[^a-z0-9]+/g, '-').replace(/-+/g, '-');
    const componentId = `${llmAnalysis.category || 'uncategorized'}.${slugifiedName}.community.v1`;

    // 8. Insert into components table (ONLY if not rejected)
    let componentDbId = null;
    if (componentStatus !== 'rejected') {
      const cleanedCode = llmAnalysis.cleaned_code || submission.original_code;

      const { data: componentRow, error: compError } = await supabaseAdmin
        .from('components')
        .insert({
          component_id: componentId,
          name: submission.name,
          version: 'v1',
          version_number: 1,
          author_id: submission.user_id,
          author_type: 'community',

          // Classification
          category: llmAnalysis.category,
          subcategory: llmAnalysis.subcategory,
          component_type: llmAnalysis.component_type,

          // Rich Metadata (all LLM-generated)
          display_name: llmAnalysis.display_name || submission.name,
          description: llmAnalysis.description,
          visual_description: llmAnalysis.visual_description,
          mood_tone: llmAnalysis.mood_tone,
          design_personality: llmAnalysis.design_personality,
          color_mode: llmAnalysis.color_mode,
          color_primary: llmAnalysis.color_primary,
          color_secondary: llmAnalysis.color_secondary,
          color_accent: llmAnalysis.color_accent,
          color_background: llmAnalysis.color_background,
          color_palette: llmAnalysis.color_palette,
          color_warmth: llmAnalysis.color_warmth,
          color_theme: llmAnalysis.color_theme,
          typography_style: llmAnalysis.typography_style,
          layout_type: llmAnalysis.layout_type,
          suitable_for: llmAnalysis.suitable_for,
          not_suitable_for: llmAnalysis.not_suitable_for,
          industry_tags: llmAnalysis.industry_tags,
          supports: llmAnalysis.supports,
          requires: llmAnalysis.requires,
          responsive: llmAnalysis.responsive,
          has_animation: llmAnalysis.has_animation,
          tags: llmAnalysis.tags,
          keywords: llmAnalysis.keywords,

          // Quality
          quality_score: qualityScore,
          usage_count: 0,
          rating_avg: 0,
          rating_count: 0,

          // Visual Assets
          preview_image_url: thumbnailUrl,
          thumbnail_url: thumbnailUrl,
          preview_video_url: videoUrl,

          // Code Bundle — same format as existing bundles in registry.js
          // getBundleAsync() reads bundle_code from this column
          bundle_code: {
            id: componentId,
            files: [{
              path: `src/components/${submission.name.replace(/\s+/g, '')}.jsx`,
              content: cleanedCode,
            }],
            usage: {
              importName: submission.name.replace(/\s+/g, ''),
              importPath: `./components/${submission.name.replace(/\s+/g, '')}`,
              renderTag: `<${submission.name.replace(/\s+/g, '')} />`
            }
          },
          bundle_size_bytes: new TextEncoder().encode(cleanedCode).length,

          // Status & Content Hash
          status: componentStatus,
          content_hash: submission.content_hash,
          is_premium: true,
          submission_id: submission.id,
        })
        .select('id')
        .single();

      if (compError) {
        console.error(`[Analyzer] Component insert failed:`, compError);
        throw compError;
      }
      componentDbId = componentRow.id;
    }

    // 9. Update submission record
    await supabaseAdmin.from('community_submissions').update({
      component_id: componentDbId,
      cleaned_code: llmAnalysis.cleaned_code || null,
      llm_analysis: llmAnalysis,
      screenshot_url: screenshotUrl,
      video_url: videoUrl,
      quality_score: qualityScore,
      auto_approved: componentStatus === 'active',
      status: componentStatus === 'active' ? 'approved' : componentStatus,
      processing_time_ms: Date.now() - startTime,
      updated_at: new Date().toISOString(),
    }).eq('id', submission_id);

    // 10. Update reputation
    const reputationPoints = componentStatus === 'active' ? 15 : componentStatus === 'pending_review' ? 5 : -2;
    await supabaseAdmin.rpc('increment_reputation', {
      p_user_id: submission.user_id,
      p_points: reputationPoints
    });

    // 11. Clear temporary base64 data from submission (save DB space)
    await supabaseAdmin.from('community_submissions').update({
      thumbnail_base64: null,
      video_base64: null,
    }).eq('id', submission_id);

    // 12. Mark job complete
    await supabaseAdmin.from('submission_jobs').update({
      status: 'completed',
      completed_at: new Date().toISOString(),
      result: { componentStatus, qualityScore, componentDbId },
    }).eq('id', job.id);

    console.log(`[Analyzer] Submission ${submission_id} processed in ${Date.now() - startTime}ms → ${componentStatus} (score: ${qualityScore})`);

  } catch (error) {
    console.error(`[Analyzer] Job ${job.id} failed:`, error);

    // Increment attempt count
    const newAttempts = (job.attempts || 0) + 1;
    if (newAttempts >= job.max_attempts) {
      // Mark as permanently failed
      await supabaseAdmin.from('submission_jobs')
        .update({ status: 'failed', error_message: error.message, attempts: newAttempts })
        .eq('id', job.id);
      await supabaseAdmin.from('community_submissions')
        .update({ status: 'rejected', rejection_reason: 'Processing failed after multiple attempts. Please try again.' })
        .eq('id', submission_id);
    } else {
      // Retry with exponential backoff (handled by worker poll interval)
      await supabaseAdmin.from('submission_jobs')
        .update({ status: 'pending', error_message: error.message, attempts: newAttempts,
                   retry_after: new Date(Date.now() + 5000 * Math.pow(2, newAttempts)).toISOString() })
        .eq('id', job.id);
    }
  }
}

/**
 * WORKER POLL LOOP: Runs every 5 seconds, picks one pending job at a time.
 * Uses SELECT ... FOR UPDATE SKIP LOCKED to prevent duplicate processing.
 */
async function runWorker() {
  while (true) {
    const { data: jobs } = await supabaseAdmin
      .from('submission_jobs')
      .select('*')
      .eq('status', 'pending')
      .or('retry_after.is.null,retry_after.lte.' + new Date().toISOString())
      .order('created_at', { ascending: true })
      .limit(1);

    if (jobs && jobs.length > 0) {
      await processSubmissionJob(jobs[0]);
    }

    await new Promise(r => setTimeout(r, 5000)); // 5s poll interval
  }
}

/**
 * LLM COST FALLBACK: When daily budget is exhausted, extract basic metadata
 * from the code using regex patterns (no LLM call needed).
 */
function basicMetadataExtraction(code, name) {
  const hasMotion = /framer-motion|motion\./i.test(code);
  const hasDarkBg = /bg-(?:black|gray-9|slate-9|neutral-9|zinc-9)/i.test(code) || /background:\s*#(?:0|1|2)/i.test(code);
  const hasGrid = /grid-cols|grid\s/i.test(code);

  return {
    category: 'uncategorized',
    subcategory: null,
    component_type: name.toLowerCase().replace(/\s+/g, '-'),
    display_name: name,
    description: `Community component: ${name}`,
    visual_description: 'Community-submitted component (auto-analysis pending)',
    mood_tone: 'neutral',
    color_mode: hasDarkBg ? 'dark' : 'light',
    suitable_for: ['general'],
    not_suitable_for: [],
    industry_tags: [],
    supports: hasMotion ? ['framer-motion'] : [],
    requires: [],
    responsive: /md:|lg:|sm:/i.test(code),
    has_animation: hasMotion,
    tags: ['community'],
    keywords: name.toLowerCase().split(/\s+/),
    quality_score: 5.0,  // Neutral score — forces manual review
    language: /\.tsx/.test(code) ? 'tsx' : 'jsx',
    cleaned_code: null,
  };
}
```

### S9.6 LLM Multimodal Analysis Function (Structured Output with Zod)

Uses `generateObject` from the `ai` library with Zod schemas (matching the pattern used in `select-components.js` and `plan-website-components.js`):

```javascript
// server/lib/community-analyzer.js

  subcategory: z.string().nullable().describe('Sub-category slug if applicable'),
  component_type: z.string().describe('Specific type (e.g., "hero-video", "pricing-toggle")'),
  display_name: z.string().describe('Clean display name'),
  description: z.string().describe('2-3 sentence description'),
  visual_description: z.string().describe('Detailed visual description: colors, layout, spacing, feel'),
  mood_tone: z.string().describe('e.g., professional, playful, minimal, bold, elegant'),
  design_personality: z.object({
    style: z.string(),

    formality: z.string(),
  }),
  color_mode: z.enum(['dark', 'light', 'mixed', 'adaptive']),
  color_primary: z.string().nullable(),
  color_secondary: z.string().nullable(),
  color_accent: z.string().nullable(),
  color_background: z.string().nullable(),
  color_palette: z.array(z.string()).nullable(),
  color_warmth: z.enum(['warm', 'cool', 'neutral', 'vibrant']).nullable(),
  color_theme: z.string().nullable(),
  typography_style: z.string().nullable(),
  layout_type: z.string().describe('e.g., full-width, centered, split, grid'),

  language: z.enum(['jsx', 'tsx']),
  cleaned_code: z.string().nullable().describe('Fixed code if issues found, null otherwise'),
  code_issues_found: z.array(z.string()),
  code_fixes_applied: z.array(z.string()),
});

/**
 * Multimodal LLM analysis: code + screenshot → structured metadata
 * Uses generateObject for type-safe structured output
 */
export async function analyzeCommunityComponent({ code, screenshotUrl, userProvidedName, userProvidedDescription, userCategoryHint }) {
  // Fetch taxonomy for classification
  const { data: categories } = await supabaseAdmin
    .from('component_categories')
    .select('slug, name, description, parent_category_id')
    .eq('is_active', true);

  const messages = [
    {
      role: 'system',
      content: `You are an expert UI component analyst for the Volturiano AI Website Builder.
A community user submitted a React component. Analyze BOTH the code AND the screenshot to produce a complete metadata profile.

AVAILABLE CATEGORIES:
${categories.map(c => `- ${c.slug}: ${c.name} — ${c.description || ''}`).join('\n')}

QUALITY SCORING RUBRIC:
- 9-10: Production-ready, beautiful, well-structured, responsive, accessible
- 7-8: Good quality, minor improvements possible, usable as-is
- 5-6: Decent, functional but not polished
- 3-4: Below average, significant issues
- 1-2: Broken, non-functional, or very poor quality

CODE CLEANUP RULES:
- Fix missing export default statements
- Fix incorrect import paths
- Remove console.log statements
- Ensure component accepts and uses props properly
- Do NOT change the visual design — only fix technical issues`
    },
    {
      role: 'user',
      content: [
        {
          type: 'text',
          text: `Component Name: "${userProvidedName}"
User Description: "${userProvidedDescription || 'Not provided — generate one'}"
Category Hint: "${userCategoryHint || 'Not provided — auto-detect'}"

CODE:
\`\`\`
${code}
\`\`\``
        },
        // Include screenshot if available (multimodal)
        ...(screenshotUrl ? [{
          type: 'image',
          image: screenshotUrl,
        }] : []),
      ]
    }
  ];

  const result = await generateObject({
    model: getModel('gemini-2.0-flash'),  // Cost-effective for metadata extraction
    schema: componentAnalysisSchema,
    messages,
  });

  return result.object;
}
```

### S9.10 Component Versioning

When a user edits an active component, the original version is **immutable**. The edit creates a new version. Templates pin to specific versions — they keep working even if the author publishes v2.

```sql
-- Versioning model:
-- component_id = 'hero.gradient-dark.community' (no version suffix)
-- version_number = 1, 2, 3, ...
-- parent_component_id = UUID of v1 (NULL for v1 itself)
--
-- getCatalogForPromptAsync() always returns the LATEST active version.
-- getBundleAsync() can fetch a specific version when templates need it.
-- Templates store component_version_number alongside component_id.

-- View: latest active version of each component
CREATE OR REPLACE VIEW latest_active_components AS
SELECT DISTINCT ON (component_id) *
FROM components
WHERE status = 'active'
ORDER BY component_id, version_number DESC;
```

```javascript
// Version bump on edit — creates new version, not in-place update
async function editCommunityComponent(userId, componentDbId, newCode) {
  // 1. Fetch existing
  const { data: existing } = await supabaseAdmin
    .from('components')
    .select('*')
    .eq('id', componentDbId)
    .eq('author_id', userId)
    .single();

  if (!existing) throw new Error('Component not found or not yours');

  // 2. Deprecate old version
  await supabaseAdmin.from('components')
    .update({ status: 'deprecated' })
    .eq('id', componentDbId);

  // 3. Create new version (re-run LLM analysis via job queue)
  const newVersionNumber = (existing.version_number || 1) + 1;
  const contentHash = createHash('sha256').update(newCode.replace(/\s+/g, ' ').trim()).digest('hex');

  const { data: submission } = await supabaseAdmin
    .from('community_submissions')
    .insert({
      user_id: userId,
      submission_type: 'component',
      name: existing.name,
      original_code: newCode,
      content_hash: contentHash,
      status: 'processing',
    })
    .select('id')
    .single();

  // Enqueue analysis (same async pipeline as new submissions)
  await supabaseAdmin.from('submission_jobs').insert({
    submission_id: submission.id,
    job_type: 'analyze_component',
    status: 'pending',
    attempts: 0,
    max_attempts: 3,
  });

  return { submissionId: submission.id, newVersion: newVersionNumber };
}
```

### S9.11 Component Ratings & Reviews

```sql
CREATE TABLE component_ratings (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  component_id UUID NOT NULL REFERENCES components(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  rating INTEGER NOT NULL CHECK (rating >= 1 AND rating <= 5),
  review_text TEXT,
  review_title TEXT,
  helpful_count INTEGER DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(component_id, user_id)  -- One review per user per component
);

CREATE INDEX idx_ratings_component ON component_ratings(component_id);
CREATE INDEX idx_ratings_user ON component_ratings(user_id);
CREATE INDEX idx_ratings_rating ON component_ratings(rating DESC);

-- Trigger to auto-update component rating_avg and rating_count
-- PERFORMANCE NOTE: At scale (10k+ ratings per component), consider a materialized
-- counter instead of SELECT AVG/COUNT. For now, the unique constraint on
-- (component_id, user_id) keeps the subquery result set small (max 1 row per user).
CREATE OR REPLACE FUNCTION update_component_rating_stats()
RETURNS TRIGGER AS $$
BEGIN
  UPDATE components SET
    rating_avg = (SELECT AVG(rating)::FLOAT FROM component_ratings WHERE component_id = COALESCE(NEW.component_id, OLD.component_id)),
    rating_count = (SELECT COUNT(*) FROM component_ratings WHERE component_id = COALESCE(NEW.component_id, OLD.component_id)),
    updated_at = NOW()
  WHERE id = COALESCE(NEW.component_id, OLD.component_id);
  RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_rating_change
  AFTER INSERT OR UPDATE OR DELETE ON component_ratings
  FOR EACH ROW EXECUTE FUNCTION update_component_rating_stats();
```

### S9.12 Reputation System

```sql
CREATE OR REPLACE FUNCTION increment_reputation(p_user_id UUID, p_points INTEGER)
RETURNS VOID AS $$
BEGIN
  UPDATE profiles SET
    reputation_score = GREATEST(0, COALESCE(reputation_score, 0) + p_points),
    components_submitted = CASE
      WHEN p_points > 0 AND p_points >= 10 THEN COALESCE(components_submitted, 0) + 1
      ELSE COALESCE(components_submitted, 0)
    END,
    updated_at = NOW()
  WHERE id = p_user_id;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- Reputation points schedule:
-- Component submitted (enters processing): +5
-- Component auto-approved (quality >= 8):  +15
-- Component manually approved:             +10
-- Component auto-rejected (quality < 4):   -2
-- Component used in a build:               +1 per use
-- Component rated 4+ stars:                +3
-- Component reaches 100 uses:              +25 (milestone bonus)
-- Template submitted:                      +8
-- Template approved:                       +15
-- Flagged for review:                      -5
-- Confirmed violation:                     -20
-- Self-removed by author:                  -5
```

```sql
-- Track AI selection events for feedback loop
CREATE TABLE ai_selection_events (

  build_id TEXT NOT NULL,
  component_id UUID NOT NULL REFERENCES components(id),
  was_selected BOOLEAN NOT NULL DEFAULT TRUE,
  was_kept BOOLEAN,           -- NULL = build incomplete, TRUE = user kept it, FALSE = user replaced/removed
  selection_confidence FLOAT, -- From select-components.js LLM output
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_selection_events_component ON ai_selection_events(component_id);
CREATE INDEX idx_selection_events_build ON ai_selection_events(build_id);
```

```javascript
// After build completion, check which components were kept vs removed
// Called when user manually edits or regenerates specific components
async function recordComponentRetention(buildId, keptComponentIds, removedComponentIds) {
  // Mark kept components
  for (const compId of keptComponentIds) {
    await supabaseAdmin.from('ai_selection_events')
      .update({ was_kept: true })
      .eq('build_id', buildId)
      .eq('component_id', compId);
  }
  // Mark removed components
  for (const compId of removedComponentIds) {
    await supabaseAdmin.from('ai_selection_events')
      .update({ was_kept: false })
      .eq('build_id', buildId)
      .eq('component_id', compId);
  }

  // retention_rate = was_kept_count / total_selection_count

}
```

```javascript
async function deprecateUserComponent(userId, componentId) {
  const { data: component } = await supabaseAdmin
    .from('components')
    .select('id, author_id, usage_count, status')
    .eq('id', componentId)
    .eq('author_id', userId)
    .eq('status', 'active')
    .single();

  if (!component) throw new Error('Component not found, not yours, or not active');

  // Soft-delete: deprecated (templates can still reference it)
  await supabaseAdmin.from('components').update({
    status: 'deprecated',
    updated_at: new Date().toISOString()
  }).eq('id', componentId);

  await supabaseAdmin.from('community_submissions').update({
    status: 'deprecated',
    updated_at: new Date().toISOString()
  }).eq('component_id', componentId).eq('user_id', userId);

  await supabaseAdmin.rpc('increment_reputation', {
    p_user_id: userId,
    p_points: -5
  });

  return { success: true, message: 'Component deprecated. Templates using it will continue to work.' };
```

## Phase S10: ULTRA Community Template Builder — Compose, Combine & Share Full Website Recipes

**Status:** ✅ Done (Backend complete. Visual Composer & community browsing UI deferred to S11)
**Timeline:** 3-4 weeks
**Priority:** HIGH — Templates are the second-order scaling engine
**Dependencies:** Phase S9, Phase S7

### S10.1 Overview & Strategic Vision

Phase S10 evolves the builder from "picking atoms" to "arranging molecules." Templates are **recipes** — curated, semantically verified combinations of 5–12 components that form a high-converting website structure.

**The "Flywheel" Effect:**
1.  **Phase S9 (Atoms):** Community submits high-quality components.
2.  **Phase S10 (Molecules):** Community (and Official Designers) group those components into "Best-of" recipes.
3.  **Phase S11 (Marketplace):** Users discover templates, or AI selects them automatically in the build flow.

**Key Architecture Decisions for S10:**
- **Mode A: Visual Composition:** "Playlist" style creation. Browse components, drag into order, preview as a stack, and publish.
- **Mode B: Smart Splitting (LLM):** Paste massive JSX of a full landing page. An async LLM job decomposes the code into individual components (atomization) and then creates a template linking them back together.
- **Versioning:** Templates are as immutable as components. Editing a template creates a new version_number.
- **Cross-Ownership:** A template can contain components from multiple authors. Authorship of the "Recipe" is distinct from authorship of the "Ingredients."

---

### S10.2 Template Creation Workflow — Mode A: Visual Composer

Designed for power users who want to curate specific looks.

1.  **Selection:** User opens Template Builder. Browses the components library (Status=Active).
2.  **Stacking:** User adds 4–12 components to their "Draft Stack."
3.  **Arrangement:** Drag-and-drop ordering. The stack renders in a live-preview iframe using the S9 sandbox technique.
4.  **Metadata:** User provides Name and Description. LLM analyzes the stack to auto-fill industry, color mode, and design style.
5.  **Submission:** 
    - **Sync:** Insert into community_submissions (type='template'), status='processing'.
    - **Async:** LLM performs multimodal analysis of the combined stack screenshot + linked components metadata.
    - **Result:** Status → active.

---

### S10.3 Template Creation Workflow — Mode B: Smart Splitting (LLM-Powered)

Designed for users moving existing designs into Volturiano.

1.  **The Paste:** User pastes a monolithic page.jsx block (up to 200KB).
2.  **Initial Insert:** Submission is saved as type='template_scratch', status='atomizing'.
3.  **The Splitting Pipeline (Async):**
    - **Job Queue:** template_splitter background job picks up the work.
    - **Decomposition:** LLM identifies "natural breaks" (e.g., <Navbar>, <Hero>, <Features>).
    - **Atomization:** LLM extracts code for each section, applies S9 security scanning, and creates 5–10 new components in the components table (Status=Active, parent=null).
    - **Reconstruction:** Job creates a record in templates and template_sections linking these new IDs in the correct order.
4.  **Completion:** User receives an SSE notification "Your template and 7 new components have been generated!"
5.  **State:** Status → pending_review (scratch templates require higher moderation).

---

### S10.4 The Template Splitter Pipeline (Backend)

The "Smart Splitter" uses a high-context LLM (Gemini 2.0 Flash) to perform "Code Surgery."

**Function: splitMonolithIntoComponents(rawCode)**
- Input: String (JSX)
- Process:
  1.  **Refactor:** LLM identifies functional boundaries.
  2.  **Isolate:** It extracts CSS (Tailwind/Module) relevant to each section.
  3.  **Sanitize:** Applies imports whitelist to each atom.
  4.  **Taxonomy:** Classifies each atom into S7 categories.
- Output: [{ name, category, code, display_hint } ...]

**Implementation Hint (Registry.js + Jobs.js):**
```javascript

  3. Map all global styles/Tailwind classes into the individual components.
  4. Output a JSON array of objects with 'name', 'code', 'category', 'visual_description'.
```

### S10.7 Concrete RLS Policies for Templates

Granular security ensuring users can only manage their own templates.

```sql
-- RLS: templates
ALTER TABLE templates ENABLE ROW LEVEL SECURITY;

-- Anyone can see active templates
CREATE POLICY "templates_select_active"
  ON templates FOR SELECT
  USING (status = 'active' OR auth.uid() = author_id);

-- Authors can insert
CREATE POLICY "templates_insert_own"
  ON templates FOR INSERT
  WITH CHECK (auth.uid() = author_id);

-- Authors can update (only if status is draft or pending)
CREATE POLICY "templates_update_own"
  ON templates FOR UPDATE
  USING (auth.uid() = author_id AND status IN ('draft', 'pending_review'))
  WITH CHECK (auth.uid() = author_id);

-- RLS: template_sections
ALTER TABLE template_sections ENABLE ROW LEVEL SECURITY;

-- Linked to template visibility
CREATE POLICY "sections_select_visible"
  ON template_sections FOR SELECT
  USING (EXISTS (
    SELECT 1 FROM templates t WHERE t.id = template_sections.template_id
  ));
```

### S10.12 Quality Scoring Algorithm & LLM Metadata

When a template is finalized, the `analyzeTemplateJob` calculates the score:

```javascript
// Scoring logic in submission-analyzer.js
function calculateTemplateScore(llmMetadata, componentScores) {
  const avgCompQuality = componentScores.reduce((a,b) => a+b, 0) / componentScores.length;
  const themeMatchIdx = llmMetadata.theme_score / 10;
  
  // Logic: A template is only as good as its weakest link + the harmony between links
  const baseScore = (avgCompQuality * 0.7) + (llmMetadata.quality_score * 0.3);
  return baseScore * (0.8 + (themeMatchIdx * 0.2));
}
```

## ✅ Phase S12: Credits System & Stripe Integration — COMPLETED ✅
**Status:** COMPLETED (March 11, 2026)
**Note:** Production deployment will handle final tunnel stabilization as per `BeforeProductionChecklist.txt`.
**Priority:** CRITICAL — High-Security Monetization Engine
**Dependencies:** Phase S1 (Auth), Phase S2 (Core Schema)

### S12.1 Strategic Architecture: The "Iron-Clad" Security Model

To prevent "credit hacking" and unauthorized balance manipulation, we are moving the **Source of Truth** and the **Deduction Logic** directly into the Supabase PostgreSQL layer. 

**Security Principles:**
1.  **Frontend is Untrusted:** The frontend never says "Set credits to X." It only requests an action (e.g., "Build Site").
2.  **API is the Messenger:** The Express backend validates the request and asks the Database to perform the math.
3.  **Database is the Enforcer:** Strict **Row Level Security (RLS)** prevents users from manually updating their own credit counts. Only internal Database Functions and the `service_role` key can modify balances.
4.  **Atomic Transactions:** Deductions and ledger entries happen in a single SQL transaction to prevent "double-spending" bugs.

---

### S12.2 Database Layer — The Secure Vault (SQL)

We implement the core logic using PostgreSQL functions and triggers. This ensures that even if our Express server is compromised, the database rules protect the user balances.

**Step S12.2.1: Credit Schema Enhancements**
We ensure the `profiles` table is ready to handle three distinct credit states: Daily Free, Purchased balance, and Unlimited (Admin/Pro).

```sql
-- Add high-precision credit columns if not already present
ALTER TABLE profiles 
  ADD COLUMN IF NOT EXISTS total_credits_purchased INTEGER DEFAULT 0,
  ADD COLUMN IF NOT EXISTS daily_credits_limit INTEGER DEFAULT 15,
  ADD COLUMN IF NOT EXISTS daily_credits_used INTEGER DEFAULT 0,
  ADD COLUMN IF NOT EXISTS daily_credits_reset_at TIMESTAMPTZ DEFAULT NOW();

-- Ensure users cannot touch their own sensitive credit columns
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;

CREATE POLICY "profiles_update_restricted" 
  ON profiles FOR UPDATE 
  USING (auth.uid() = id)
  WITH CHECK (
    -- Allow updates to display_name, bio, etc.
    -- BLOCK updates to any credit or plan related columns via RLS
    (SELECT plan FROM profiles WHERE id = auth.uid()) = plan AND
    (SELECT daily_credits_limit FROM profiles WHERE id = auth.uid()) = daily_credits_limit AND
    (SELECT total_credits_purchased FROM profiles WHERE id = auth.uid()) = total_credits_purchased
  );
```

**Step S12.2.2: The Atomic `deduct_credits` Function**
This is the single most important security feature. It performs all checks and the subtraction in one thread-safe operation.

```sql
CREATE OR REPLACE FUNCTION deduct_credits_safe(p_user_id UUID, p_amount INTEGER, p_description TEXT, p_project_id UUID DEFAULT NULL)
RETURNS JSONB AS $$
DECLARE
    v_profile RECORD;
    v_success BOOLEAN := FALSE;
    v_error_message TEXT := '';
BEGIN
    -- 1. Fetch current profile state with a ROW LOCK (FOR UPDATE) to prevent race conditions
    SELECT * INTO v_profile FROM profiles WHERE id = p_user_id FOR UPDATE;

    IF NOT FOUND THEN
        RETURN jsonb_build_object('success', false, 'error', 'User not found');
    END IF;

    -- 2. Handle Daily Reset logic inside the atomic transaction
    IF v_profile.daily_credits_reset_at < CURRENT_TIMESTAMP THEN
        UPDATE profiles SET 
            daily_credits_used = 0, 
            daily_credits_reset_at = (CURRENT_DATE + INTERVAL '1 day')::timestamptz 
        WHERE id = p_user_id;
        v_profile.daily_credits_used := 0;
    END IF;

    -- 3. Deduction Logic Chain
    -- Strategy: Use Daily Free credits FIRST, then Purchased credits.
    IF v_profile.plan = 'admin' OR v_profile.plan = 'enterprise' THEN
        -- Unlimited plans: Just record the transaction but don't subtrack
        v_success := TRUE;
    ELSIF v_profile.daily_credits_used < v_profile.daily_credits_limit THEN
        -- Use Daily Free
        UPDATE profiles SET daily_credits_used = daily_credits_used + p_amount WHERE id = p_user_id;
        v_success := TRUE;
    ELSIF v_profile.total_credits_purchased >= p_amount THEN
        -- Use Purchased Credits
        UPDATE profiles SET total_credits_purchased = total_credits_purchased - p_amount WHERE id = p_user_id;
        v_success := TRUE;
    ELSE
        -- Insufficient balance
        v_success := FALSE;
        v_error_message := 'Insufficient credits. Free daily limit reached and no purchased credits remaining.';
    END IF;

    -- 4. record transaction if successful
    IF v_success THEN
        INSERT INTO credit_transactions (user_id, amount, type, description, project_id)
        VALUES (p_user_id, -p_amount, 'usage', p_description, p_project_id);
    END IF;

    RETURN jsonb_build_object('success', v_success, 'error', v_error_message);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

**Step S12.3.2: The Webhook Orchestrator (The Fulfillment Guard)**
The Webhook is the only way credits are added. It listens for a verified signal from Stripe that money has actually changed hands.

```javascript
// Location: web/server/routes/webhooks.js

router.post('/stripe-fulfillment', express.raw({type: 'application/json'}), async (req, res) => {
  const sig = req.headers['stripe-signature'];
  let event;

  try {
    event = stripe.webhooks.constructEvent(req.body, sig, process.env.STRIPE_WEBHOOK_SECRET);
  } catch (err) {
    return res.status(400).send(`Webhook Error: ${err.message}`);
  }

  if (event.type === 'checkout.session.completed') {
    const session = event.data.object;
    const { user_id, credit_amount } = session.metadata;

    // USE SERVICE ROLE TO UPDATE DB (Bypassing RLS)
    await supabaseAdmin.rpc('add_credits_safe', {
      p_user_id: user_id,
      p_amount: parseInt(credit_amount),
      p_description: `Stripe Purchase: ${session.id}`
    });
    
    console.log(`✅ Credits fulfilled for user ${user_id}: +${credit_amount}`);
  }

  res.json({received: true});
});
```

### S12.4 Frontend Integration — The User's Credit Experience

**Step S12.4.1: The Credit Balance Hook**

```javascript
// web/src/hooks/useCredits.js
export function useCredits() {
  const { profile } = useAuth();
  
  const dailyRemaining = Math.max(0, profile.daily_credits_limit - profile.daily_credits_used);
  const purchasedRemaining = profile.total_credits_purchased;
  const isOutOfCredits = dailyRemaining <= 0 && purchasedRemaining <= 0;

  return { dailyRemaining, purchasedRemaining, isOutOfCredits };
}
```

## Phase S24: Social Engagement & Personal Library — "Liked Components" System

**Status:** PLANNED
**Timeline:** 1 week
**Priority:** MEDIUM (User Engagement & Personalized Experience)
**Dependencies:** Phase S6 (Catalog), S11 (Community UI), S13 (Dashboard)

### S24.1 Overview & "Like vs Bookmark" Pivot

To simplify user engagement and align with modern social curation patterns (like Pinterest or Behance), we are pivoting from a generic "Bookmark" system to a unified **"Liked Components"** feature. 

**User Flow:**
1.  **Discover:** User browses the Community Hub or Generation Marquee.
2.  **Preview:** User opens the `SandpackPreviewPopup`.
3.  **Heart:** User clicks the Heart icon. The icon turns red, and the component is instantly added to their personal collection.
4.  **Recall:** User goes to their **Dashboard Sidebar → Liked components** (formerly Bookmarks) to find all saved inspiration for future builds.

### S24.2 Database Schema: component_likes

We will use a dedicated `component_likes` table (renamed/evolved from any draft bookmark table) to track the many-to-many relationship.

```sql
CREATE TABLE component_likes (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  component_id UUID NOT NULL REFERENCES components(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ DEFAULT NOW(),

  -- Prevent a user from liking the same component twice
  UNIQUE(user_id, component_id)
);

-- Indexing for fast dashboard retrieval
CREATE INDEX idx_component_likes_user ON component_likes(user_id);
CREATE INDEX idx_component_likes_component ON component_likes(component_id);
```

### S24.3 Automatic Social Stats (Triggers)

Every time a component is liked, we increment a `total_likes` counter on the `components` table. This allows us to sort the Community Hub by "Most Liked" without performing expensive joins on every page load.

```sql
-- 1. Add likes_count column to components
ALTER TABLE components ADD COLUMN likes_count INTEGER DEFAULT 0;

-- 2. Create the update function
CREATE OR REPLACE FUNCTION update_component_likes_count()
RETURNS TRIGGER AS $$
BEGIN
  IF (TG_OP = 'INSERT') THEN
    UPDATE components SET likes_count = likes_count + 1 WHERE id = NEW.component_id;
  ELSIF (TG_OP = 'DELETE') THEN
    UPDATE components SET likes_count = likes_count - 1 WHERE id = OLD.component_id;
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- 3. Attach the trigger
CREATE TRIGGER on_component_like_change
  AFTER INSERT OR DELETE ON component_likes
  FOR EACH ROW EXECUTE FUNCTION update_component_likes_count();
```

### S24.4 Client-Side Implementation Plan

#### S24.4.1 Dashboard Sidebar Branding
- **Label Change:** Locate the sidebar in `Dashboard.jsx` (or `Sidebar.jsx`) and rename "Bookmarks" to **"Liked components"**.
- **Icon Change:** Replace the bookmark icon with the **Heart SVG** (path matching the one in `SandpackPreviewPopup`).
- **Route Filter:** The "Liked components" view should fetch data from `supabase.from('component_likes').select('*, components(*)')` filtered by the current `user_id`.

#### S24.4.2 Preview Popup Logic (`SandpackPreviewPopup.jsx`)

#### S25.6.3 Updated `deduct_credits_safe()` Function

New 4-bucket priority deduction:

3. `subscription_credits > 0` → decrement `subscription_credits`
4. `purchased_credits > 0` → decrement `purchased_credits`
5. Otherwise → return `INSUFFICIENT_CREDITS`

- `'subscription'` → sets `subscription_credits` (replace, not add)
- `'purchased'` → adds to `purchased_credits`

Returns all buckets: `monthly_free_remaining`, `signup_bonus_remaining`, `subscription_remaining`, `purchased_remaining`, `total_available`, `subscription_plan`, `subscription_status`.

## Phase S26: Persistent Hybrid/Premium Builder Mode Sync

**Status:** ✅ COMPLETED
**Timeline:** 1 day
**Priority:** MEDIUM
**Dependencies:** Phase S2 (Profiles schema setup)

### S26.1 Overview

The Volturiano Builder supports two primary operational modes:
1. **Hybrid Mode:** Merges custom AI-generated code alongside high-quality pre-vetted Volturiano community components.
2. **Premium Mode:** Stricts the user to pure architectural superiority using *only* pre-vetted premium community components.

Historically, this setting was stored purely in `localStorage`, meaning users would lose their preference if they logged in from a different browser or cleared their cache. In Phase S26, we wire this setting directly up to the Supabase `profiles` table.

### S26.2 Schema Validation
- The `profiles` table already includes a `preferred_mode` column.
  ```sql
  preferred_mode TEXT DEFAULT 'hybrid' CHECK (preferred_mode IN ('free', 'hybrid', 'premium'))
  ```

- Handled visual loading states while the Supabase mutation is in progress.

**2. Builder Engine Integration (`Builder.jsx`)**

- Syncs state changes if the profile is refreshed in the background.
