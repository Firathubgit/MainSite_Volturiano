# 1. ✅ THE TOYOTA PHILOSOPHY (No code changes — guiding philosophy)

This document is the absolute source of truth for the Volturiano Generation Pipeline.
The Toyota Engineering Philosophy: Less is More. Highly verifiable. Append-only.
Robust invariant contracts. Simple infrastructure that makes restrictions unnecessary.

Core Tenets:
1. Infrastructure Over Restriction: We don't tell the LLM "don't do X" — we build infrastructure
   that makes X unnecessary. Good plumbing means you don't need signs saying "don't flood."
2. Latent Extensibility: The app starts as a single page (SPA) but contains the latent
   architecture to transform into a multi-page app (MPA) only when structurally required.
3. Community Component Advantage: This is what makes Volturiano different from Lovable, v0,
   Bolt, and every other AI builder. We have a living catalog of community-submitted components
   that the LLM can intelligently select, adapt, and compose. The AI doesn't generate everything
   from scratch — it CHOOSES the best available building blocks.
4. LLM Autonomy: The AI gets creative freedom for layout, structure, imports, and composition.
   It can compose components inside components, use routing when needed, and build whatever
   architecture serves the user's vision. The sandbox is a full VM — let it be used fully.
5. Healing Loops: Every build failure is a lesson. Errors are captured and fed back to a
   specialized agent. The polish step catches edge cases. No stress.

# 4. ✅ THE ULTRA V2 PIPELINE — How Supabase Component Selection Actually Works (No code changes — documentation only)

File: `server/lib/select-components-v2.js` (1,031 lines)

This is the engine that makes Volturiano different. Here's how it works:

## 4.1 The 8-Step Selection Process

```
Step 0a: TEMPLATE MATCHING
  ├─ Query `weighted_templates` view (top 10 by composite score)
  ├─ LLM evaluates: does any template match the user's request?
  ├─ If confidence >= 0.75 → SHORT CIRCUIT (use entire template, skip Steps 1-5)
  └─ If no match → continue to individual component selection

Step 0b: TEMPLATE BLUEPRINT (if matched)
  ├─ Load `template_sections` with component JOINs
  ├─ Get ordered list of components from the template
  └─ Skip directly to Step 6 (compatibility validation)

Step 1: WEBSITE TYPE DETECTION
  ├─ Query `website_type_blueprints` (cached 1 hour)
  ├─ LLM matches user prompt to closest blueprint
  ├─ If no confident match → DYNAMIC BLUEPRINT GENERATION
  │   ├─ LLM assembles custom blueprint from available categories
  │   ├─ If confidence >= 0.7, persist to DB for future reuse
  │   └─ The system literally learns new website types
  └─ Returns blueprint slug + confidence

Step 2: BLUEPRINT LOADING
  └─ Load full blueprint from Supabase (required + optional categories)

Step 3: CATEGORY REFINEMENT
  ├─ LLM refines categories based on user's specific prompt
  ├─ May add optional categories, remove irrelevant ones
  └─ Always ensures header + footer are included

Step 4: INDUSTRY-AWARE FILTERING
  ├─ Query `components` table filtered by refined categories
  ├─ Filter by `suitable_for` industry tags
  ├─ If explicit components named in prompt → force-inject into candidate pool
  └─ Fallback: if zero candidates, fetch top 100 by quality_score

Step 5: THEME & STYLE SCORING + LLM FINAL SELECTION
  ├─ Score each candidate:
  │   ├─ quality_score * 0.3
  │   ├─ color_mode match: +2.0
  │   ├─ color_warmth match: +1.5
  │   ├─ usage popularity: up to +1.5
  │   └─ explicit component: +100 (force to top)
  ├─ Take top 30 scored candidates
  └─ LLM picks final 6-10 from top 30

Step 6: COMPATIBILITY VALIDATION
  ├─ Check `component_compatibility` table for style-clash/incompatible pairs
  └─ Auto-swap: drop lower-scored component in conflicting pair

Step 7: CODE BUNDLE FETCH
  ├─ Fetch actual React source code from `components.bundle_code`
  └─ Return enriched components with metadata + source code
```

## 4.2 Key Supabase Tables Involved

```
components              — Individual component registry (code, metadata, quality)
component_categories    — Category taxonomy (header, hero, pricing, footer, etc.)
website_type_blueprints — Pre-defined website archetypes (SaaS, restaurant, portfolio)
industry_verticals      — Industry tags for filtering
color_themes            — Color theme presets
component_compatibility — Conflict/harmony graph between component pairs
templates               — Community-submitted full website templates
template_sections       — Ordered component lists within templates
weighted_templates      — View with composite scoring for template ranking
```

## 4.3 The Hybrid Mode (Default)

The planner in `plan-website-components.js` runs in three modes:

- `strict`: ONLY premium components from Supabase. LLM forbidden from generating.
- `hybrid` (DEFAULT): V2 selects best premium components, LLM fills uncovered roles.
- `off`: No premium components. Pure LLM generation.

In hybrid mode:
1. V2 Pipeline selects premium components for as many roles as possible
2. The planner checks which standard roles (header, hero, feature, footer) are missing
3. For missing roles, it creates "generated" placeholder entries
4. `generate-single-component.js` is called only for these gaps
5. A Master Copywriter LLM pass customizes all component copy to match the user's vision

This means a typical website might be:
- Header: PREMIUM (community component, proven quality)
- Hero: PREMIUM (community component, stunning visuals)
- Features: GENERATED (custom AI content for this specific business)
- Testimonials: PREMIUM (community component)
- Pricing: PREMIUM (community component)
- Footer: PREMIUM (community component)

The user gets 80% premium quality + 20% custom-tailored content = best of both worlds.

# 5. ✅ THE RESTRICTION PROBLEM — What Previous Devs Got Wrong (No code changes — diagnosis only, fix is Section 6)

The current system prompt in `generate-ai-code-stream.js` has these restrictions:

```
CURRENT RESTRICTIONS (TO BE REMOVED/REPLACED):

1. "NO ROUTING: Unless explicitly asked, stack everything on one page."
   → Prevents the system from ever creating multi-page sites naturally

2. "SANDBOX REALITY: Do NOT invent sub-pages, external routes, or site-wide 
    structures that are not shown in the Current file structure."
   → Prevents the LLM from being creative with architecture

3. "ATOMIC SECTION RULES: Section files must NOT import or render the Header, 
    Hero, or Footer."
   → Prevents component composition (a Pricing page that imports a CTA button)

4. "APP.JSX COMPOSITION RULES: App.jsx is for assembling components ONLY. 
    NO INLINE UI."
   → Prevents the LLM from writing layout code where it naturally belongs

5. "All paths MUST be flat: src/components/Name.jsx (NO subfolders)"
   → Prevents organized directory structures for larger projects

6. "UI LIBS BANNED: @headlessui/react, @chakra-ui/react, @radix-ui"
   → Unnecessarily limits component quality (some are already in sandbox)
```

WHY these restrictions existed:
- The previous devs wanted to avoid build errors. Each restriction prevents a class of errors.
- But they also prevent a class of GOOD outcomes. The AI can't build anything sophisticated.

WHY we can remove them:
- The auto-repair loop (5 attempts) catches build failures
- The polish step catches aesthetic issues
- The import graph validator catches missing files
- The package whitelist prevents hallucinated dependencies
- GOOD INFRASTRUCTURE makes restrictions unnecessary

The Toyota way: Don't put speed bumps on the highway. Build the highway right.

# 6. ✅ THE NEW ARCHITECTURE — Infrastructure Over Restriction (IMPLEMENTED — generate-ai-code-stream.js prompt rewritten)

Instead of telling the LLM what NOT to do, we provide infrastructure that makes
the right thing the EASY thing:

## 6.1 What We Keep (Good Infrastructure)

✅ ALLOWED_PACKAGES whitelist in apply-ai-code-stream.js — This prevents dependency
   hallucination. The LLM can import whatever it wants, but only whitelisted packages
   actually get installed. Non-whitelisted imports get stripped with a comment. GOOD.

✅ sanitizeImports() — Strips illegal imports, validates lucide-react icon names. GOOD.

✅ auto-repair.js — 5 attempts at surgical error fixing. GOOD.

✅ polish-refinement.js — Final pass for brand leakage and aesthetic consistency. GOOD.

✅ Import graph validation — Ensures all relative imports resolve to real files. GOOD.

✅ Deterministic App.jsx rendering via render-app-template.js — Prevents the LLM from
   breaking the component stack on initial builds. GOOD.

✅ Design system enforcement — Components use the derived color palette, not random colors. GOOD.

## 6.2 What We Remove (Bad Restrictions → replaced with infrastructure)

❌ "NO ROUTING" → REPLACED WITH: Latent Router Pattern (see Section 8)
   The system ALLOWS routing when needed. HashRouter in App.jsx, controlled by the
   render-app-template dual-mode renderer. Infrastructure handles it.

❌ "SANDBOX REALITY: Don't invent sub-pages" → REPLACED WITH: siteMap.js contract
   The LLM CAN create sub-pages. They're governed by siteMap.js as the source of truth.
   If it creates a page, it must add it to siteMap.js. The import graph validates it.

❌ "Section files must NOT import Header/Footer" → REPLACED WITH: shared component pattern
   In MPA mode, Header/Footer render in App.jsx OUTSIDE <Routes>. Page components
   naturally don't need to render them. In SPA mode, the existing stack works. No restriction 
   needed — the architecture makes the right thing default.

❌ "App.jsx is for assembling ONLY, NO INLINE UI" → REPLACED WITH: freedom + polish
   The LLM can write whatever it needs in App.jsx. If it's ugly or broken, the polish
   step and auto-repair will fix it. Trust the LLM, verify the output.

❌ "All paths MUST be flat" → REPLACED WITH: organized directory convention
   src/components/ for sections, src/pages/ for page components, src/app/ for config.
   The LLM can use subdirectories if the project is complex enough to need them.
   The import graph validates all paths resolve correctly.

❌ "UI LIBS BANNED" → REPLACED WITH: the ALLOWED_PACKAGES whitelist
   @radix-ui/react-icons is already in the sandbox. If it's in the whitelist, it's allowed.
   The whitelist is the single source of truth for what can be imported.

## 6.3 The New System Prompt Philosophy

OLD: "Here are 20 things you CANNOT do."
NEW: "Here is the architecture. Work within it. Build whatever serves the user."

The new system prompt should give the LLM:
1. The directory convention (where files go)
2. The design system (what colors/fonts to use)
3. The component manifest (what already exists in the sandbox)
4. The user's vision (what they want)
5. Freedom to compose, import, route, and structure as needed

The infrastructure handles the rest:
- Bad imports → stripped by sanitizeImports()
- Bad packages → blocked by ALLOWED_PACKAGES
- Build errors → fixed by auto-repair (5 attempts)
- Brand leakage → fixed by polish step
- Missing files → caught by import graph validation

# 7. ✅ INTELLIGENT COMPONENT SELECTION FOR EDITS — The Missing Piece (IMPLEMENTED — edit prompt updated with catalog awareness)

This is the BIGGEST improvement in V4.0. Currently, the edit pipeline never searches
Supabase. The LLM generates everything from scratch on edits. This is wrong.

## 7.1 The Decision Framework

When a user sends a chat message to edit their website, the LLM should DECIDE:

```
USER MESSAGE → LLM INTENT DETECTION → ACTION

"Add a pricing section"        → ADD_COMPONENT    → Search Supabase for pricing components
"Add testimonials"             → ADD_COMPONENT    → Search Supabase for testimonial components
"Change the hero title"        → CONTENT_EDIT     → Edit the existing hero text
"Delete the footer"            → REMOVE_COMPONENT → Remove footer from App.jsx
"Make it darker"               → THEME_CHANGE     → Restyle all components
"Add an About page"            → ADD_PAGE         → Create page + route (see Section 8)
"Replace the hero with X"      → SWAP_COMPONENT   → Search Supabase for replacement
"Rewrite everything"           → FULL_REGENERATE  → Re-run full pipeline
```

## 7.2 When to Search Supabase (ADD_COMPONENT / SWAP_COMPONENT)

The edit flow should include a PRE-STEP: Intent + Component Search.

```
[USER CHAT MESSAGE]
    ↓
[STEP 0: INTENT CLASSIFICATION]
    ↓ LLM classifies: ADD_COMPONENT | CONTENT_EDIT | REMOVE | THEME | SWAP | ADD_PAGE
    ↓
[STEP 1: CONDITIONAL SUPABASE SEARCH]
    ├─ If ADD_COMPONENT or SWAP:
    │   ├─ Extract what kind of component is needed (pricing, testimonials, etc.)
    │   ├─ Query Supabase: getCatalogForPromptAsync(keywords, 20)
    │   ├─ Include component metadata in the LLM context
    │   └─ LLM decides: use a premium component OR generate from scratch
    │
    ├─ If CONTENT_EDIT or THEME_CHANGE or REMOVE:
    │   └─ Skip Supabase. Edit existing files directly.
    │
    └─ If ADD_PAGE:
        └─ Search Supabase for page-type components, create route
```

## 7.3 How It Works in Practice

### Use Case 1: "Add a pricing section to my website"

1. LLM classifies: ADD_COMPONENT (pricing)
2. Backend searches Supabase: `getCatalogForPromptAsync(['pricing'], 10)`
3. Returns 10 pricing components with metadata:
   ```
   - NAME: "GlassPricing", ID: "ui_pricing_01", DESCRIPTION: "3-tier glass pricing cards"
   - NAME: "GradientPricing", ID: "ui_pricing_02", DESCRIPTION: "Gradient pricing with toggle"
   - NAME: "MinimalPricing", ID: "ui_pricing_03", DESCRIPTION: "Clean minimal pricing grid"
   ```
4. LLM evaluates: "GlassPricing fits the user's dark glassmorphism site best"
5. Backend fetches the bundle: `getBundleAsync('ui_pricing_01')`
6. Component is written to sandbox at `src/components/premium/ui_pricing_01.jsx`
7. LLM updates App.jsx to import and render the new pricing component
8. Build verification → auto-repair if needed → polish step

### Use Case 2: "Change the hero headline to 'Welcome to Acme'"

1. LLM classifies: CONTENT_EDIT
2. NO Supabase search needed
3. LLM reads current Hero.jsx from sandbox
4. Outputs updated Hero.jsx with the new headline
5. Only Hero.jsx is changed — everything else stays

### Use Case 3: "Remove the testimonials section"

1. LLM classifies: REMOVE_COMPONENT
2. NO Supabase search needed
3. LLM reads current App.jsx
4. Outputs updated App.jsx without the Testimonials import/render
5. The Testimonials.jsx file stays on disk (harmless) but is no longer rendered

### Use Case 4: "Replace the hero with something more modern"

1. LLM classifies: SWAP_COMPONENT (hero)
2. Backend searches Supabase: `getCatalogForPromptAsync(['hero', 'modern'], 10)`
3. Returns 10 hero components
4. LLM picks the best match for the current design system
5. New hero is written to sandbox, old hero is removed from App.jsx
6. Build verification → polish

# 8. ✅ MULTI-PAGE SUPPORT — The Latent Router Pattern (IMPLEMENTED — BrowserRouter removed from e2b-provider.js)

## 8.1 The Core Principle

EVERY generated site starts as a single-page application. The multi-page architecture
is DORMANT — present in the infrastructure but not activated until needed.

When multi-page IS activated:
- App.jsx becomes a routing shell with HashRouter
- Content moves to src/pages/Home.jsx, src/pages/About.jsx, etc.
- Header/Footer render OUTSIDE the <Routes> block (shared across all pages)
- src/app/siteMap.js becomes the route registry

When multi-page is NOT needed:
- App.jsx is a simple vertical component stack (exactly like today)
- No router, no pages directory, no complexity
- 90% of Builder users never need multi-page

## 8.2 Trigger Conditions

The system detects multi-page intent through:
1. User prompt keywords: "about page", "login page", "multiple pages"
2. Edit mode: "Add an About page", "Create a login page"
3. Community component injection: user drags a full-page component
4. LLM judgment: if the user's request naturally requires multiple pages

## 8.3 The "Move to Home" Operation

When a single-page site transitions to multi-page, these steps occur atomically:

1. EXTRACT the content components from App.jsx (everything between Header and Footer)
2. CREATE src/pages/Home.jsx with those content components
3. REWRITE App.jsx as a routing shell:
   ```jsx
   <HashRouter>
     <div className="min-h-screen">
       <Header />
       <Routes>
         <Route path="/" element={<Home />} />
         <Route path="/about" element={<About />} />
       </Routes>
       <Footer />
     </div>
   </HashRouter>
   ```
4. CREATE src/app/siteMap.js with the route registry
5. CREATE the requested new page(s) in src/pages/
6. UPDATE the Header/Navbar to read from siteMap.js

This is the RISKIEST operation in the pipeline. The auto-repair loop is the safety net.

## 8.4 CRITICAL: The BrowserRouter Conflict (MUST FIX FIRST)

The E2B sandbox template at `e2b-provider.js` line 374-381 ALREADY wraps <App /> in 
<BrowserRouter> inside main.jsx. If render-app-template.js generates App.jsx with 
<HashRouter>, you get DOUBLE ROUTER NESTING. React will crash.

FIX (Phase 0 — before ANY multi-page work):
1. Remove <BrowserRouter> from main.jsx in e2b-provider.js
2. main.jsx becomes just: ReactDOM.createRoot(...).render(<App />)
3. App.jsx becomes the SOLE router authority
4. SPA sites: App.jsx has no router (works exactly like today)
5. MPA sites: App.jsx has <HashRouter> (new capability)

This fix is SAFE for existing SPA sites because the current App.jsx never uses 
any routing features — it's just a vertical stack of components.

## 8.5 The siteMap.js Contract

```javascript
// src/app/siteMap.js — Route registry
export const siteMap = [
  { path: '/', label: 'Home', component: 'Home', navVisible: true },
  { path: '/about', label: 'About Us', component: 'About', navVisible: true },
  { path: '/pricing', label: 'Pricing', component: 'Pricing', navVisible: true },
];
```

The Navbar MUST read from this file:
```jsx
import { siteMap } from '../app/siteMap';
import { Link, useLocation } from 'react-router-dom';

function Navbar() {
  const location = useLocation();
  return (
    <nav>
      {siteMap.filter(item => item.navVisible).map(item => (
        <Link key={item.path} to={item.path}>{item.label}</Link>
      ))}
    </nav>
  );
}
```

This is the TRUTH FILE. No hardcoded nav links. Everything flows from siteMap.js.

# 9. ✅ THE RENDER-APP-TEMPLATE REWRITE (IMPLEMENTED — dual-mode SPA+MPA renderer + route passthrough)

File: `server/lib/render-app-template.js` (currently 72 lines)

This becomes a dual-mode renderer:

```javascript
export function renderAppTemplate({ components, isMultiPage = false, pages = [], sharedComponents = [] }) {
    if (!isMultiPage) {
        return renderSPATemplate(components);  // EXISTING behavior, unchanged
    }
    return renderMPATemplate(components, pages, sharedComponents);  // NEW
}

function renderSPATemplate(components) {
    // ... existing code, exactly as today — vertical component stack ...
}

function renderMPATemplate(components, pages, sharedComponents) {
    // 1. Identify shared vs page-specific components
    const sharedSet = new Set(sharedComponents.map(c => c.refId));
    const shared = components.filter(c => sharedSet.has(c.refId));
    
    // 2. Build imports
    const sharedImports = shared.map(c => {
        let importPath = c.path;
        if (importPath.startsWith('src/')) importPath = './' + importPath.substring(4);
        return `import ${c.exportName} from '${importPath}'`;
    }).join('\n');
    
    const pageImports = pages.map(p =>
        `import ${p.component} from './pages/${p.component}.jsx'`
    ).join('\n');
    
    // 3. Build routes
    const routes = pages.map(p =>
        `          <Route path="${p.path}" element={<${p.component} />} />`
    ).join('\n');
    
    // 4. Determine shared layout
    const headerComp = shared.find(c => c.role === 'header');
    const footerComp = shared.find(c => c.role === 'footer');
    
    return `import React from 'react'
import { HashRouter, Routes, Route } from 'react-router-dom'
import './index.css'
${sharedImports}
${pageImports}

export default function App() {
  return (
    <HashRouter>
```

# 19. ARCHITECTURAL DECISION RECORDS

## ADR-001: Infrastructure Over Restriction
**Status:** ACCEPTED
**Context:** Previous devs added 20+ restrictions to the system prompt to prevent errors.
These restrictions also prevented the LLM from building anything sophisticated.
**Decision:** Remove restrictions. Keep infrastructure (whitelist, sanitizer, repair, polish).
**Consequence:** The LLM has creative freedom. Edge cases are caught by the healing loop.

## ADR-002: HashRouter over BrowserRouter
**Status:** ACCEPTED
**Context:** Published sites are static files from Supabase Storage. BrowserRouter needs
server-side fallback. Supabase Storage returns 404 for sub-routes.
**Decision:** Use HashRouter for all multi-page sites.
**Consequence:** URLs include # (e.g., /#/about). No server changes needed.

## ADR-003: Latent Router (Not Always Active)
**Status:** ACCEPTED
**Context:** 90% of users create simple landing pages. Forcing routing adds complexity.
**Decision:** Multi-page routing activates ONLY when explicitly needed.
**Consequence:** Simple sites remain simple. Complex sites get routing.

## ADR-004: siteMap.js as Single Source of Truth
**Status:** ACCEPTED
**Context:** Hardcoded nav links desync when pages are added/removed.
**Decision:** All navigation reads from siteMap.js. No hardcoded links.
**Consequence:** Adding a page = updating siteMap.js. Navbar auto-reflects.

## ADR-005: Conditional Supabase Search on Edits
**Status:** ACCEPTED
**Context:** The edit pipeline currently never searches Supabase, generating everything
from scratch even when premium components exist for the requested type.
**Decision:** LLM classifies edit intent first. ADD/SWAP triggers Supabase search.
Other intents (EDIT, REMOVE, THEME) skip Supabase for speed.
**Consequence:** Better component quality on edits. Slight latency on ADD/SWAP.

## ADR-006: LLM Autonomy with Guardrails
**Status:** ACCEPTED
**Context:** Restrictive prompts prevent errors but also prevent quality.
**Decision:** Let the LLM compose freely. Guardrails are infrastructure:
  - ALLOWED_PACKAGES whitelist
  - sanitizeImports() 
  - auto-repair loop (5 attempts)
  - polish step (brand leakage fix)
  - import graph validation
**Consequence:** More creative output. Edge cases caught by infrastructure.
