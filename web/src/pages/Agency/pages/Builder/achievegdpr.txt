This document defines every GDPR-related task required before the Volturiano
Builder platform goes live on volturiano.com. It covers technical implementation,
legal documentation, consent management, data subject rights, and vendor
compliance. Each phase must be completed and checked off sequentially.

ARCHITECTURE CONTEXT:
- Frontend: Vite + React SPA at web/src/
- Backend: Express server at web/server/
- DB: Supabase (VolturianoBuilder project) — PostgreSQL with RLS
- Auth: Supabase Auth (JWT-based)
- Payment: Stripe (billing.js, webhooks.js)
- Storage: Supabase Storage (published-sites, components, project-thumbnails)
- Analytics: Vercel Analytics + Speed Insights
- Hosting: Vercel (volturiano.com)

YOUR LAWFUL BASES:
- Account data (email, name) → Contract (providing the service)
- Payment data (Stripe customer ID) → Contract + Legal obligation (tax records)
- AI generation data (prompts, generated code) → Contract (service delivery)
- Usage analytics (Vercel Analytics) → Legitimate interest (improving the service)
- Cookie/session data → Consent (non-essential), Contract (essential session)

### G5.2 Right to Erasure ("Delete Account")

Users can request complete deletion of their account and all associated data.

**File:** `web/server/routes/settings.js` [MODIFY — add delete endpoint]
**File:** `web/src/pages/Agency/pages/Builder/Dashboard/ProfileSettings.jsx` [MODIFY — add delete button]

#### G5.2.1 Backend: Account Deletion Endpoint

**Endpoint:** `DELETE /api/settings/delete-account`

Deletion cascade order:
1. Delete all snapshots for user's projects
2. Delete all published site files from Supabase Storage
3. Delete all published_sites DB records
4. Delete all project thumbnails from storage
5. Delete all projects DB records
6. Delete all community contributions (or anonymize — see G5.2.2)
7. Delete all credit_transactions (or anonymize for tax records)
8. Delete profile record
9. Delete Supabase Auth user (via admin.auth.deleteUser)
10. Cancel any active Stripe subscription
11. Sign out the user

Swedish Bokföringslagen (7-year record keeping). Instead of deleting:

- Remove any identifying description text
- Keep amount, type, and timestamps for accounting

Purpose: Ensure all Supabase tables have proper Row Level Security policies that

### G7.1 RLS Policy Audit

Run in Supabase SQL Editor:
```sql
SELECT schemaname, tablename, policyname, permissive, roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public'
ORDER BY tablename, policyname;
```

For each table, verify:

#### G7.1.1 `profiles` Table RLS

Expected policies:
- SELECT: Users can read own profile (`auth.uid() = id`)
- UPDATE: Users can update own profile (`auth.uid() = id`)
- INSERT: Handled by trigger (handle_new_user)
- DELETE: Should NOT be allowed client-side (handled by server-side deletion)

Critical check: Ensure users CANNOT update credit columns client-side:
- `purchased_credits`, `subscription_credits`, `signup_bonus_credits`,
  `monthly_free_earned`, `total_credits_remaining`, `daily_credits_limit`
  should be blocked from client-side UPDATE.

#### G7.1.2 `projects` Table RLS

Expected policies:
- SELECT: `user_id = auth.uid()` (users see only their projects)
- INSERT: `user_id = auth.uid()`
- UPDATE: `user_id = auth.uid()`
- DELETE: `user_id = auth.uid()`

#### G7.1.3 `published_sites` Table RLS

Expected policies:
- SELECT own: `user_id = auth.uid()`
- SELECT public: `status = 'active'` (for public listing)
- INSERT/UPDATE/DELETE: `user_id = auth.uid()`

#### G7.1.4 `credit_transactions` Table RLS

Expected policies:
- SELECT: `user_id = auth.uid()` (users see only their transactions)
- INSERT: DENY to client (only server/service_role can insert)
- UPDATE: DENY to client
- DELETE: DENY to client

#### G7.1.5 `snapshots` Table RLS

Must have:
- SELECT/INSERT/UPDATE/DELETE only for rows where the snapshot's project
  belongs to the user: `EXISTS (SELECT 1 FROM projects WHERE projects.id = snapshots.project_id AND projects.user_id = auth.uid())`

### G8.1 Server Log Sanitization

Current issues found in codebase:
1. `index.js` line 59: Logs ALL incoming request URLs (may contain tokens in query params)
2. `index.js` line 76: Logs ALL parsed request bodies (may contain PII)
3. `billing.js`: Logs user email when creating Stripe customer
4. `publish.js`: Logs project/user IDs (identifiers)
5. `webhooks.js`: Logs session metadata including user_id

Remediation:
- Replace verbose `console.log` with structured logger (e.g., `pino`)
- Strip PII from log output: hash or mask emails, user IDs
- Never log request bodies in production
- Set log level to 'info' in production (not 'debug')
- Implement log rotation / TTL (Vercel handles this automatically)
