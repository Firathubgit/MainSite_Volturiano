## Executive Summary

The Volturiano Builder is a chat-based AI website generation platform built on a multi-agent pipeline (GPT-5.2 primary, GPT-4o selection/enhancement, GPT-4o-mini narration). It currently generates React websites inside E2B Firecracker MicroVMs with a 52-component premium catalog and 4 templates.

This roadmap defines 15 phases of strategic upgrades to transform the builder from its current "functional MVP" state into a premium product that surpasses Lovable, Base44, and Replit in:

1. **DESIGN QUALITY** — Contextually accurate color schemes, typography, and layout decisions based on the actual website purpose (no more purple gradients for dog websites)
2. **COMPONENT INTELLIGENCE** — 150-component catalog with rich metadata (suitability tags, color palettes, visual descriptions, industry fit)
3. **PIPELINE RELIABILITY** — Infinity self-healing loop guaranteeing zero React errors before preview
4. **PUBLISHING** — Public URLs under volturiano.com domain system
5. **GITHUB** — One-click repo creation with full code export
6. **CHECKPOINTS** — Chat-level restore like Lovable/Cursor
7. **ACCOUNTS** — Supabase auth with builder-specific tables
8. **MONETIZATION** — Stripe credits system with free daily allowance
9. **TEMPLATES** — 10 categorized starter templates
10. **MULTI-PAGE** — Header nav links that actually route to real pages

**Key Metrics:**

| Metric | Target |
|--------|--------|
| 1-shot success rate | >95% pages render without errors |
| Design quality | "looks premium" judgment in <3 seconds |
| Component reuse | >60% of pages use catalog components |
| Average generation time | <90 seconds for full site |
| Catalog size | 150 components (from current 52) |
| Template count | 10 (from current 4) |

## Project Vision & Non-Negotiable Principles

### 2.1 Locked Vibe Keywords
**Priority:** Non-Negotiable  

Premium, Cinematic, Bold, Dark-Lux, Sporty-Tech

These five keywords define EVERY design decision. Any generated website that does not feel premium is a failure. The generated output must look like it was built by a $50,000 agency, not a free template.

### 2.2 Forbidden Vibes (NEVER)

- Cheap gradients (random purple-pink on a dog website)
- Generic Tailwind landing pages (standard blue/white default)
- Cramped spacing / weak typography
- Stocky UI / undifferentiated layouts
- "Lorem Ipsum" or "Welcome to our website" placeholder text
- Components that ignore the website's actual purpose

### 2.3 The Product Identity
**Priority:** Non-Negotiable  

This is primarily a: **WEBSITE BUILDER** (multi-page + routing) with hybrid component composition (catalog-first, LLM-generated fallback)

Default output format: Vite React (single-page initially, multi-page planned)

The builder is NOT just a landing page generator. The vision is full websites with real navigation, multiple pages, and contextually accurate content.

### 2.4 The "Better Than Lovable" Scoreboard

| Metric | Lovable | Us (Current) | Us (Target) |
|--------|---------|--------------|-------------|
| 1-shot render success | ~85% | ~65% | >95% |

| Public domain publishing | Yes | No | Yes |
| GitHub integration | Yes | No | Yes |
| Chat checkpoints | Yes | No | Yes |
| Template variety | Many | 4 | 10+ |
| Component catalog | N/A | 52 | 150 |
| Free tier | Limited | None | 15 sites/day |
| Stripe billing | Yes | No | Yes |
| Self-healing builds | Partial | Basic | Infinity loop |

### 2.5 Core Architectural Principles

1. **CATALOG-FIRST:** The LLM must select from premium catalog first. Only generate new components if the catalog genuinely has no match.
2. **CONTEXT-DRIVEN DESIGN:** Every design decision (colors, typography, imagery, layout) must be derived from the website's PURPOSE, not random.
3. **QUALITY OVER SPEED:** A 2-minute build that looks flawless beats a 30-second build that looks generic.
4. **ZERO-ERROR GUARANTEE:** The preview iframe must NEVER show a React error or white screen to the user. Infinite self-healing until it works.
5. **PREMIUM DEFAULTS:** Every component, whether catalog or generated, must meet a design quality floor. No "Coming Soon" placeholders. No placeholder text.

### 3.4 Current Prompt Weaknesses (enhance-prompt.js)
**Status:** Needs Major Upgrade  

The current system prompt is:
> "You are an expert UX writer and product designer..."
> Rules include "Make it feel premium" and "Be concrete"

**Problems:**
1. No design system guidance — the enhance step doesn't inject ANY color palette, typography, or layout rules based on website purpose
2. No industry-specific direction — "Make a dog website" gets the same generic "premium" treatment as "Make a bank website"
3. No output structure — the enhanced prompt is free-form text, not structured with explicit color/mood/typography directives
4. No contextual color reasoning — the system never asks "What colors suit a dog grooming business?" (earthy browns, warm golds, natural greens)

### 3.5 Current Selection Weaknesses (select-components.js)
**Status:** Needs Major Upgrade  

The select-components system prompt currently:
1. Dumps the ENTIRE catalog JSON into the system prompt for the LLM
2. Has NO suitability context per component (which industries/niches)
3. Has NO color context (does this component use dark mode? light mode?)
4. Has NO visual description to help the LLM understand what it's selecting
5. Confidence thresholds are reasonable (0.72 high, 0.55 adaptation) but the LLM doesn't have enough information to make accurate confidence calls

### 3.6 Current Generation Weaknesses (generate-single-component.js)
**Status:** Needs Major Upgrade  

The system prompt for component generation:
1. Says "Stunning, premium, high-conversion UI" — but provides NO specific design direction based on the actual website purpose
2. Uses Tailwind CSS utilities with no design token guidance
3. No color palette injection — the AI picks random gradients
4. No typography guidance — no font family, size scale, or hierarchy rules
5. No mood/tone guidance — components ignore the emotional context
6. The "MEDIA RULES" section just says "Use realistic Unsplash URLs" without guidance on WHAT to search for (dog images for dog sites, etc.)

## Gap Analysis: Current State vs. Vision

### 4.1 Design Quality Gap
**Priority:** CRITICAL — Priority 1  
**Impact:** High  

**Problem:** A user asks for a "dog grooming website" and gets purple-pink gradients with generic "Welcome to our website" copy. The design has zero connection to the actual business type.

**Root Cause:** The pipeline has NO contextual design intelligence. At no point does any agent reason about:
- What colors suit dog grooming? (warm earth tones, golden amber, forest green)
- What imagery? (happy dogs, grooming tools, clean facilities)
- What tone? (friendly, trustworthy, playful but professional)
- What typography? (rounded, approachable fonts — not sharp/angular)

**Solution:** Insert a "Design System Derivation" step between enhance-prompt and select-components. This new agent (GPT-4o) takes the enhanced prompt and produces a structured design system object:
```json
{
  "colorPalette": {
    "primary": "#D4A76A",
    "secondary": "#2D5016",
    "accent": "#F5E6D3",
    "background": "#FAFAF5",
    "text": "#1A1A1A",
    "mood": "warm, natural, friendly"
  },
  "typography": {
    "heading": "Nunito, rounded-sans",
    "body": "Inter, sans-serif",
    "tone": "approachable, clear"
  },
  "imagery": {
    "subjects": ["happy dogs", "grooming", "clean spaces"],
    "style": "bright, warm lighting, lifestyle photography",
    "unsplashKeywords": ["dog grooming", "golden retriever", "pet spa"]
  },
  "mood": "friendly, trustworthy, playful-professional",
  "industryFit": ["pet services", "dog grooming", "animal care"],
  "layoutPreference": "warm, open spacing, rounded corners, card-based"
}
```

This design system is then injected into EVERY subsequent pipeline stage:
- select-components: "Select components that match warm/natural palette"
- plan-website-components: "Plan layout with rounded corners, warm tones"
- generate-single-component: "Use these exact colors: primary=#D4A76A..."

### 4.2 Component Catalog Context Gap
**Priority:** CRITICAL — Priority 1  
**Impact:** High  

**Problem:** The catalog entries have minimal context. The LLM selecting premium components doesn't know what they look like, what colors they use, or which industries they suit. It's guessing based on vague "tags" and "keywords."

**Solution:** Expand every catalog entry with rich metadata (see Appendix A for full schema). Key additions per component:
- `"visualDescription"`: "A dark-themed hero with a large video background..."
- `"colorProfile"`: `{ "primary": "#000", "accents": ["#F97316"], "mode": "dark" }`
- `"suitableFor"`: `["tech startups", "SaaS", "agencies", "luxury brands"]`
- `"notSuitableFor"`: `["children's sites", "pet stores", "bakeries"]`
- `"moodTone"`: "bold, futuristic, high-tech"
- `"typographyStyle"`: "large display sans-serif, monospace accents"

### 4.3 Component Catalog Size Gap
**Priority:** High — Priority 2  

**Current:** 52 bundles across 11 categories  
**Target:** 150 bundles across 20+ categories

New categories needed:
- About / Team
- Contact / Form
- Blog / Article
- Gallery / Portfolio
- Map / Location
- Stats / Numbers
- Newsletter / Signup
- Services / What We Do
- Process / How It Works
- Clients / Logos (enhanced)

### 4.4 Publishing Gap
**Priority:** High — Priority 2  

**Current:** No public publishing. Users can only preview in the iframe and download ZIP.  
**Target:** Public URLs like `https://dog-website.volturiano.com/builder/live/[slug]`

### 4.5 GitHub Gap
**Priority:** High — Priority 2  

**Current:** No GitHub integration. Users download ZIP only.  
**Target:** One-click "Push to GitHub" button beside the download button.

### 4.6 Checkpoint Gap
**Priority:** Medium — Priority 3  

**Current:** No checkpoint system. If a chat iteration makes things worse, the user cannot go back. Chat history is ephemeral.  
**Target:** Every chat message creates a snapshot. User can click any previous chat to restore the website to that exact state.

### 4.7 Account & Monetization Gap
**Priority:** Medium — Priority 3  

**Current:** No auth for builder. No credits. No usage tracking. No billing.  
**Target:** Supabase accounts (separate from car platform), credits system, Stripe payments, free daily allowance (15 sites × 2 chats each).

      await updateSubscription(event.data.object);
      break;
    case 'customer.subscription.deleted':
      await cancelSubscription(event.data.object);
      break;
  }

  res.json({ received: true });
});
`

### 9.6 Credit Check Middleware
**Priority:** Critical  
**Estimated Time:** 2-3 days  

**Detailed Steps:**

**Step 9.6.1: Implementation**
`javascript
// server/middleware/credit-check.js
export async function requireCredits(req, res, next) {
  const userId = req.user?.id;
  if (!userId) {
    // Guest user - check IP rate limit
    const guestBuilds = await getGuestBuildCount(req.ip);
    if (guestBuilds >= 2) {
      return res.status(403).json({
        error: 'guest_limit',
        message: 'Sign up for 15 free daily builds'
      });
    }
    return next();
  }

  const profile = await getBuilderProfile(userId);

  // Reset daily credits if new day
  if (profile.daily_credits_reset_at < today()) {
    await resetDailyCredits(userId);
    profile.daily_credits_used = 0;
  }

  // Check free daily allowance first
  if (profile.daily_credits_used < 15) {
    return next();
  }

  // Check purchased credits
  if (profile.total_credits_remaining > 0) {
    return next();
  }

  // Check subscription
  if (profile.plan === 'pro' || profile.plan === 'enterprise') {
    return next();
  }

  return res.status(403).json({
    error: 'insufficient_credits',
    message: 'Daily limit reached. Purchase more credits or upgrade to Pro.',
    creditsUsed: profile.daily_credits_used,
    creditsLimit: 15
  });
}

### F.1 Emergent (E1 Agent)  Key Intelligence

#### F.1.1 Architecture Overview

Emergent uses a full-stack template: React frontend + FastAPI backend + MongoDB. The agent operates inside a Docker machine with supervisord managing services.

**Key architectural properties:**
- Frontend on port 3000, backend on port 8001
- Hot-reload enabled for both frontend and backend
- Kubernetes ingress routes /api/* to backend, everything else to frontend
- Environment variables are PROTECTED  never hardcoded, never modified
- Uses ShadCN UI component library (pre-installed, 40+ components)
- Tailwind CSS with dark/light mode support via CSS variables
- React Router for client-side routing

#### F.1.2 Development Workflow (Critical  Adopt This Pattern)

Emergent's 5-step workflow is the GOLD STANDARD for phased delivery:

**Step 1: ANALYSIS & CLARIFICATION**
- Never proceed with unclear requests
- If external API keys needed, ask user BEFORE proceeding
-  **VOLTURIANO ADOPTION:** Our enhance-prompt step should detect when user intent is ambiguous and request clarification through the chat UX before burning generation credits.

**Step 2: FRONTEND-FIRST WITH MOCK DATA**
- Build frontend ONLY with mock data (mock.js file, not hardcoded)
- Components capped at 300-400 lines each
- Maximum 5 files written per batch
- Interactive elements MUST work as frontend-only experiences
- Use SCREENSHOT TOOL to verify app was actually created
- Ask user approval before proceeding to backend
-  **VOLTURIANO ADOPTION:** Our builder already does frontend-first, but we should cap component size (currently unlimited) and add a visual verification step after rendering (Phase 4: screenshot/DOM check).

**Step 3: BACKEND DEVELOPMENT**
- Create /app/contracts.md capturing: API contracts, mock data mapping, backend implementation plan, frontend/backend integration approach
-  **VOLTURIANO ADOPTION:** When we add multi-page + backend features (Phase 13), generate a contracts document for Supabase integration.

**Step 4: TESTING PROTOCOL**
- test_result.md is a living document (never recreated, only updated)
- Backend testing always runs FIRST
- Frontend testing requires EXPLICIT user permission
- Never fix something that a testing agent already fixed
-  **VOLTURIANO ADOPTION:** Our self-healing loop (Phase 4) should maintain a repair log in the build manifest. Also adopt the principle of never duplicating a fix attempt.

**Step 5: POST-TESTING**
- Web search for latest solutions when stuck in error loops
-  **VOLTURIANO ADOPTION:** Include a web search fallback in our infinity repair loop (Phase 4) when standard repair strategies fail.

### F.2 Google AI Code (AI Studio)  Key Intelligence

#### F.2.1 Architecture Overview

Google's AI Code generator is a FRONTEND-ONLY React SPA generator:

#### F.2.2 Code Generation Structure (Adopt for Phase 3)

- index.html (required)  browser entry
- App.tsx (required)  main component

**XML-Based Output Format:**
`xml
<changes>
  <change>
    <file>[full_path]</file>
    <description>[what changed]</description>
    <content><![CDATA[full file content]]></content>
  </change>
</changes>
`
-  **VOLTURIANO ADOPTION:** We already use <file path=...> XML tags via file-blocks.js. Google's addition of <description> per file is worth adopting  pipe file descriptions to the AI narrator for better chat messages.

**Metadata.json:**
- Every generated app includes a metadata.json with name + description
- Can declare required permissions (camera, microphone, geolocation)
-  **VOLTURIANO ADOPTION:** Generate a site-metadata.json in each build for the publishing system (Phase 5). Include: name, description, industry, design system summary, build timestamp.

#### F.2.3 React Pitfall Prevention (Adopt for Phase 3 & 4)

**Infinite Loop Prevention:**
- useEffect + useCallback dependency chains cause infinite re-renders
- Solution: Use functional state updates (prevState => ...) and empty dependency arrays with eslint-disable comments
-  **VOLTURIANO ADOPTION:** Add these anti-patterns to our generate-single-component system prompt as explicit FORBIDDEN patterns. Also add infinite loop detection to our verify-build step.

**Component Scope Rules:**
- NEVER define components inside other component function bodies
- Define helper components OUTSIDE parent to prevent remount issues
- Pass state as props, not via closure
-  **VOLTURIANO ADOPTION:** Add COMPONENT SCOPE rules to our generation prompt. This prevents real bugs in generated code.

**Template Literal Escaping:**
- Never escape outer backticks of template literals
- Always escape inner backticks
-  **VOLTURIANO ADOPTION:** Add to generation prompt as code quality rule.

**Router Limitations:**
- MUST use HashRouter instead of BrowserRouter in sandboxed environments
-  **VOLTURIANO ADOPTION:** Critical for Phase 13 (multi-page routing). Our E2B sandbox uses iframe, so HashRouter is the correct choice. BrowserRouter would break in the preview iframe.

#### F.2.4 Responsive Design (Adopt for Phase 1)
- Mobile-first approach: design for smallest screen, enhance upward
- Tailwind breakpoint prefixes (sm:, md:, lg:)
- Persistent call-to-action: make primary controls sticky
-  **VOLTURIANO ADOPTION:** Add RESPONSIVE DESIGN directives to both derive-design-system (include responsive strategy) and generate-single-component (enforce mobile-first Tailwind classes).

### F.5 Prompt Engineering Patterns to Adopt

#### F.5.1 From Emergent  The Agency Mindset

Emergent frames their agent as a powerful, intelligent & creative agent that builds launchable MVPs that customers love. Their prompts emphasize:
- Build ambitious applications that go beyond toy apps
- Create the first aha moment as soon as possible
- Frontend should act as a good and complete teaser to a full stack app
- Thorough thinking in EVERY output (planning, architecture reasoning)

 **ADOPT:** Frame our Maestro narrator (Phase 14) with this same ambition. The chat messages should convey we're building something premium energy.

#### F.5.2 From Google  Structured Precision

Google's prompts are EXTREMELY detailed and structured. Key patterns:
- Every correct and incorrect example is shown side-by-side
- Forbidden patterns are explicitly listed with exact code
- Output format is rigidly defined (XML structure)
- Type safety rules are exhaustive (import rules, enum rules)

 **ADOPT:** Our generation prompts (Phase 3) should include CORRECT vs INCORRECT example pairs. Show the AI exactly what bad output looks like and what good output looks like. This dramatically reduces errors.

#### F.5.3 From Lovable  Design System First

Lovable's prompts obsessively repeat the design system message:
- The design system is EVERYTHING
- Start with the design system. This is CRITICAL.
- ALL styles must be defined in the design system
- NEVER write ad hoc styles in components
- Make designs that WOW the user at first glance

 **ADOPT:** Mirror this obsessive reinforcement in our Phase 1 prompts. The derive-design-system step is not optional  it's THE foundation. Every downstream prompt should repeat: USE THE DESIGN SYSTEM TOKENS.
