PURPOSE
-------
After you run real builds (hybrid/strict premium), use this file to know:
  • What should be true for each implemented phase (0–3, 4, 6, 8) and planned later phases
  • Which server/client log lines to capture and send back for “official” completion sign-off

§3 NOTE (BuilderStraightUpgrade.txt — “Premium copy: why it never lands”)
-------------------------------------------------------------------------
  • `bundleToFileBlocks` prop-regex still only rewrites default prop patterns; that is expected.
  • Body/demo copy is addressed by Phase 1 hydrate + Phase 0 premium copy-only polish, and by
    fuzzy copywriter name merge. Verification = hydrate + layoutType logs below + preview text.

LOG PREFIX (grep-friendly)
---------------------------
All temporary verification logs use:

  [BUILDER-VERIFY]

Server (Node): search your terminal running `web/server` (or Railway logs):

  Windows PowerShell:  Select-String -Path .\path\to\log.txt -Pattern "BUILDER-VERIFY"
  Or copy terminal output and search for BUILDER-VERIFY

Client (browser): DevTools → Console → filter: BUILDER-VERIFY

LOG REFERENCE (what each line means)
------------------------------------
Phase 0 — polish / apply
  [BUILDER-VERIFY] apply: premiumPolishPaths override count=N
      → Optional explicit premium paths sent on apply (rare).
  [BUILDER-VERIFY] polish split: standard=A premiumCopyOnly=B premiumPathsOverride=C
      → Final polish will run full rewrite on A files, copy-only on B (C = size of override Set).
  [BUILDER-VERIFY] polish file mode=premiumCopyOnly path=…
      → Per-file confirmation of copy-only mode under premium/.
  [BUILDER-VERIFY] mini-polish: candidateFiles=N (paths under src/components/premium/ excluded)
      → Mini pass intentionally skips premium catalog files.
  [BUILDER-VERIFY] apply: polish rollback — pre-polish snapshot restored …
      → Polish failed verify twice; sandbox was restored to the snapshot taken immediately before the polish pass.

Phase 1 — plan merge + hydration
  [BUILDER-VERIFY] plan copy merge: fuzzyMatched planComponent="…" copywriterRow="…"
      → Copywriter name did not match exactly; fuzzy merge used (expected sometimes).
  [BUILDER-VERIFY] hydrate: skipped no keyContent/props file=…
      → Route short-circuit (should align with client not calling when empty).
  [BUILDER-VERIFY] hydrate: start file=… chars=… model=… hasKey=… propKeys=…
      → LLM hydration call started.
  [BUILDER-VERIFY] hydrate: done file=… outChars=… skipped=false
      → Hydration produced new file content.
  [BUILDER-VERIFY] hydrate: done file=… skipped=no_file_block | empty_block
      → Model output unusable; original content kept.

Client (Generation.jsx)
  [BUILDER-VERIFY] generation: plan layoutType= …
      → Echo of server-resolved archetype (Phase 2).
  [BUILDER-VERIFY] generation: hydrate request { bundle, path, hasKey, propCount }
  [BUILDER-VERIFY] generation: hydrate applied { path, skipped, outLen }

Phase 2 — layoutType + dynamic counts (plan + V2 pipeline)
  [BUILDER-VERIFY] plan layoutType=… (v2.payload=…|inferred) | (source=v1)
      → Resolved archetype; V2 uses selectComponentsV2.layoutType or inferLayoutTypeFromPrompt.
  [BUILDER-VERIFY] v2 structural inject: layoutType=web-app (only header required…)
      → V2 pool step will not inject hero/footer from candidates when web-app.
  [BUILDER-VERIFY] enforcePlanStructure: layoutType=web-app (dedupe only…)
      → Plan-level dedupe pass aware of web-app (no extra behavior beyond logging).

Phase 3 — intent classification (pre-plan)
  [BUILDER-VERIFY] classify-intent: layoutType=… complexity=… needsHero=…
      → Lightweight `generateObject` result from `/api/classify-intent`.
  [BUILDER-VERIFY] generation: intentClassification layoutType= …
      → Client received intent and will pass it to plan.
  [BUILDER-VERIFY] plan layoutType override intentClassification=…
      → Plan used classifier layout type instead of V2/inferred only.
  [BUILDER-VERIFY] plan layoutType=… (source=v1+intent)
      → V1 JSON plan merged with intent when applicable.

Phase 4 + 8 — smart polish + efficiency (death-spiral mitigation)
  [BUILDER-VERIFY] polish filter: skippedTiny=… skippedSkipPaths=… polishable=…
      → Files under 500 chars and optional skipPaths excluded before triage.
  [BUILDER-VERIFY] polish triage: standard=N skip=… copy_only=… full_polish=…
      → Lightweight triage of standard (non-premium) files.
  [BUILDER-VERIFY] polish workItems=N (parallel batch)
      → Actual LLM batch size after triage + premium copy-only queue.
  [BUILDER-VERIFY] polish concurrency poolLimit=2|3
  [BUILDER-VERIFY] polish designSpec=from_apply_cache
      → Design spec was pre-computed in apply (repair pass does not regenerate).
  [BUILDER-VERIFY] apply: designSpec pre-cached for polish (repair pass reuses)
  [BUILDER-VERIFY] apply: polishSkipPaths count=N
      → Optional body polishSkipPaths (e.g. freshly generated single-component paths).
  [BUILDER-VERIFY] mini-polish: narrowed X → Y file(s) (only paths changed by main polish)
      → Mini pass scope reduced vs whole sandbox.

Phase 6 — visual verify after vite build (BuilderStraightUpgrade §7)
  [BUILDER-VERIFY] visual verify ok scrollHeight=… textLen=… media=…
      → Puppeteer loaded the sandbox preview URL; DOM looks non-empty.
  [BUILDER-VERIFY] visual verify hasContent=false scrollHeight=… textLen=… media=…
      → Likely blank or near-empty page; client should also receive SSE warning.
  [BUILDER-VERIFY] visual verify skipped: …
      → No URL, or Puppeteer/DOM check threw (non-fatal).

WHAT TO SEND BACK AFTER A TEST BUILD
------------------------------------
1. One paragraph: prompt used, premiumMode (hybrid/strict/off), model id.
2. Server lines containing [BUILDER-VERIFY] from that session (or full server log chunk).
3. Any [BUILDER-VERIFY] lines from the browser console (Generation.jsx).
4. If polish rolled back: note whether preview still worked; include VERIFY / POLISH lines if present.

PHASE 0 — Premium polish protection (IMPLEMENTED)
================================================================================

ASSURANCES TO CHECK
-------------------
• Paths under `src/components/premium/` are treated as premium for final polish
  (`isPremiumFile`); copy-only prompts, no raw salvage on missing `<file>` blocks.
• Optional body `premiumPolishPaths` (array) on apply → `premiumPaths` Set for extra paths.
• Phase 4 triage never upgrades premium to full-rewrite polish (always copy-only queue).
• Mini-polish does not read or rewrite files under `PREMIUM_PATH_PREFIX`
  (apply-ai-code-stream.js).

DEBUG LINES YOU SHOULD SEE (server)
-----------------------------------
• [BUILDER-VERIFY] apply: premiumPolishPaths override count=N
• [BUILDER-VERIFY] polish split: standard=… premiumCopyOnly=…

SUCCESS CRITERIA
----------------
• Build completes; premium JSX still runs (no blank shader canvas from polish).
• Logs show premium file count > 0 when the project has premium components.

PHASE 1 — Copy hydration + copywriter name merge (IMPLEMENTED)
================================================================================

ASSURANCES TO CHECK
-------------------
• Plan merge: copywriter row matches plan component by exact name OR normalized name
  (spaces/dashes/underscores stripped, case-insensitive).
• After each premium bundle (Generation.jsx Stage A.1), if `keyContent` or `props`
  exists, each `.jsx`/`.tsx` in that bundle is POSTed to `/api/hydrate-premium-copy`
  before the merged file list is sent to apply.
• Hydrate uses `resolveLightweightModel(heavyModel)`; body may include `model`, `buildId`.

DEBUG LINES YOU SHOULD SEE
---------------------------
Server:
• [BUILDER-VERIFY] plan copy merge: fuzzyMatched=… plan=… copywriter=…
• [BUILDER-VERIFY] hydrate: start …
• [BUILDER-VERIFY] hydrate: done … (skipped=…)

Client (browser):
• [BUILDER-VERIFY] generation: hydrate request { bundle, path, hasKey, propCount }
• [BUILDER-VERIFY] generation: hydrate applied { path, skipped, outLen }

SUCCESS CRITERIA
----------------
• For a hybrid build with premium: hydrate “start/done” appears for bundles that have copy.
• Preview shows user-specific copy before you rely on polish alone.
• If hydrate skips (no keyContent/props), logs show skipped path—expected for some bundles.

PHASE 2 — Dynamic component counts / layoutType (IMPLEMENTED)
================================================================================

  BuilderStraightUpgrade.txt §5 (component count ceiling): superseded by this phase —
  V1 adaptive `layoutType` bands + V2 "6–20" / targetSize 6–18; see roadmap Phase 2 checklist.

ASSURANCES TO CHECK
-------------------
• API `plan` / `planData` includes `layoutType` (marketing-landing | business-site | web-app |
  portfolio | e-commerce).
• V1 JSON plan: model sets `layoutType`; if missing, server fills via inferLayoutTypeFromPrompt.
• V2: select-components-v2 raises selection ceiling (6–20 in prompts, targetSize up to 18) and
  passes layoutType on the v2 result object.
• web-app: hybrid “missing role” fillers do not add hero/footer shells; mandatory fallback
  injection after flatten skips hero/footer; structural selection only requires header from pool.

SUCCESS CRITERIA
----------------
• Dashboard-style prompt → layoutType web-app in logs; component count can exceed old 5–9 band.
• Marketing prompt → marketing-landing or business-site; hero/footer still plausible.

PHASE 4 + 8 — Smart polish + efficiency (IMPLEMENTED)
================================================================================

ASSURANCES TO CHECK
-------------------
• Triage runs on standard files (premium stays copy-only without triage).
• Parallel polish uses concurrency 2 (Anthropic) / 3 (others); files &lt;500 chars skipped;
  optional `polishSkipPaths` on `/api/apply-ai-code-stream` merged into polish `skipPaths`.
• Design spec: `[BUILDER-VERIFY] apply: designSpec pre-cached for polish (repair pass reuses)`;
  polish may log `[BUILDER-VERIFY] polish designSpec=from_apply_cache`.
• Salvage of raw code without &lt;file&gt; tags is disabled for copy-only and repair passes.
• Mini-polish: `[BUILDER-VERIFY] mini-polish: narrowed X → Y file(s) (only paths changed by main polish)`
  when narrowing applies; optional `polishSkipPaths` → `[BUILDER-VERIFY] apply: polishSkipPaths count=N`.
