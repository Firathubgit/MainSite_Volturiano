1. EXECUTIVE SUMMARY (FOR JUNIORS)
================================================================================

Welcome to the Volturiano Builder. If you are reading this, you are responsible
for maintaining the most advanced AI code generation pipeline in the world.

**What does this system actually do?**
It takes a user's vague idea (e.g., "Build a Netflix clone for cats") and
turns it into a real, working React application running inside a secure
virtual machine (E2B Firecracker MicroVM).

**It is NOT just a text generator.**
It is a **Multi-Agent System**. Think of it like a digital software agency:
1.  **The PM (GPT-4o)**: Talks to the client, figures out specs, enhances prompts.
2.  **The Curator (GPT-4o)**: Selects premium components from a 52-bundle catalog.
3.  **The Architect (Gemini 3.1 Pro)**: Decides which files to build, with structural IDs.
4.  **The Devs (Gemini 3.1 Pro)**: Write the actual code (Hero.jsx, App.jsx) using structured output.
5.  **The DevOps (Python/Node)**: Write files to VM, install packages, restart Vite.
6.  **The Inspector (npx vite build)**: Verifies the build passes.
7.  **The Surgeon (auto-repair.js)**: Fixes broken imports if the build fails.
8.  **The Narrator (GPT-4o-mini)**: Talks to the user during build like a human dev.

**What changed in the last week (Feb 10-17, 2026)?**
- Build Manifest system for tracking all pipeline stages
- Auto-Repair engine that regenerates App.jsx when imports break
- Import Graph validator that checks relative imports before build
- SSE Event contracts with typed events (verify_started, repair_done, etc.)
- AI Build Narrator that generates conversational build messages via GPT-4o-mini
- Deterministic App.jsx rendering via render-app-template.js
- ComponentSelector UI for manual premium component picking
- Serial Delivery Queue for ordered file-write log messages
- Concurrency limits on parallel component generation
- Schema refinements (refId, exportName, appComposition, nullable fields)
- Sandbox Factory pattern + SandboxManager singleton
- File cache in global.sandboxState for edit-mode context

3. BUILD MODES (3 ENTRY POINTS)
================================================================================

The Builder has THREE distinct ways to produce an app. Understanding which mode
is used is critical for debugging.

### 3.1 Prompt Mode (Default)
**Trigger**: User types a prompt like "Make a bakery website"
**Flow**: enhance → select → plan → generate/bundle → apply
**Key Files**: All route files are involved
**Code Path**: `startGeneration(prompt, null, images, null)` in Generation.jsx

### 3.2 Template Mode
**Trigger**: User selects a template from the Builder page (templateId is set)
**Flow**: build-template → apply (skips enhance/select/plan entirely)
**Key File**: `server/routes/build-template.js`
**Code Path**: `startGeneration(prompt, templateId, images, null)` in Generation.jsx
**How it works**: Templates are predefined compositions in `server/lib/registry/templates/`.
  Each template lists component IDs. The registry resolves all bundles, assembles
  App.jsx, and returns the complete code payload.

### 3.3 Manual Selection Mode
**Trigger**: User opens the ComponentSelector UI and picks specific components
**Flow**: build-from-selection → apply (skips enhance/select/plan entirely)
**Key File**: `server/routes/build-from-selection.js`
**Code Path**: `startGeneration(prompt, null, images, manualSelectionIds)` in Generation.jsx
**How it works**: The user hand-picks component IDs. The registry resolves each
  bundle, assembles App.jsx deterministically, and returns the code.

### 3.4 Edit Mode (Post-Build Iteration)
**Trigger**: User types a follow-up prompt after initial build
**Flow**: Two paths—
  Path A (retry with structured pipeline): Same as Prompt Mode but with isEdit=true
  Path B (fallback streaming): generate-ai-code-stream with conversation context
**Key Detail**: The fallback streamer injects ALL existing file contents from
  `global.sandboxState.fileCache` into the system prompt (up to 50,000 chars
  per file). This ensures the AI doesn't lose context during edits.

### 4.6 Serial Delivery Queue
File-write events ("Wrote src/components/Hero.jsx") need to appear in
chronological order with 2-second delays between them. The delivery queue
ensures this:
```javascript
useEffect(() => {
  if (deliveryQueue.length === 0 || isProcessingQueue.current) return;

  const processNext = async () => {
    isProcessingQueue.current = true;
    const [next, ...rest] = deliveryQueue;

    if (next.type === 'log') {
      addChatMessage(next.path, 'log');
      await new Promise(r => setTimeout(r, 2000)); // 2s gap for creation effect
    } else {
      addChatMessage(next.content, next.chatType || 'ai-narrator', next.metadata);
      await new Promise(r => setTimeout(r, 400)); // Short gap for messages
    }

    setDeliveryQueue(prev => prev.slice(1));
    isProcessingQueue.current = false;
  };

  processNext();
}, [deliveryQueue, addChatMessage]);
```

### 5.2 What is a Bundle?
A bundle is a self-contained JSON file representing a premium component. It
contains the component's JSX code, CSS, and metadata. When the planner selects
a premium component, the builder fetches the bundle from the registry and
writes it directly to the sandbox — no LLM generation needed.

### 5.3 The Catalog (catalog.json — 73KB)
The catalog is a flat array of component metadata used for LLM selection.
Each entry includes: id, name, description, category, tags, requires
(packages). The `getCatalogForPrompt()` function returns a compact version
for injection into LLM prompts.

### 5.4 Key Registry Functions
- `getCatalog()` — Returns the full catalog with all metadata
- `getCatalogForPrompt(keywords, maxItems)` — Returns compact catalog for LLM
- `getBundle(id)` — Returns a specific bundle JSON by ID
- `bundleToFileBlocks(bundle, propsOverrides)` — Converts bundle to <file> tags
- `preflightBundleAssets(bundle)` — Validates that asset URLs are reachable
- `buildSelectionCode(componentIds)` — Assembles code from manual selection
- `buildTemplateCode(templateId)` — Assembles code from a template definition
- `listTemplates()` / `getTemplate(id)` — Template management

### 5.5 Asset Preflight
Before using a premium component, the system checks if all external assets
(images, videos, fonts) referenced in the bundle are actually reachable.
If they're not and `fallbackAllowed=true`, the component is moved to the
"custom generation" list. This prevents broken images in the final build.

7. THE SELF-HEALING PIPELINE (Auto-Repair + Import Graph)
================================================================================

This is the most significant engineering addition in the last week. The system
now verifies builds and attempts automatic repair when they fail.

### 7.1 Build Verification (verify-sandbox-build.js)
After writing all files to the sandbox, the pipeline runs `npx vite build`
inside the E2B MicroVM. This catches:
- Missing imports (Module not found)
- Syntax errors
- Invalid JSX
- Missing dependencies

```javascript
// verify-sandbox-build.js
const result = await sandbox.commands.run('npx vite build', {
  cwd: '/home/user/app',
  timeoutMs: 60000 // 1 minute timeout
});
const success = result.exitCode === 0;
```

### 7.2 Import Graph Validator (import-graph.js)
Before auto-repair, the system builds a dependency graph:
1. Collects all generated file paths into `availableFiles` Set
2. Adds premium component paths
3. Whitelists standard Vite files (index.css, main.jsx, App.css)
4. Scans every file for `import ... from './...'` statements
5. Checks if each relative import resolves to an available file
6. Supports extension resolution (.jsx, .js, .tsx, .ts, .css, .json)
7. Supports index file resolution (import './dir' → './dir/index.jsx')
8. Returns array of issues with code `E-IMP-01`

### 7.3 Auto-Repair Engine (auto-repair.js)
When the build fails, the auto-repair engine attempts to fix it:

**Strategy A: Regenerate App.jsx** (currently the only strategy)
1. Run the import validator to find broken imports
2. Filter for missing imports in App.jsx specifically
3. Build list of valid components from (a) premium list and (b) generated files
4. Extract export names from generated file content using regex
5. Call `renderAppTemplate()` to deterministically generate a new App.jsx
   that ONLY imports components that actually exist
6. Write the fixed App.jsx to the sandbox
7. Run build verification again

```javascript
// auto-repair.js
const issues = validateImports(files, premiumComponents);
const missingImports = issues.filter(i => i.kind === 'missing_local_import');
const appIssues = missingImports.filter(i => i.from.endsWith('App.jsx'));

// ... extract valid components from files ...

const newAppJsx = renderAppTemplate({ components: uniqueValidComponents });
return { success: true, fixedFiles: [{ path: 'src/App.jsx', content: newAppJsx }], strategy: 'regenerate_app_jsx' };
```

### 7.4 Deterministic App.jsx Rendering (render-app-template.js)
Instead of asking the AI to generate App.jsx (which can hallucinate imports),
we now have a deterministic template renderer:
```javascript
export function renderAppTemplate({ components }) {
  // Converts: [{ exportName: 'Hero', path: 'src/components/Hero.jsx' }, ...]
  // Into: A complete App.jsx with correct imports and render order

  return `import React from 'react'
import './index.css'
import Hero from './components/Hero.jsx'
import Footer from './components/Footer.jsx'

export default function App() {
  return (
    <div className="min-h-screen">
      <Hero />
      <Footer />
    </div>
  )
}`;
}
```

### 8.1 Event Types (sse-events.js)
The build pipeline communicates via Server-Sent Events (SSE) with typed events:

| Event Type | Category | Payload |
|-----------|----------|---------|
| `plan_started` | Lifecycle | `{ buildId, prompt }` |
| `apply_started` | Lifecycle | `{ buildId, files, components }` |
| `file_written` | Lifecycle | `{ path, size }` |
| `verify_started` | Lifecycle | `{ cmd }` |
| `verify_passed` | Lifecycle | `{ durationMs }` |
| `verify_failed` | Lifecycle | `{ excerpt, logs }` |
| `repair_started` | Lifecycle | `{ strategy, files }` |
| `repair_done` | Lifecycle | `{ changed }` |
| `rollback_started` | Lifecycle | — |
| `rollback_done` | Lifecycle | `{ filesRestored }` |
| `complete` | Lifecycle | `{ filesCreated, verified, durationMs }` |
| `ai_thinking` | AI | `{ stage, durationMs? }` |
| `ai_message` | AI | `{ message, context?, style? }` |
| `ai_thought` | AI | `{ thought }` |
| `progress` | Progress | `{ current, total, item }` |
| `error` | System | `{ message }` |
| `warning` | System | `{ message }` |
| `keepalive` | System | (empty, sent every 15s) |

### 8.2 SSEWriter Class
A utility class that wraps the HTTP response with typed event sending:
```javascript
const sse = new SSEWriter(res);
sse.send(SSE_EVENTS.FILE_WRITTEN, { path: 'src/components/Hero.jsx', size: 4521 });
sse.aiMessage('Building the hero section with gradient backgrounds...', {}, 'casual');
sse.aiThinking('verifying');
sse.end();
```

### 8.3 Frontend SSE Processing (SSEEventHandler.jsx)
The `useSSEEvents` hook provides `processChunk(text)` which:
1. Splits raw text by newline
2. Detects `event:` and `data:` lines
3. Dispatches to `onThinking`, `onMessage`, `onStatusUpdate`, `onComplete`, `onError`

SSEEventHandler.jsx also exports:
- `AIThinkingIndicator` — Animated shimmer text ("Analyzing...", "Designing...")


### 10.3 Sandbox Creation Flow (create-ai-sandbox-v2.js)
1. Defensively cleanup: `sandboxManager.terminateAll()`, `global.activeSandboxProvider.terminate()`
2. Clear `global.existingFiles`
3. Check for `E2B_API_KEY` in environment
4. `SandboxFactory.create()` → new E2BProvider
5. `provider.createSandbox()` → returns { sandboxId, url }
6. `provider.setupViteApp()` → writes Vite boilerplate (vite.config.js, package.json, etc.)
7. Register in SandboxManager
8. Set global state
9. Return { sandboxId, url } to client

### 10.4 File Cache for Edit Mode
When files are written to the sandbox, they're also cached in
`global.sandboxState.fileCache.files`. During edit mode, the fallback
streaming generator (`generate-ai-code-stream.js`) injects ALL cached
file contents (up to 50,000 chars each) into the system prompt. This
ensures the AI has full context of the existing codebase.

11. THE BUILD MANIFEST (Single Source of Truth)
================================================================================

### 11.1 Purpose
The Build Manifest is an in-memory store that tracks every stage of a build.
Each build is identified by a UUID (`buildId`) generated at the start of
`startGeneration()` in Generation.jsx.

### 11.2 Manifest Structure
```javascript
{
  build_id: 'uuid-here',
  mode: 'initial',              // 'initial' | 'edit' | 'template'
  startTime: Date.now(),
  lastUpdate: Date.now(),
  planned: [                    // Set by plan-website-components.js
    { refId: 'HeroSection', path: 'src/components/Hero.jsx', source: 'premium', description: '...' }
  ],
  generated: [                  // Pushed by generate-single-component.js
    { path: 'src/components/Hero.jsx', bytes: 4521, timestamp: Date.now() }
  ],
  applied: [                    // Pushed by apply-ai-code-stream.js
    'src/components/Hero.jsx'
  ],
  verify: {
    status: 'pending',          // 'pending' | 'passed' | 'failed'
    logs: []
  }
}
```

### 11.3 API
```javascript
import { createManifest, getManifest, updateManifest, log } from '../lib/build-manifest.js';

createManifest(buildId, 'initial');                                    // Start a new build
updateManifest(buildId, { planned: [...] });                           // Set planned components
updateManifest(buildId, { generated: [{ path, bytes, timestamp }] }); // Push generated file
updateManifest(buildId, { applied: ['src/App.jsx'] });                 // Push applied file
log(buildId, '[route-name] message');                                  // Consistent logging
```

JUNIOR DEVELOPER FAQ (UPDATED)
================================================================================

**Q: Why do we generate App.jsx last?**
A: Because App.jsx imports other components. If generated first, it might import
files that don't exist yet. Additionally, the auto-repair system can regenerate
App.jsx deterministically using render-app-template.js, which only imports files
that are confirmed to exist.

**Q: What is "Premium Mode"?**
A: Pre-built, human-coded components from the registry (52 bundles). When enabled,
the selector (GPT-4o) picks matching bundles from the catalog. Premium components
skip LLM generation entirely — the code is read directly from the bundle JSON.
This makes them faster AND higher quality than generated components.

**Q: Why does the preview sometimes show a white screen?**
A: Usually a "Module Not Found" error from hallucinated imports. The auto-repair
system now catches this: it runs `npx vite build`, detects the missing import
via the import graph validator, and regenerates App.jsx without the broken import.

**Q: What is the Build Manifest?**
A: An in-memory data structure (Map) that tracks every stage of a build:
planned components, generated files, applied files, and verification status.
Each build has a UUID. All route files log to it via `log(buildId, message)`.

**Q: What is the Serial Delivery Queue?**
A: A mechanism that ensures "Wrote src/components/Hero.jsx" messages appear in
the chat in chronological order with 2-second delays between each one. Without
it, files could appear out of order or all at once.

**Q: How do I add a new premium component?**
A: Create a JSON file in `server/lib/registry/bundles/` following the existing format
(id, name, files array with path+content). Then add the component's metadata to
`catalog.json` with id, name, description, category, tags, and requires fields.

**Q: What happens when the AI hallucinates an icon name?**
A: The system prompt explicitly blacklists known problematic icons:
"Do NOT use 'UniversalAccess' or 'Accessibility'. Use 'Eye', 'Globe', or 'Check' instead."
This is enforced in the generate-single-component.js system prompt.

**Q: What is the "Fallback Streaming" path?**
A: If the structured pipeline fails (e.g., sandbox 500 error, structured output
parse error), Generation.jsx falls back to `generate-ai-code-stream.js` which
streams raw text with <file path="...">code</file> tags. This is less reliable
but more resilient. The apply pipeline handles both formats.

**Q: How does the confidence threshold work in component selection?**
A: Two thresholds in app.config.js:
- `confidenceThreshold` (0.72): Components above this are used as-is
- `adaptationThreshold` (0.55): Components between 0.55-0.72 need prop adaptation
- Below 0.55: Dropped, moved to "customComponentsNeeded" for LLM generation
